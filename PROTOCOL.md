The MCP adapter connects to IPv4 loopback `127.0.0.1:61172` by default. Both the extension host process and client may set `BITWIG_AGENT_PORT` to the same alternate port; the extension reads it during initialization, validates ASCII decimal `1..65535`, and still binds only `127.0.0.1`. One UTF-8 JSON request and one JSON response per TCP connection, each terminated by newline. This is internal transport, not an extra agent orchestration protocol. No automatic retries. Requests are limited to 1 MiB and responses to 16 MiB; a response over the cap is, for a write, an unknown result with reason `transport` (a read gets the error).

The TCP endpoint is unauthenticated. Any local process able to connect can invoke tools; use only in a trusted local environment and never expose or forward this port to a network. Context tokens and target guards are not authentication.

Request:

```json
{"id":"client-generated-unique-id","protocol":"0.5","method":"status","params":{},"timeoutMs":5000}
```

`id` is a nonempty string (maximum 128 characters), `method` a known method, `params` an object, `timeoutMs` an integer from 100 through 10000 (through 60000 for `grid.modules.insert/move/delete/rename`, `grid.connections.set` and `ack`, whose per-entry verification reads the whole graph, and for `project.saveAs`, `export.audio` and `tracks.bounce`, which wait for a native job). Missing timeout defaults to 5000. Reject invalid input before scheduling work. The host adapter checks the monotonic deadline immediately before each mutation, including deferred callbacks. A dispatched host action cannot necessarily be cancelled.

Response:

```json
{"id":"client-generated-unique-id","result":{"outcome":"applied"}}
```

or

```json
{"id":"client-generated-unique-id","error":{"code":"stale","reason":"target_changed","message":"Another device is at this position than the one read.","next":"Re-list the devices."}}
```

The client checks response correlation. A lost connection or an unknown result must not become an automatic replay; see [Results, errors and recovery](#results-errors-and-recovery). `id` correlates requests; it is not a persistent deduplication key. A result describes actual observation/verification scope, not universal success.

MCP (`bitwig-agent-mcp`) offers the methods whose table row has `expose` true, plus a `help` tool (topics, and a method's full description and example); an `expose:false` method is neither listed nor callable from MCP or the CLI. A call returns the result object (or, on error, the error object) as both `structuredContent` and JSON text, without an outer `result` or `error` wrapper; `isError` is true for every error and for outcome `not_applied` or `unknown`. A tool's description is at most 600 characters, its remainder is read with `help`; `timeoutMs` is not in the MCP input schema and MCP rejects it (each method's default applies; `meters.get` defaults to its longest window plus 300 ms); annotations come from the method's verb. An unknown or unexposed tool name is a JSON-RPC invalid-params error. Text uses compact separators without dropping values, nulls, outcomes or error fields; whitespace is not a protocol contract. The toolkit does not route to the GUI automatically. An agent may explicitly use Computer Use for unsupported operations, but must inspect uncertain writes rather than blindly repeat them through another interface.

Version `0.2.0` uses MCP SDK 2.3+. Expected bridge and argument-validation failures remain error-flagged tool results with the envelopes above. An unexpected uncaught adapter exception instead surfaces as an MCP JSON-RPC error under SDK 2, not a fabricated tool result or acknowledgement. Such a protocol error is not permission to retry: the host operation may already have run.

The registry includes `grid.*` and read-only `modulators.*` methods across discovery, flat and one-hop layer direct parameters, Actions, transport, tracks, devices/Remote Controls, launcher, MIDI and version-gated Grid inspection/scalar and boolean-panel writes/module insertion/move/selective delete/raw custom-name CAS/single-input cable editing. Existing request shapes remain unchanged. `status` with `detail:"full"` describes implemented domains and limits, not host acceptance. `bitwig-agent --help`, `bitwig-agent <resource> --help` and `bitwig-agent help METHOD` expose the Python registry offline; the Java/MCP fixture checks transported schemas against the host registry. This is not complete Bitwig interface coverage.

Java transport boundary (Gson): `RpcServer.Handler.handle(String method, JsonObject params, long deadlineNanos)` returns `CompletableFuture<JsonObject>` containing the **result** object. Handler must enqueue work for the host and never call host model APIs from the network thread. Transport does not implement retries, host state, selection or business logic. Transport errors are envelopes; host method rejections may complete exceptionally using the shared `RpcException` type carrying `reason` (its `code` is derived), `message`, optional `next` and the unknown flag.

## Results, errors and recovery

Every request carries `"protocol":"0.5"`; a host built for another version answers `incompatible` / `protocol_mismatch`. A reply is a result or an error, never both.

**Outcomes.** A write result carries `outcome`; a read carries none. In rising severity:

| Outcome | Meaning |
|---|---|
| `already_matched` | Nothing was written: the observed state already satisfied the request. |
| `applied` | Written and observed. |
| `sent` | Dispatched once. The method has no observer, or only observed a queue; the effect is not established. |
| `not_applied` | Not written (for example an earlier entry failed); `reason` says why. |
| `unknown` | May or may not have changed. Stop and inspect; never retry. |

The top-level `outcome` is the worst entry. A field or batch entry is `{requested, observed (only when it differs), outcome, reason?}`. A top-level `reason` appears only when the outcome is not a success; `message` and `next` may accompany it. A top-level `verification` says how a result was confirmed; it is one of a closed set (the bundle's `verifications`):

| `verification` | Confirmed by |
|---|---|
| `native_readback` | Reading Bitwig's native document model back after the write (or, for a no-op, before it). |
| `api_readback` | Observing the public Controller API (bank counts, names, types, UUIDs, slot content, values) change as requested. |
| `file_readback` | Reading files on disk (written project or rendered audio headers, preset or device files). |
| `system_readback` | Read back from the operating system, e.g. PipeWire links. |

Every `applied` outcome carries a `verification`: on the entry or field that is `applied`, and repeated at the top level when all applied entries agree (always, for a single-effect call; client-composed methods such as `grid.apply` aggregate their steps the same way). `already_matched` may carry one. `sent`, `not_applied`, `unknown` and errors carry none. The one exception is the `applied` of `ack`, which observes nothing. Native results also carry `nativeVersion` and `nativeJarSha256`, the host binary that answered. Other result keys are data (values, counts, diffs, warnings).

**Errors.** `{code, reason, message, next?, current?, observed?, entries?}`. An error always means nothing changed, so the call may be corrected and repeated. `current` is the ref now found where a stale ref pointed (`target_changed`), `observed` the current values an `expect` did not match, and `entries` the refused entries of a batch, each an error with its `index`. Each reason belongs to one code and also explains a result entry:

| Code | Do |
|---|---|
| `invalid_params` | Fix the arguments. |
| `stale` | Rediscover the target, then retry. |
| `conflict` | Re-read; change the request. |
| `pending` | `busy`: wait. `unresolved`: inspect, then `ack`. |
| `unsafe_state` | Fix the state first (stop transport, activate the engine, save). |
| `unavailable` | Wait or fix the environment. |
| `refused` | Bitwig or policy refused; do not repeat unchanged. |
| `incompatible` | Match client and extension builds. |
| `unknown_method` | Check `bitwig-agent --help`. |
| `internal` | Report it. |

The closed reason list, each reason with its code, is `REASONS` in [`src/bitwig_agent/protocol/base.py`](src/bitwig_agent/protocol/base.py) (with `Outcome` and `ErrorCode`); it is exported in the protocol bundle.

**Unknown.** Once a write is dispatched, anything not proven becomes a result, not an error: `{outcome:"unknown", reason, message, next?}` (`not_observed`, `readback_mismatch`, `target_changed`, `side_effect`, `deadline`, `job_failed`). When a result carries no `next` of its own, `next` names the read method of the method that was called (`transport.set` → `transport.get`; the spec's `inspect`, one table in the registry), so the caller knows what to inspect before another write. The client's own lost response or timeout of a write is the same result with reason `transport` or `deadline`. A read, or a failure before dispatch, is an error. Nothing is retried automatically, a request ID is not an idempotency key, and a later matching read does not acknowledge the original write.

**Batches.** Everything is validated first. Entries then run in order, continue past `sent`, and stop at the first entry whose outcome is neither `applied`, `already_matched` nor `sent`; every later entry is `{outcome:"not_applied", reason:"not_reached"}`. An entry the deadline margin cut off is `not_applied` / `deadline`, the rest `not_reached`.

**`batch`.** `batch {calls:[{method, params?}]}` (1–1024 calls) runs several writes under that rule as one call; the client composes it (the extension never receives it), and the CLI's `bitwig-agent batch` (JSON Lines) and the MCP `batch` tool are the same method. Every call is validated first, as if it were made alone; a read, `ack` and `batch` itself are refused (a read has no outcome to continue or stop on and later calls cannot use what it returns; `ack` releases a hold only after you inspected what it covers). One refused call refuses the batch with nothing run: an `invalid_params` error whose `entries` has one row per call, in order, each the call's own error or `{outcome:"not_applied", reason:"not_reached"}`. Otherwise the calls run in order through the same path as single calls, and the result is `{outcome, verification?, reason?, next?, entries}` with exactly one entry per call, in order: the call's own result; a call that errs is `{outcome:"not_applied", reason, message, error}` (nothing changed) and stops the batch like any outcome outside `applied`, `already_matched`, `sent`; every later call is `not_reached`. `outcome` is the worst entry and `verification` follows the leaf rule (repeated only when every applied entry names the same one). A stop carries the stopping entry's `reason` and a `next`: the calls before it are done, an `unknown` call is inspected and never resent, and only the remaining calls are sent again. If the stopping entry has its own `next` (a composed call such as `devices.insert {params}` whose insert already applied says not to repeat it), the batch `next` quotes it instead of telling you to resend that call. A call cannot use a ref an earlier call in the same batch returns: send those in a second batch. Over MCP, as for every tool, a call's `params` may not carry `timeoutMs` (`invalid_params`, nothing runs); a CLI line keeps its own `timeoutMs`.

**Insert and configure.** `devices.insert {params}` and `modulators.insert {params, map}` create an object and configure it in one call; the client runs them as the standalone calls (the insert, then `parameters.set` per `params` entry, then `modulators.map` per `map` entry; the extension never receives `params` or `map`). `params` is keyed by parameter name, the only place a name addresses a target: the object has no refs before the call. Names resolve against the new object's rows (`parameters.list` on the new device; the `modulator` row the insert returned), exactly and among parameters that have a ref. Without `params`/`map` the result is the plain insert result. With them the result is `{outcome, verification?, ref, reason?, next?, entries}`: one entry per step (`step` is `insert`, `params.<name>` or `map[<i>]`, plus that call's own result), under the batch rule. A name that is missing (`unknown_name`, with the closest names as `candidates`) or shared (`ambiguous_name`, `candidates` are the matching refs) refuses its step and nothing after the insert is written; a step whose call errs is `not_applied` with the error's reason (and `error`). Once the insert applied, the top level keeps the new object's `ref` whatever the later steps did, and a non-success carries `next` naming the steps not done and the calls (`parameters.set`, `modulators.map`) that finish them on that ref: never repeat the insert, which would create a second object. Nothing is rolled back. An insert that is not `applied` runs nothing else (later steps `not_reached`) and keeps its own `next`; an insert error is the call's error. Values of `devices.insert` `params` are checked (normalized 0..1 or `{display}`) and `map` targets must be on the device `to`, both before anything is sent. Each step is its own Undo step, but configure steps that arrive together may merge into one (observed on 6.1.7: a device with several `params` undoes in two steps, all parameters then the insert; a modulator with two `params` and one `map` in three, the mapping, the parameters, then the insert). The first Undo reverts the last configure step, never the insert.

**Holds.** An unknown write may leave a hold that refuses further writes in its domain with `{code:"pending", reason:"unresolved", next:"Inspect X, then ack <id>."}`. `status` lists every hold as `holds:[{id, ackable, description}]`. After inspecting with a read method, `ack {id}` releases it (`{outcome:"applied", id, released}`); it records that you looked and undoes or repeats nothing. An unknown id is `stale` / `unknown_hold`. A hold with `ackable:false` is in flight (a pending request) and is released by its owner: `ack` refuses it as `busy`. A long job's hold becomes ackable once its request has returned: `ack` then gives up on the job, so the domain admits writes again while the native work may still finish (`jobs.get` keeps reporting it, with `acknowledged:true`). Holds live in the extension's memory; reloading the extension clears them without settling the pending native work.

**Long jobs.** `export.audio`, `tracks.bounce` and `project.saveAs` that outlive their wait return `{outcome:"unknown", reason:"deadline", job:"<kind>:<n>", next}`. `jobs.get {id}` reports `{job:{id, method, state:"dispatching"|"running"|"completed"|"unknown", outcome? (completed only), reason?, ...evidence}}`; a completed job is verified at that moment. Only the current job of its kind is known (else `target_not_found`).

**Frontends.** MCP sets `isError` and the CLI exits 1 for an error and for a result whose `outcome` is present and outside {`applied`, `already_matched`, `sent`}.

## Core discovery and direct parameters

Parameter objects accept exactly the listed keys; extra keys and explicit nulls are rejected. Unless a narrower bound is documented, strings must be nonempty and at most4096 UTF-16 code units. `trackId` is a UUID reported by the current track bank, not a name. Root `deviceIndex` is an integer0–15; general paging is not implemented. The separate one-layer API below does not reinterpret flat device indices. MCP/CLI `timeoutMs` is removed from method params and sent in the transport envelope.

| Method | Exact params |
|---|---|
| `status` | `{}` or `{"detail":"full"}` |
| `tracks.list` | `{}`; rows `{ref, index, type, isGroup, groupExpanded, parent, depth, parentResolved, volume:{value,display}, pan:{value,display}, mute, solo, arm, sends:[{name,display,enabled}]}` plus `tree:{complete,…}` and `window`; `ref` is the track ref every track-addressed method takes, `parent` the group's track ref or null; mix values are null while unobserved (`tracks.get` has their refs and completeness) |
| `devices.list` | `{"target": track ref or chain ref}` |
| `parameters.list` | `{"target": device ref}` |
| `parameters.set` | `{"target": parameter ref, "value": 0.5, "expect": {"value": 0.4}?}`; `value` is the bare value a read returned, `{"display":"800 Hz"}` or, for a modulator control, `{"label":"Bipolar"}` |

`status` returns `hostVersion`, `apiVersion`, `projectName`, `engineActive`, `playing`, `projectModified` (observed `Project.isModified()`: true unsaved, false saved, null unobserved), the two window capacities, and `instance:{pid,parentPid,display,waylandDisplay}` (which Bitwig process answered: its pid, its parent pid (the launcher that forked it) and `DISPLAY`/`WAYLAND_DISPLAY`, null when unset; `context.get` carries it too), `holds:[{id,ackable,description}]` (see [Results, errors and recovery](#results-errors-and-recovery)), and `parameterBindingDiagnostics`. Diagnostics report the current bank target, match/established state, source-local ID callback counters, cache generation and observed-proxy identity scope; when unbound, only established/identity scope are present. They are not a complete callback event trace. `status` also returns `extension:{version,build}`: package version and git short SHA (`-dirty` if uncommitted changes) embedded by `scripts/build.py`, or `"unknown"`. The Python client adds `extensionMismatch:{extensionVersion,clientVersion,warning}` to a `status` result when the versions differ; the call still succeeds. It also adds `supportedBitwig`, the Bitwig versions this package supports, read from `shared/host.json`. Status is a snapshot, not a project identity or host-test certificate. `detail:"full"` adds the implemented surface and each domain's binding and coverage section: `methods`, `domains` (methods by domain), `windows`, `units`, `parameterIdentityScope`, `writeSemantics`, `projectSaveAs:{method,available,reason?,binding,verification}` (the separate `project.saveAs` binding) and `render:{methods,available,reason?,binding,verification}` (the `export.audio`/`bounce.inPlace` bindings; both bind on first query and never dispatch). It replaces the removed `capabilities` method; the Grid and modulator sections follow with their slices.

`status` and `context.get` also carry `projectReady` (true/false/null) with `projectReadyReason` and `projectChangedMsAgo`. The public API has no project-loaded event, so this is a heuristic: null = project name not yet observed; false = a project-name change (extension start, project switch/recovery, Save As) within the last 3 s (`project_changed_settling`) or the track bank is unsized (`track_bank_unobserved`); true = `settled`. While false, `tracks.insert`, `devices.insert`, `devices.delete`, `devices.move`, `devices.layers.insert`, `tracks.group`, `clips.insert/import/copy/move` (and `clips.set`/`clips.delete` on arranger clips), `scenes.insert` and the Grid write methods (`project.saveAs` and `project.activateEngine` are never gated) (`grid.modules.*`, `grid.connections.set`, `grid.parameters.set`, `grid.voicing.set`, which `grid.apply` uses) fail `not_ready`; null does not block. `context.get` also reports `engineActive`. With `engineActive:false`, `clips.launch` fails `engine_inactive` (an error: nothing dispatched) and `transport.set` `playing:true` succeeds with a `warnings` entry; the client-side `audio.capture` and `grid.probe` check `status` first and fail `engine_inactive` before touching anything. Fix: `project.activateEngine`.

`tracks.list` returns `tracks:[{ref,index,type,parent,depth,…}]`, `scope:"flat_track_bank"`, and `window:{offset,capacity,total,complete}`. A track outside the current window is rejected rather than silently selecting another target. The mix columns come from the same public observers as `tracks.get`, so a mix table is `tracks list --format=tsv --fields=name,type,volume.display,pan.display,mute,solo`.

`devices.list` returns `parent`, `devices:[{ref,name,type}]`, `scope` (`top_level` for a track, `chain` for a chain) and the same window metadata. A track window has capacity 16; a chain lists all its devices (up to 256 rows). The device `ref` is what every device method takes back (refs come from reads and go back unchanged).

`parameters.list` takes a device ref (a root device or a device inside a chain) and returns `parent`, `parameters:[{ref,name,value:{value,display?}}]` and `scope:"host_exposed_direct_parameters"`. `value.value` is normalized 0..1 or null when unobserved; `value.display` is the host's own display text, present only when the host reported it while the list was built: the extension observes the display text of the listed ids through one `DirectParameterValueDisplayObserver` per device and stops observing when the request ends. No list is needed before a write: a parameter ref is located by its id in the observed id set, and its owning device is compared by position and name.

`parameters.set` takes `target` (a parameter ref owned by a device, a Remote Controls page or a modulator), `value` and an optional `expect`. A direct parameter and a Remote Control take a normalized number in [0,1] (the host call uses resolution 16384, rounding to its 16383 intervals) or, for a direct parameter, `{display}`. `{display:"800 Hz"}` is solved by bisection against the display text the host reports: the text must be a number followed by the unit the parameter shows (`Hz` and `kHz`, `s` and `ms`, `dB`, `%`, ...; the unit must equal the one the parameter displays now; a ratio `a:b` is read as larger over smaller, so Bitwig's `1:8.00` and `8:1` both mean 8 and `4:1` equals `1:4`), every probe is a real write, and the call needs a stopped transport (`unsafe_state` otherwise). A text display ("LP 24"), another unit, an enum or a display write to a Remote Control is `invalid_params` with reason `unsupported_unit`, before anything is written and the message carries the parameter's current value and display where observed; a display the parameter cannot show to that precision is `not_applied` with `displayWrite.failure:"display_not_reachable"` and the original value put back. `expect {value}` compares the current value first: another value is `stale` with reason `target_changed` and `observed:{value}`. The result is `{outcome, ref, fields:{value:{requested,observed?,outcome,reason?}}}` plus `displayWrite` for a display write (`probes`, `observedDisplay`, `normalized`, `restored`).

The outcome is `already_matched` when the value was already within one host step (nothing dispatched), `applied` when a later callback from the same device proxy matches (for a device inside a chain: the native value read back in the same document-thread pass), else `unknown` with reason `readback_mismatch` or `not_observed`; a stale pre-write cache or another device's callback is never evidence. A Remote Control whose cached value is not fresh (after a page switch or rebind; the host does not echo an unchanged value) is read from the native model first: when the mapped parameter already holds the value the result is `already_matched` with `verification:"native_readback"` and nothing is sent; when the model cannot say (no 6.1.4 binding, an unmatched page or an empty slot) the write is dispatched as before. A device, id set or Remote Controls state that changes under a request after dispatch makes the outcome `unknown` with reason `target_changed`. Observation is bounded to roughly 750 ms.

Argument names are strict: there are no aliases. An unknown field gets a hint (closest accepted name, plus a small guessed-name map such as `offset`/`limit` -> `moduleOffset`/`moduleLimit`, `tempo` -> `tempo`, `instanceId` -> `moduleId`/`targetModuleId`); fix the name and retry, nothing was dispatched.

`target_not_found` means nothing is at the addressed ref; `target_changed` means another object is there now (the error carries `current` when the host can name what is there now; a native identity mismatch carries none) or the target changed while a call was queued or running; `unsafe_state` covers a transport, recording or automation-write change during the call. `stale_context` and `stale_target` were removed in 0.5. Each of these is an error before dispatch: rediscover, then retry. A deadline or target change after dispatch is an unknown result. No automatic retry or GUI fallback is implemented.

### Chains and the devices inside them

A chain ref names one chain of a layer device (Instrument Layer, FX Layer, the Selectors, a Drum Machine pad that has a chain) by its layer UUID, so it survives reordering of the layers. The UUID names the host's chain object, not what is in it: loading another preset onto the layer device keeps the existing chains and their UUIDs, so a ref read before the load still resolves to the new content (a device ref inside it is still compared by index and name); the chain `name` is compared only when the chain itself is the target. A device inside a chain is addressed by `{kind:"device", chain, index, name}`; its `chain` may itself belong to a device inside a chain.

| Method | Exact params |
|---|---|
| `chains.list` | `{"target": device ref}` |
| `chains.set` | `{"target": chain ref, "volume"?: 0..1 or {"display"}, "pan"?: 0..1 or {"display"}, "mute"?: bool, "solo"?: bool, "active"?: true, "expect"?: {volume, pan, mute, solo, active}}`, at least one field |
| `chains.insert` | `{"to": device ref, "pad"?: 0..127}`; `pad` is required for a Drum Machine and refused elsewhere |
| `devices.list` | `{"target": chain ref}` lists the devices of a chain |
| `parameters.list`, `parameters.set`, `devices.get`, `devices.set`, `devices.select`, `devices.insert`, `devices.delete`, `devices.move` | a device ref inside a chain works like a root device ref |

`chains.list` returns `parent`, `scope:"one_chain_hop"`, a `window`, and `chains:[{ref,name,channelIndex,readiness,deviceCount,window,volume,pan,mute,solo,active?}]`, every chain of the device (up to 256). `volume` and `pan` are `{value, display}` (normalized 0..1, pan 0.5 is centre; `null` when the chain has no mixer); `active` is present only on a Selector's chains and is true on the one the Selector plays. The strips use bindings added after the first 6.1.4 and 6.1.7 name tables: a host without them still lists chains, without the strip fields and with `stripsUnavailable` saying why. Chains and the devices in them are not observed through proxies: each request walks the native document (Bitwig 6.1.4 only; `host_mismatch` or `native_unavailable` otherwise) from its verified root device, finds the chain by its UUID and the device by its index, and compares the ref's fields there, so a device stays addressable after inserts, deletes and moves around it and no window limits a chain. A device without layers, chains or drum pads (including the single-chain Chain container), FX slots are `unsupported_scope`, and a pad without a chain is not listed (an empty pad chain made by `chains.insert` is, with `deviceCount` 0). A chain ref is session-scoped: it follows its layer's UUID, and Bitwig assigns new layer UUIDs after a restart, so a chain ref from another session is `stale` with reason `target_not_found` (`next: chains.list`); re-read rather than keep chain refs across sessions.

`chains.set` writes a chain's mixer strip and a Selector's choice, mirroring `tracks.set`: only the given fields, `expect` compares bare current values first (`target_changed` with the differing values, nothing written), and the result has `ref`, the worst field `outcome`, and `fields:{name:{requested, observed?, outcome, reason?, verification?}}`. Every field is read, compared, written and read back in one native document-thread pass (`native_readback`); a field already at its value is `already_matched` and not written; a field that reads back differently is `unknown` with `readback_mismatch` (never retried). A chain without a mixer, or `active` on a chain whose device is not a Selector, is `unsupported_scope`; a parameter Bitwig will not let be written now is `invalid_target`; both before anything is written, including the first `{display}` probe. `solo` changes this chain only (other chains keep their solo state, unlike the exclusive-solo preference); a solo write that changes another chain's solo reads back as `unknown` `readback_mismatch`. `active: true` sets the Selector's active-chain index to this chain's position. `volume`/`pan` `{display}` (`"-6 dB"`, `"-25 %"`) needs a stopped transport and is found first by bisection on the host's own display text, each probe a native write (several fader moves, which Bitwig 6.1.7 records as one Undo step), reported in `displayWrite`; an unreachable display puts the fields solved before it back and reports `not_applied` (`unknown` when the restore is not confirmed). The calls are those Bitwig's own controller proxies make on the same objects (`AbstractChannelProxy`, `SoloProxy`, `ChainSelectorProxy`). Undo (native, Bitwig 6.1.7): volume, pan and mute written together are one step, a `{display}` volume with all its probes is one step, `active` is one step; solo is not an Undo step at all, as in Bitwig's own layer S button, so reverse it with `solo: false`, never with Undo (an Undo would revert an earlier edit instead).

`chains.insert` adds one empty chain with Bitwig's own operation, each its own Undo step: "Add Nested Device Chain" appends a chain (named by Bitwig, e.g. "Layer 3") to an Instrument or FX Layer or an Instrument or FX Selector; "Create empty chain" gives the Drum Machine pad with MIDI pitch `pad` (36 is C1) a chain, and a pad that already has one is `already_matched` with that chain's ref. Any other device is `unsupported_scope`. It is verified by the device's chain objects before and after (exactly one new chain, the others unchanged and in order): `applied` with `ref` (the new chain ref, ready for `devices.insert {to: ref}` and `chains.set`), `parent`, `pad` (Drum Machine), `beforeCount`, `afterCount` and `native_readback`; otherwise `unknown` with `not_observed` (no change in time) or `readback_mismatch` (the chains changed another way) and `ref: null`: read `chains.list` before another edit. Native on Bitwig 6.1.7: Instrument and FX Layer, both Selectors (whose active chain stays put) and a Drum Machine pad each took one Undo step; an `already_matched` pad took none.

Inside a chain, `parameters.list` reads every direct parameter with its host display text in one pass; `parameters.set` writes and reads the value back in the same pass (one Undo step per write), and a `{display}` write probes natively the same way. `devices.set` toggles the device's On/Off parameter; `devices.select` changes the track's device selection. Remote Controls, modulators, Grid and sidechains of a device inside a chain are `unsupported_scope`.

Chain and parameter observations do not establish native write isolation, DSP, whole-hierarchy coverage or general persistence. See [coverage limits](VERIFICATION.md#coverage-limits-and-unresolved-results).


## Host Actions

`actions.list` accepts optional `query` (case-insensitive substring of id or name), `category` (exact category id or name, case-insensitive) and `limit` (1..1000, default 100) and returns `{scope:"host_action_catalog",total,complete,actions:[{actionId,name,category:{id,name}|null}]}` (`total` counts all matches, `complete` is false when `limit` truncated them) from `Application.getActions()` and the Action metadata. These are the host's current IDs and localized names, not guessed command names. Catalog membership does not establish enablement or completion in the current UI context.

`actions.invoke` accepts `{"actionId":"..."}` plus optional `discardUnsavedChanges` (bool) (the same nonempty, maximum 4096-character string rule) and resolves it using `Application.getAction(id)`. An absent ID is rejected with `unknown_name`. The lookup and invocation run on the host thread; the deadline is checked again immediately before invocation. `Quit` closes every open project tab while only the current tab's saved state is observable, so it is refused with `unsaved_changes` unless `discardUnsavedChanges:true` (user consent only). `Close` is refused unless the current tab is observed saved or consent is given. `New`/`Open` open another tab (observed on 6.1.4) and are not guarded; there is no other policy. A returned call reports only `{outcome:"sent",actionId}`. Actions may depend on selection/focus, open dialogs or change a project. A dispatched save/export Action is not proof of a written file. Observe the resulting state explicitly; no retries, polling, selection routing or GUI fallback are added. MCP exposes `timeoutMs` separately, as for the existing methods.

Transport uses raw BPM and quarter-note beats. Tempo 20–666 is a toolkit-supported range evidenced by a shipped controller, not a claim about every native raw limit. Position/loop start are nonnegative; duration is positive; their sum must remain finite. Recording/arranger automation/launcher automation write flags are read-only. While enabled, non-stop transport mutations are rejected; explicit stop remains available. Multi-field mutations are not transactions: each field is guarded and separately verified, and earlier changes can remain when a later field fails.

When an explicit `playing:false` accompanies other transport fields, the bridge waits for the stopped-state observation before dispatching those remaining fields, within the same bounded observation window. Sending stop and seek consecutively is not sufficient: an asynchronous stop can overwrite the requested position. Deferred writes still recheck cancellation, deadlines and recording/automation guards. A missing stop observation leaves the stop field `unknown` and the remaining fields `not_applied`/`not_reached`; the caller stops rather than retrying.

Both transport reads and write-result snapshots include `projectName` from the existing interested Application source. This lets callers check the expected project label and safety flags in one response instead of pairing `status` with `transport.get`. A null, missing or changed name is not permission to mutate. This is an observed name, not full-file-path identity, an atomic snapshot across fields or a project lock.

Track volume, pan and remote control values are normalized [0,1]; accompanying host display strings are not interchangeable numeric units. Track creation rejects an incomplete initial UUID/index/type window, or a full one (the track window is full, where the new track could not be observed), before invoking a factory. In a grouped project the factory index counts top-level tracks only; creation needs an observed complete track tree, else `unsupported_scope` before any factory (see [Track tree and grouping](#track-tree-and-grouping)). After one supported factory call, attribution requires a complete after-window, one new UUID, matching type, top-level ordinal and repeated observations before assigning a name. A group appearing after dispatch or concurrent unrelated creation can still leave an unnamed created track with an unknown result. An unresolved dispatched creation holds further factories (refused `unresolved`); inspect the actual project rather than retrying, then `ack` the hold.

Mix observations belong to continuously interested bank proxies. An established UUID/existence change invalidates operation generations and masks reads/writes until an actual controller `flush` refreshes previously observed getters with matching identity/existence. This is not an atomic physical-track snapshot. Readable getter baselines do not make prior-generation equality a verified no-op: a post-rebind same-value write can remain `unknown` if the host emits no fresh callback. Agents should submit only fields that differ from a fresh readable `tracks.get` snapshot; inspect the top-level `outcome` and each field's, and never automatically retry an unknown composite result. Legacy selection can remain unreadable until a current-generation selection callback. Old operations never regain validity after same-UUID reappearance.

`tracks.select` is an explicit UI-navigation command, not a verified mix-field setter. Like `devices.select`, it returns `outcome:"sent"`. It dispatches once even when a cached selection value is already true; that value cannot prove the requested editor navigation. Its snapshot can still contain `selected:null` after a project/proxy rebind, and it has no setter-style `fields` acknowledgement. Inspect the actual track/device context and any selection-triggered arming before dependent edits. UUID/rebind, cancellation and deadline guards remain active; a failure after dispatch is an unknown result and must stop the caller. A dispatch-only receipt is not permission to repeat the command blindly. While a launcher cursor operation (`notes.*`, `clips.insert/import`) is running, `tracks.select`, `devices.select` and `actions.invoke` fail fast with `busy`; nothing is queued.

Explicit normalized volume, pan and Remote Control mutations use the native `setImmediately` API: absolute RPC values must not wait for physical-controller pickup. Global takeover preferences are untouched. Remote value writes additionally reject active or unobserved recording/automation-write modes immediately before dispatch.

Device insertion requires the expected count and complete top-level window. Confirmation observes a fresh appended device, a count delta and unchanged prefix; `requestedIdentifierVerified:false` explicitly distinguishes that observation from proof of the requested plug-in/preset identity. File insertion passes the path to the native host API, not a shell. `devices.catalog` checks local factory Grid file presence; insertion and rendered musical identity need separate native evidence. Community website UUIDs are not advertised as native device IDs.

### Device chain edits and preset search

`devices.insert` observes the chain's bank: the count must rise by one, every device before the insertion point must be unchanged (name, type) and every device after it must appear shifted by one slot, with the new slot reporting fresh metadata. Optional `params` {name: value} sets initial values on the new device in the same call (see [Insert and configure](#results-errors-and-recovery)). The result adds `parent`, `ref` (the new device's ref, absent when not identified) and `inserted` (that slot's name/type, null if not identified); `verification` is `api_readback` in a track's chain and `native_readback` in a chain inside a device. `position` anchors are device refs of the same parent; an anchor in another parent is `invalid_params`. In a track's chain `start`, `end`, `before`, `after` use the public `startOfDeviceChainInsertionPoint`, `endOfDeviceChainInsertionPoint`, `Device.beforeDeviceInsertionPoint` and `Device.afterDeviceInsertionPoint`. In a chain inside a device the insert, delete and move are the native model operations behind those insertion points and `deleteObject` (the id or path is resolved to a file first; one the host does not know is `invalid_target`, before anything is sent), and each edit is proven by the chain's device objects before and after it: the inserted object is new, the deleted one is gone, the moved one is the same object at its new index, everything else in the same order. Devices with the same name and type are therefore told apart.

`devices.delete` and `devices.move` address one device by ref, require no recording/automation write and, in a track's chain, the complete 16-device window; they compare the chain before and after (observed names/types in a track's chain, device objects in a chain inside a device). Delete reports `deleted`, `beforeCount`, `afterCount`, `before`, `after` and `verification` (`api_readback`, or `native_readback` inside a device). Move reports `moved:{deviceIndex,name,type,toIndex}`, the moved device's new `ref` and `verification` (`api_readback`, or `native_readback`); a device already at the requested position is `already_matched`. In a track's chain a move among devices with identical names and types cannot be told from no move: it dispatches once and the result is `unknown` with a `hint`. For all three, an `unknown` result (`not_observed` or `readback_mismatch`) means read `devices.list` before another edit; nothing is retried. Each edit is one native Undo step. A root chain is limited to 16 devices (a longer chain is `outside_window`); a chain inside a device has no window limit. Moving between chains or tracks is unsupported.

`presets.search` never calls the host. It walks the user library (`~/Bitwig Studio/Library`) and installed packages (`~/.BitwigStudio/installed-packages`, plus the macOS/Windows locations; `BITWIG_PRESET_ROOTS` replaces the roots) for `.bwpreset` files. User-library presets with a plain header yield `device`, `deviceType`, `category`, `deviceCategory`, `creator` and `comment`; package presets are encrypted, so only `path`, `creator`, `package` and `folders` are known (`metadataReadable:false`), and `device`/`category` then match folder and package names. Query words must all occur (case, spaces and punctuation ignored) in the name, folders, package, creator or readable metadata; results rank name hits first and carry `insert:{kind:"file",path}` for `devices.insert`. `deviceType` matches only readable metadata. A hit is a file on disk: that the host loads it, and what it sounds like, is separate evidence.

Remote tokens bind observed track/device/page/control metadata, not persistent physical devices or invisible same-name remappings. Observed lifecycle changes mask affected controls until actual host flush reconciles current previously observed getters; subscription history is retained because unchanged callbacks may not replay. Absent/remapping controls and never-observed/nonfinite getters remain unavailable. Flush refreshes page comparison baselines but never advances write acknowledgement sequences or freshness. Thus a recovered same-value request can dispatch and remain unacknowledged rather than claim a verified no-op. Old tokens and pending operations do not regain validity. Neither remote nor direct parameter controls expose Grid module creation/cables.

`clips.launch` and `launcher.stop` are `applied` when the requested playing/stopped state is observed. A confirmed queue is `sent` (`playbackState:"queued"`): accept this only as an explicitly expected dispatch-only result, then independently inspect `launcher.list` for actual playback/stop before dependent edits. If neither the desired state nor a queue is observed within the bounded observation window, the result is `unknown`/`not_observed`: stop the writer, do not retry. These are launcher-state observations, not musical/audio completion or cancellation guarantees.

`clips.import` shares the launcher mutation/cursor lease, checks the explicit slot is empty immediately before `replaceInsertionPoint().insertFile`, and requires a fresh observed content transition. The result reports `verification:"api_readback"` and `requestedFileVerified:false`: it does not prove file identity, decoding or audible output. Unsupported native content may silently do nothing; an unobserved dispatched import is `unknown`/`not_observed`, never a retry. The SDK has no atomic conditional insertion; an external edit after the final occupancy check remains a race.

An unresolved dispatched launcher creation/import leaves a hold (`launcher.mutation:<n>`, keyed by track and absolute scene) beyond the RPC future's lifetime. Conflicting creation, import and note writes are refused `unresolved`; inspection remains available. Positively observed completion releases the target, as does `ack` after you inspect the slot. Late callbacks, an empty observation or elapsed time do not clear an ambiguous result. Recreating the extension also clears this in-memory guard but does not cancel or establish completion of pending native work: inspect and settle host state first.

### Mixer levels, sends, meters, markers

Guide references are to the Bitwig Studio user guide (5.3 text, the latest published): sends §7.1.6, faders and meters §7.1.8, time signature §2.3.3, cue markers §5.5.1.

**Display-addressed levels.** The controller API has no dB or percent setter and publishes no fader curve, so `{display}` on `tracks.set` `volume`/`pan` and on `tracks.sends.set` `value` bisects the normalized value against the host's own displayed text (`Parameter.displayedValue`): write, wait for the value callback, let the display callback settle two polls, read the text, narrow. The text is only parsed, never converted by a formula: dB needs a `dB` unit, `-inf`/`∞` means the bottom of the scale; pan needs `%`, a side letter or `C`/`Center` (Bitwig itself shows `0.00 %` for centre and `-25.0 %` for left; `25% L` and `C` also parse). A display that cannot be parsed is `invalid_params`/`unsupported_unit` before any write. Success needs the displayed number within half of the last displayed digit of the target; the result carries `displayWrite` keyed by field (`volume`, `pan`, `value`) with `{requested, target, observedDisplay, normalized, originalNormalized, probes, matched, method, failure?, restored?}`, at most 28 writes per field, so several fader moves are written while it searches. An unreachable or unreadable display restores the original value and applies no other field of the call: `not_applied` when the restore is observed (`displayWrite.<field>.failure`: `display_not_reachable`, `display_unparseable`, `probe_not_observed`, or reason `deadline`), else `unknown`. A bare value is the 0–1 number a read returned; pan 0 is hard left, 0.5 is centre.

**`tracks.sends.set`.** The send is addressed by its send ref (`{kind:"send", track, index, name}` from a `tracks.get` send row; `index` is offset-adjusted and the send's name is compared, so a reordered send is `stale`/`target_changed` with `current`; a renamed track does not invalidate it). `value` is written with `setImmediately`, `enabled` last, each verified against an observer callback after the write (`applied`, `already_matched` when nothing needed writing). A level write turns a disabled send on (guide §7.1.6: new projects start with all sends disabled); the result reports `autoEnabled`. With a level, `enabled:false` is always dispatched (the level may switch the send on after the metadata was read); `enabled:true` the send already shows is `already_matched`, since a level never switches a send off. Send pre/post mode is not exposed. `tracks.get` send rows additionally carry `effectTrack` (the track ref of the effect track with the same ordinal as the send, null when not in the window).

**`meters.get`.** Registers `Channel.addVuMeterObserver(128, channel, peak|rms)` for left and right of every bank track at startup (a failed registration makes the method answer `unsupported_scope`). Values are the host's 0–127 steps; the public API gives no dB mapping, so none is claimed. A steady meter fires no callback, so the standing level at window start counts. Per track ref: `peakMax`, `rmsMax`, `rmsMean` (20 ms polls), `callbacks`, `silent`, `targetUnchanged`; plus `playingAtStart`/`playingAtEnd`. Meters move only while audio renders; the default `timeoutMs` (5300) covers the longest window; a smaller explicit `timeoutMs` than `windowMs` + 300 is refused (`invalid_params`). For loudness use `audio.analyze mode=loudness`.

**Cue markers.** `markers.list` reads `Arranger.createCueMarkerBank(64)`: `{markers:[{ref,name,beat}],window,observationsComplete}` sorted by beat; a marker ref is `{kind:"marker",index,name,beat}`, its rank plus name and beat, not an id. Writes need the whole list inside the window and recording/automation off; `markers.insert` also needs an observed stopped transport and refuses a beat that already holds a marker (`target_exists`). The native call only adds at the playhead and adds nothing where a marker already sits, so insert moves the playhead to `beat` (free, checked above), waits until the playhead is observed there, calls `Transport.addCueMarkerAtPlaybackPosition()` once, identifies the one new marker as the single multiset difference of the list, then names it (and moves it to `beat`, should the host have placed it elsewhere) and puts the playhead back where it was in the same controller callback; `applied` also needs the playhead observed back there. A playhead never observed at `beat` adds nothing and is `unknown`/`not_observed` like an unobserved insert. `markers.set`/`markers.delete` take that ref and compare all of it: no marker at the rank is `stale`/`target_not_found`, another name or beat there is `stale`/`target_changed` with the ref now at that rank as `current`. Every write is verified by comparing the full observed list with the expected one (`applied`); an unobserved result is `unknown`/`not_observed`, leaves a hold (`status.holds`) and blocks further marker writes (`unresolved`) until `ack`. Time-signature change markers (guide §5.5.2) have no public API.

**Guide settings.** `metronomeVolume` is `Transport.metronomeVolume()` (normalized 0..1, not dB; read as `{value,display}` with the host's `displayedValue()`), `punchInEnabled`/`punchOutEnabled` are `isPunchInEnabled()`/`isPunchOutEnabled()`, `preRoll` is `Transport.preRoll()`, `defaultLaunchQuantization` is `Transport.defaultLaunchQuantization()` and `recordQuantizationGrid` is `Application.recordQuantizationGrid()`. The three enums accept only an id the host itself lists through `EnumValue.enumDefinition()` (returned inside each unit as `options`; nothing is hand-written here, so the lists follow the installed Bitwig); an unlisted value is `invalid_params` before any field is written, except the value the host currently reports. A stored project id the transport observer reports outside the list is read as the listed id `EnumValue.get()` gives for it (Bitwig 6.1.4 reports `bar` for `1`); a value with no listed id is flagged in `observedOutsideOptions` and writing it back is `already_matched`. The same holds for the track and clip enums. All use the same per-field observer readback and recording/automation guard as the other transport fields. The public API exposes no per-clip or per-scene quantization beyond what is documented under `clips.set`.

**Time signature.** `transport.set timeSignature:"7/8"` calls `TimeSignatureValue.set(String)` (numerator 1–32, denominator 1/2/4/8/16/32 as validated by the toolkit; the host decides what it accepts, readback is the proof) and is verified like the other transport fields; `transport.get` returns the string the host reports.

### Project Key Signature (version-gated)

Bitwig 6.0 added a project key signature, the transport's Root Key and Scale parameters; note FX such as Arpeggiator and Note Transpose follow it with Use Global Key ([What's New in 6.0](https://downloads.bitwig.com/6.0/Release-Notes-6.0.html)), as does Sampler's Spectral mode from 6.1 ([What's New in 6.1](https://downloads.bitwig.com/6.1/Release-Notes-6.1.pdf)). The public controller API has no key signature, so `project.key.get` and `project.key.set` use exact native bindings behind the version/JAR-hash gate (`native_unavailable` otherwise, also for a key the running version's name table lacks; there is no public fallback). On the native document thread the controller Project proxy's target is the project; its transport (`project.state.transport`) holds the tonal space and its key signature, whose Root Key and Scale are host enum parameters.

- **Values come from Bitwig.** Each parameter's options are its own enum definition, read on every call and returned as `options`; nothing is hand-written here. Root Key values are 0–11 (C … B); a Scale value is a 12-bit pitch-class mask (Bitwig 6.1.4 natively: Major 2741, Minor 1453), not an ordinal. A mask outside the list (a custom scale) reads with `label:null`; `scaleName` is Bitwig's own name of the current scale definition (`"minor"`, or `"custom [...]"`).
- **Write.** `root`/`scale` name an option by label (case-insensitive) or value; anything else is `invalid_params` before anything is written. Recording or either automation-write mode blocks it (`unsafe_state`); playback may run. Fields that already match are not written. The changed fields are set with the controller setter (`parameter.controller.setRaw`, Root Key first) inside one `project.begin("Set Key Signature")`/`project.end` transaction, so they are one Undo step (`nativeUndo:true`, `undoLabel`), then the key signature is read again in the same document task.
- **Result.** The read's fields plus `fields:{root?,scale?}` with `requested`, `observed` (in the form requested: a label request reads back the label) when it differs, and `applied`/`already_matched` with `verification:"native_readback"`. A field that does not read back is `unknown`/`readback_mismatch`; the result is then `unknown`, leaves a hold and refuses further key writes (`unresolved`) until `ack project.key` after `project.key.get`. Native readback is the model value, not proof that a device follows the key, nor save/reopen.

### MIDI window and edits

Every `notes.get/edit` request supplies `target`, a launcher clip ref (a scene past the count or an empty slot is `stale`/`target_not_found`; another clip or scene name there is `target_changed` with `current`), and optional `channel` (0–15, default 0). The five grid fields are supplied together or all omitted. Explicit: `stepSize` (1/128–4), `startStep` (0–1048576), `steps` (1–128), `pitchStart` (0–127), `pitchCount` (1–128; range must end at or below 128). Omitted on `notes.set` (and for `clips.insert` notes): the window is derived from the onsets alone, echoed with `derived:true`: the finest grid among 4, 2, 1 … 1/128 beat that aligns every onset and holds every note in one 128-step window (so existing finer onsets stay visible to collision checks), `startStep` at the earliest onset and the pitch range of the edits. When none does, the coarsest grid aligning every onset is cut into 128-step windows, each holding whole notes (a note longer than 128 steps of that grid is refused with the fix: shorten it, or write it in a call of its own); see [windowed writes](#windowed-writes). Omitted on `notes.get`: the loop is read over pitches 0–127 at 0.125 beat (1/32 note) when the loop is at most 16 beats, else 0.25 beat (1/16 note), at most 128 steps; if the loop is longer, `windowCoversLoop:false` and `continuation` names the next explicit window (never coarser than 1/16). MIDI numbers avoid octave-label conventions: 60 means the same pitch even when the UI calls it C3 rather than C4.

Each edit is either `{"op":"set","beat":0,"pitch":60,"velocity":90,"duration":1}` or `{"op":"clear","beat":0,"pitch":60}` (a clear removes the onsets inside the cell). Velocity is an integer 1–127, duration 1/128–4096 beats. Beat and duration must align exactly to the requested step grid. Set duration must fit the requested window and observed loop end. Duplicate cells, overlapping same-pitch sets, existing onset collisions and edits starting inside a sustain are rejected before note writes. Clearing an obstructing note requires an explicit earlier call; there is no whole-clip replacement.

`clips.insert` into a slot initializes the new clip's playback stop to `loop.length` as well as creating its loop extent. Creation is `applied` only when the requested name, loop length and playback stop read back. This avoids the native four-beat default stop on longer clips. It does not configure Next Action or automatic scene sequencing; those controls and scene naming still require the native interface.

For `.mid` / `.midi` imports, the extension validates Standard MIDI File parsing and requires a positive-velocity note-on or another channel event before dispatch. Controller/program/pitch-only MIDI remains eligible for host import. Malformed, metadata-only or note-off-only files return the error `invalid_file`, without placing a hold. Use `clips.insert` for intentional silence. This preflight does not verify decoded host notes, multitrack placement or tempo metadata behavior. Other file formats retain host-side interpretation. An import already dispatched without an observed content transition leaves a hold, released only by an observed completion or by `ack` after you inspect the slot; there is no automatic reset for possible late writes.

`clips.insert` into a slot, `notes.get` and `notes.set` explicitly select the launcher clip in the UI. They bind the cursor using slot-proxy equality and track UUID, with a local cursor-operation lease; no name fallback. This can affect host auto-arm/editor selection according to existing preferences. These calls do not silently change preferences.

Selection itself counts as dispatch, including for `notes.get`: a later context change, deadline or host failure reports `outcome:"unknown"` even when no note was written. A refusal after selection is therefore an unknown result, never an error: an already-dispatched selection may have had UI or auto-arm side effects. A failed read is therefore not automatically safe to retry.

Readback reports actual `NoteStep` state, duration and grid-cell onset. Note rows are `{beat,pitch,velocity,duration}` with integer MIDI `velocity` 1–127, the unit `notes.set` accepts (the host's 0–1 value is rounded); channel is the window's and step is `beat/stepSize`. The public API does not establish exact sub-step onsets or multiple onsets within a cell; the read covers one channel and window, never the whole clip. `gridReadiness:"scheduled_settling_not_acknowledged"` means grid data follows observed cursor identity plus a fixed settle delay covering the known Bitwig 6.1.3 refresh debounce; the public API has no grid offset/step acknowledgement, so this is not a host-data barrier and delayed same-cell callbacks carry no source-window identity. Dense reads return at most 2048 onset rows, with `notesInWindow`, `notesReturned`, `completeWindow` and subdivision guidance.

`notes.set` (and `noteWrite`) is compact by default: the top-level `outcome` is the worst over every edit, `summary:{requested,dispatched,alreadyMatched,verified,unverified}` counts them, `undo` says how the write entered Bitwig's Undo history ([one Undo step](#one-undo-step)), `notesInWindow` counts onsets, and `unverifiedEdits` lists only edits that were not read back (`{index,op,beat,pitch,outcome,reason,observed}`, `index` into the request's `edits`/`notes`; `observed` is the cell's onset row, or `{beat,pitch,state}` for an empty or sustained cell). `detail:"full"` instead returns the `notes.get`-style window listing plus an `edits` entry per edit (all edits, including verified). Failure semantics and write checks are identical in both modes. This is not a lossless arbitrary-MIDI exporter. A successfully dispatched cursor operation is not proof of audio-clip suitability, saved persistence or audible output.

Grid reconfiguration has a separate unresolved readiness limit: the installed API exposes setters but no acknowledged current step-size/scroll-offset revision. Configuration follows observed cursor identity, then waits 150 ms to cover the observed 6.1.3 100 ms grid-refresh debounce plus a delivery margin. Results expose `gridSettleMs`, `gridReadiness:"scheduled_settling_not_acknowledged"` and `gridGeneration`, not a data barrier. Generation scoping rejects known old/unsettled observations, but a late same-cell callback has no source-window ID. A cold first-read regression previously returned beat 1 for a note the native Inspector placed at beat 2. The correction does not retroactively pass the original preservation criterion or guarantee arbitrary delayed callback delivery. Alternating-window/step-size and independent native E2E remain separate evidence; consumers must not treat grid readback as atomic or lossless. See [coverage limits](VERIFICATION.md#coverage-limits-and-unresolved-results).

#### Note rules

Shared by `notes.set` and `clips.insert` (launcher and arranger). Onsets lie on the 1/128-beat grid (with an explicit window: on its `stepSize`). Durations are written as requested; they need not align to any grid. Bitwig stores a duration to 1/1048576 beat (native readback of 0.225 is 0.22500038146972656 = round(0.225 x 2^20) / 2^20), so a set is verified when its readback is within half that step of the request, and the rules below judge each note's end as stored. No two entries share a beat and pitch, no set starts before an earlier same-pitch set ends, every note fits the clip length (or the explicit window), and a clear is a single cell. Every broken rule is reported in one `invalid_params` error, in request order, each as `notes[i]`/`edits[i]` with a fix (`... shorten notes[4] to duration <= 0.5`); nothing is selected or written.

#### One Undo step

On the inspected Bitwig 6.1.4 JAR every note of a `notes.set` call (and of a launcher `clips.insert`) is written as one Undo step, `undo:"one_step"`. Bitwig's public setters post one document event per note, each its own outermost transaction and so its own Undo step; instead one native document task resolves the slot's clip (track UUID, clip name and slot identity checked natively), observes every cell, applies the preflight rules below to all of them, and writes the cells that differ inside one transaction labelled "Edit Notes" (inner per-note transactions merge into it). Times and durations use the setter's 2^-20-beat rounding; the write passes no editor selection, so unlike the public setter it neither clears nor selects notes. A refusal in any cell is an error and nothing is written or selected; a failure after the transaction opened is `unknown`. When every cell already matches, no transaction opens (`undo:"none"`). The clip is then selected and each window read back per cell, as below. Without the exact binding (another host version or JAR) the module falls back to the public setters: `undo:"per_note"`, one Undo step per note.

#### Windowed writes

A derived window that needs more than 128 steps runs as several windows inside the one call, in time order. With the native binding all of them are written in the one Undo step first; the windows then only read back: every window is read, one that does not read back is `unknown` (counted as dispatched), and one left unread for lack of time is `unknown`/`not_observed`; nothing is `not_reached`. Through the public setters each window is an ordinary note edit (bind, preflight, write, per-cell readback); only the first window's selection counts as a write. The windows stop at the first one that is not `applied`/`already_matched`; when too little time is left for another (less than twice the slowest so far) the next is `not_applied`/`deadline`. A window refused before its own first write is `not_applied` with its reason; one that failed after it is `unknown`. The result is `{ref, loop…, outcome (the worst window), reason?, summary:{requested, dispatched, alreadyMatched, verified, unverified, notReached}, windows:[{window, outcome, reason?, summary?, unverifiedEdits?, …}], notReached?:[indices]}`; windows not attempted are `not_applied`/`not_reached` and their request indices are in `notReached`, so they can be sent again. Through the public setters each note is its own Bitwig Undo step, windowed or not (native: a 160-note, two-window write took 160 Undo steps). A failure before the first window dispatched is an error.

### Track tree and grouping

The guide describes group tracks as uniting "several component tracks … into one higher-level track for streamlined mixing" and grouping as "select the tracks you wish to group and then press [CTRL]+[G]" ([intro to tracks §3.2.1–3.2.2](https://www.bitwig.com/userguide/latest/intro_to_tracks)).

**Tree in `tracks.list`.** The flat bank lists tracks in tree pre-order. Each row adds `type`, `isGroup`, `groupExpanded` (groups only, else null), `parent` (the parent group's track ref; null at top level), `depth` (0 at top level) and `parentResolved`. The parent comes from one public `Track.createParentTrack(0, 0)` proxy per bank slot. The first non-master track is top-level, so its observed parent identifies the root group. A track is top-level when its parent is that root, and a child when its parent is a Group in the window. `tree:{complete, groupsPresent, reason?, scope}` is true only when the window is complete and every parent is the root or a Group earlier in the window that every track in between descends from. Otherwise `parent`/`depth` are null, never guessed. Reasons: `track_window_incomplete`, `parent_observation_missing`, `parent_not_a_group_in_window`, `group_parent_ambiguous`, `parent_order_inconsistent`, `parent_cycle`.

Observed on 6.1.4: right after `tracks.group`, the new group's own parent proxy reported neither the root nor a group in the window, while its children reported the group. A group whose parent proxy names itself or an id outside the window is therefore placed by pre-order alone, and only where that is unambiguous: it is first in the window, or it follows a top-level track that is not a group. Its row then has `parentSource:"preorder_inference"`. Otherwise the tree is incomplete with `group_parent_ambiguous` (for example a group directly after another group's child, which could be that child's sibling or top-level). When a parent proxy did not decide the row, the row also carries the raw value as `parentObserved`. When the first track is a group, the root is never taken from that group's own value: it comes from the first non-group track (effect tracks count) whose parent is outside the window; without one, groups are placed only by the pre-order rule above. A project without groups needs no parent observation: every track is top-level.

**`tracks.insert` with groups.** `Application.createAudioTrack/createInstrumentTrack/createEffectTrack(position)` insert into the root group's main or effect list (`kWY.cfM(track, min(position, count), …)` and `kWY.cfM(index, …)` in the inspected binary). A `position` anchor `{before|after: trackRef}` is turned into the anchor's top-level ordinal in its list; in a grouped project that ordinal counts only top-level tracks: a group counts once, its children do not. Insertion is refused (`unsupported_scope`, no factory) only while `tree.complete` is false. Otherwise attribution additionally requires the new track to be observed top-level at the expected top-level ordinal of its list. A new track observed inside a group, at another index, or a group appearing during a flat-project insertion is never named and stays `unknown`. `insertion.parentScope` is `top_level_of_grouped_project` or `flat_project`. A hold `tracks.insert` blocks further inserts and groupings until `ack`.

**`tracks.group`** `{targets:[1–1024 distinct track refs], name?}` creates one group containing exactly those tracks without using the UI selection. The tracks must be adjacent siblings of one parent, in order (top level or the same group); otherwise `invalid_params`/`unsupported_scope` before anything is dispatched. After Redo of a named group it comes back collapsed and its children are not listed until it is expanded (a bank limitation). Effect and master tracks are refused (`unsupported_scope`). Needs observed recording and both automation-write modes off, a complete window with at least one free track slot (room for the group) and `tree.complete`; another insertion or grouping in flight is `busy`, a running launcher cursor operation `busy` (it holds the selection lease the grouping takes).

- **Native operation.** Gated like the other private bindings: exact Bitwig 6.1.4 and the hashed JAR, else `native_unavailable`. On the native document thread it resolves each bank proxy (`ControlSurfaceProxy.getDeepestTarget`) to a native track (`zwV`), corroborates its UUID (`RYd.kFU()`, or a group's channel alias `kWY.TD2().kFU()`, matching the public channelId), takes the common parent `RYd.QNk()` (must be one `SC` group), and checks owning-project/context lifecycle. It then calls `SC.MRY(List)`, the model operation behind the track-group command `group_tracks(tracks)`.
- **What the native operation does.** In one undoable transaction it creates a group at the first listed track's index, copies that track's color, expands it, moves the tracks into it in list order, and selects the new group. Tracks are passed in flat order, so their order is kept. When tracks hold plug-ins, Bitwig may first save plug-in states asynchronously, so observation waits up to 3 s within the deadline. With `name` the extension opens one outer transaction `g2L.cfM("Group Tracks", false)` around `SC.MRY(List)` and the group's own setter `iYN.d_(String)` (the call the public `setName` ends in): the transaction manager reports only the outermost begin and end to the undo recorder, so grouping and naming are one Undo step. Found by inspecting the 6.1.4 JAR offline; the native check is in the pull request.
- **Verification** is public: exactly one new UUID in the window, of type Group, whose parent is the original parent; every requested track's `parent` is the new group; every other track's parent is unchanged. The requested tracks keep their relative order. All of this must be seen in two consecutive observations. The result is `{ref (the group), verification:"api_readback", group:{children (track refs), parent, nativeOperation, nativeUndo:true, undoGrouping, selectionSideEffect}}`. With `name`, `fields.name` reads the group's observed name back (`applied`, else `unknown`/`not_observed`).
- **Unknown outcomes.** A dispatched grouping that is not attributed is an `unknown` result with a `reason` (`not_observed`, `target_changed` or `side_effect`). It holds both `tracks.insert` and `tracks.group` (refused `unresolved`): inspect `tracks.list`, then `ack` the hold; never retry.
- **Not covered:** ungrouping, moving tracks into an existing group, grouping effect tracks, and group-owned effect tracks as targets (they are listed with their parent).

### Arranger clips (version-gated)

The guide places clips on the timeline by dragging from the Browser "to the desired timeline position" ([arranger clips §5.1.1](https://www.bitwig.com/userguide/latest/arranger_clips_and_the_browser_panel)). It copies launcher clips to the arranger by dragging them onto a track's timeline ([acquiring launcher clips §6.2.2](https://www.bitwig.com/userguide/latest/acquiring_and_working_with_launcher_clips)). It moves and resizes clips by dragging their body and edges (§5.1.2–5.1.4).

The public controller API has no arranger-clip enumeration or creation. `ControllerHost.createArrangerCursorClip` only follows the UI-selected clip. These methods therefore use exact native bindings behind the same 6.1.4 version/JAR-hash gate (`native_unavailable` otherwise). They reach the clips on one track's **main clip lane** without selecting anything:

- player track `ynF.HVx()` → lane `Tsu`;
- `sru.iAj()` → note-clip timeline `VDz`, which holds instrument (`kOI`) and audio (`Nbl`) clips;
- events `qIe.cfM()`, in event order (creation order on 6.1.4, not start order); `arranger.list` sorts them by start.

| Method | Parameters / operation |
|---|---|
| `arranger.list` | `target` (track ref) optional; read-only. Without `target` it reads every existing Audio/Instrument/Hybrid track of the track window (one native lane read each, inside one native job); clips are in track order, then by `start`. `clips:[{ref, start, length, end, bar, name, kind:"instrument"|"audio"|"other", loopEnabled, loop:{start, length}, playStart, playStop}]`, `count`, `markers:[{ref, name, beat}]` and `markersComplete` (the `markers.list` rows and its `observationsComplete`), `tempo` (bpm), `timeSignature`, `window` (the track window); `ref` is `{kind:"clip", track, lane:"main", start, name}`. `bar` is `1 + start / (numerator * 4 / denominator)` at the current public time signature (fractional off a bar line; time-signature changes are not applied); `bar`, `tempo` and `timeSignature` are null until the transport has reported them. **Safety and evidence:**

- **Writes:** need recording and both automation-write modes observed off; `tracks.routing.set` also needs an observed stopped transport, `devices.sidechain.set` does not (pending native verification on 6.1.7: reverted if changing a sidechain while playing proves unsafe). The bank target, track UUID, lane and timeline identity, owning project/context lifecycle and model thread are checked before and after the native call.
- **Overlaps:** a create, copy, move or resize whose range overlaps another clip on the lane is refused (`overlap`). Touching ends are allowed. Nothing is overwritten or trimmed.
- **Results:** `ref` (the clip after the write; none after a delete), `clip` (values, after), `previous` (edits), the whole lane `clips` (each row with its `ref`), `verification:"native_readback"`, `nativeUndo:true`, `undoGroupingVerified` (`true` for a create: the clip and its notes are one "Create Arranger Clip" transaction, one Undo step natively; `false` otherwise).
- **Unknown outcomes:** a readback mismatch after dispatch is `unknown` / `readback_mismatch`. It and any other post-dispatch failure return an unknown result and hold further arranger writes (`arranger.quarantine`, refused `unresolved`) until you inspect `arranger.list` and `ack` it. Reads stay available. Never retry.
- **Identity:** the ref is the clip's start and name, compared on every write; there is no persistent clip identity. Moving a clip makes its old ref `target_not_found`.
- **Aliases:** renaming an alias clip renames the shared content (the name lives on the clip content).

**Not covered:** automation clips, take/comp lanes, other clip lanes, group-track (meta) clips, effect/master tracks, splitting, fades, looping or other clip properties, audio file placement, cross-track copies, and arranger note editing after creation. Offline, every binding resolved against the inspected 6.1.4 JAR. Native behavior is established only by the native tests listed in VERIFICATION.

### Arranger automation points (version-gated)

The guide draws arranger automation in a track's Automation Lane section: "double-click any area of the automation lane" creates a point, and ALT-double-clicking a transition resets it "to linear interpolation" ([automation, ch. 9: The Arranger's Automation Lane Section; Drawing and Editing Automation](https://www.bitwig.com/userguide/latest/automation)). The public controller API cannot read or write points (only `hasAutomation`, `deleteAllAutomation` and touch), so these methods use exact native bindings behind the 6.1.4 version/JAR-hash gate (`native_unavailable` otherwise). Paths follow Bitwig's own model tests and lane seeding:

- player track `ynF.mvz()` → lane set `euS`; parameter reference `eD.cfM(bDH)`; find lane `LEn.Hnt(z2y)`;
- create lane `YW.MRY(z2y, false, false, false)` ("Add Automation Lane" without the seed point at the current value or the UI reveal);
- `lkr.LaE().tSS()` → point timeline `PQT`; points `qIe.cfM()` (`hMP`, ordered by beat): beat `SMz.x3t()`, value `vcm.cfM(point)` through the lane range `PQT.wGc()` (an `aL`, normalized 0..1), interpolation `dfo.FzB()` (`jRs` HOLD/LINEAR), curve `hMP.dU_()`;
- new point `bU.MRY(beat, value, jRs, curve)` (curve 0 for a new point, the kept curve for an updated one), insert `PQT.cfM(point, index)`, delete `PSn.MRY(point)`.

Targets are parameter refs: a track's volume (`FNX.tSS()`, class `A` "Volume") or pan (`FNX.nfq()`, `mAq` "Pan") of its mixer channel `ynF.TbN()`, as `tracks.get` returns them (`{kind:"parameter", owner:<track ref>, id:"volume"|"pan"}`), or `{kind:"parameter", owner:<gridModule ref>, id:<parameter key in the grid.export spec>}`: a float (`Opy`) Grid module parameter on a top-level device of the same track. Any other owner (device, remote page, modulator) is `invalid_params`/`unsupported_scope`. The parameter's owning track must be the track the ref names.

| Method | Parameters / operation |
|---|---|
| `automation.points.get` | `target` (a parameter ref: a track's `volume`/`pan` as `tracks.get` returns it, or a Grid module parameter `{kind:"parameter", owner:<gridModule ref from grid.export>, id:<parameter key>}`; any other owner is `unsupported_scope`), optional `range:{start, end}` (inclusive). Read-only, no stopped transport needed. `ref`, `lane:{exists, count, pointsHash}` (SHA-256 over every point's beat, value, interpolation and curve; an empty or missing lane is `e3b0c442…b855`) cover the whole lane; `points:[{beat, value, interpolation:"linear"\|"hold", curve}]` lists those in range, at most 1024 (`pointsInRange`, `truncated`) |
| `automation.points.set` | `target` as `automation.points.get`, `points` (0–1024 `{beat 0–4194304, value 0–1, interpolation?}`, strictly increasing, inside `range` when it is `{start, end}`), optional `range` (`{start, end}` inclusive, or `"all"`), optional `expect:{pointsHash}` from a fresh get (mismatch: `stale`/`target_changed` with `observed`). The range rule: **without `range`** only the listed points are written (inserted, or updating the point at the same beat) and nothing is removed; **with `range`** the points with `start <= beat <= end` (every point for `"all"`) become exactly the listed ones. A listed point keeps what it omits from the point it updates (interpolation, curve); a new point is `linear` unless given, curve 0. Written beats and `range` bounds snap to a 2^-20 beat grid and values to a 1e-9 grid; strict increase and range membership are checked on the snapped beats (two beats that snap together are `invalid_params`). Points are identified by beat and compared on these grids (curve too, as `automation.points.get` returns them), so points read back and written as `{beat, value, interpolation}` with `range:"all"`, or any request sent twice, are `already_matched`. Removed and updated points are deleted and the new ones inserted at their lane index (an update passes the kept curve to the new point) inside one project transaction (`g2L.cfM("Set Automation Points", false)` … `g2L.cfM(false)`); untouched points are not rewritten. A missing lane is created in that transaction; an empty request on a missing lane creates nothing. Bitwig keeps its own base point at beat 0 when a lane's last points are deleted: with nothing requested, that one point remaining counts as cleared (`applied`), and a lane holding only it is already cleared |

**Safety and evidence:**

- **Writes:** need recording and both automation-write modes observed off; `tracks.routing.set` also needs an observed stopped transport, `devices.sidechain.set` does not (pending native verification on 6.1.7: reverted if changing a sidechain while playing proves unsafe). Track proxy, UUID, lane set, parameter (Grid binding re-guarded), lane and timeline identity, owning project/context lifecycle and model thread are checked before and after the native call. Only continuous (`aL`) lanes are supported.
- **Readback:** the whole lane is read back: untouched points are the same native objects, the removed and updated ones are gone, and the lane equals the expected list (canonical beat, value, interpolation, curve). Results add `previous:{count, pointsHash}`, `summary:{inserted, updated, removed, unchanged}`, `laneCreated`, `verification:"native_readback"`, `nativeUndo:true`, `undoGroupingVerified:false`.
- **Unknown outcomes:** a mismatch is `unknown` / `readback_mismatch`; it and any other post-dispatch failure return an unknown result and hold further automation writes (`automation.quarantine`, refused `unresolved`) until you inspect `automation.points.get` and `ack` it. Reads stay available. Never retry.
- **Values** are normalized through the lane's own range; whether they equal the public normalized volume/pan values of `tracks.get` is not yet observed natively.

**Not covered:** clip-launcher automation, automation clips, group/effect/master tracks, device remote controls and non-Grid device parameters, non-float Grid controls, curve (tension) writes, and automation mode/override state. Offline, every binding resolved against the inspected 6.1.4 JAR; native behavior is not yet observed.

### Track routing and device sidechains (version-gated)

The guide's Track I/O Settings give each track an input chooser that "lets you select which signals are getting routed into the track" and an output chooser that "lets you select where the track's final audio is getting routed to" ([recording clips, Track I/O Settings](https://www.bitwig.com/userguide/latest/recording_clips)). Dynamics, Gate, Transient Control and plug-ins have a sidechain source chooser ([sidechaining tutorial](https://www.bitwig.com/learnings/sidechaining-tutorial-49/)); the Audio Sidechain, Audio Rate and Note Sidechain modulators take a project signal ([modulators](https://www.bitwig.com/userguide/latest/modulator/)). The public controller API exposes none of these as settable entries, so these methods use exact native bindings behind the 6.1.4 version/JAR-hash gate (`native_unavailable` otherwise). They call the same model operations as Bitwig's own routing menus (`bhe`/`bhg` outputs, `bhv`/`bhy` inputs and sidechains), its DAWproject importer/exporter and its internal "Route input" command:

- track proxy `getDeepestTarget()` → `zwV`; channel `zwV.JJY()` → `xJo` (a group's channel equals `kWY.TD2()` and carries the group's public trackId); identity `RYd.kFU()`;
- output chooser `ynF.OnS()` → `j2s`: current `UZr()`, set `IwV(twn)` ("Change Routing Destination"), clear `wGc()`, accept check `MRY(Object)`; destinations are a channel's `Tfs()` (audio input, `DfX`) or `Ccl()` (note input, `WIv`);
- input chooser `ynF.ADn()` and a device routing component's `GjM.eej()` → `lbA`: current `UZr()`, set `cfM(qy)` ("Change Routing Source"), clear `wGc()`, accept check `MRY(Object)`; sources are a channel's `LIl()` (pre-fader), `SLC()` (post-fader), `RbC()` (note output) and the project's `pHd.cCk()` (All ins), `JhA()` (computer keyboard), `tB1()` (on-screen keyboard); `w3i.rGR()` gives an entry's channel and `bCo.qm()` its name;
- sidechain components: every `W2w` below the device found by `com.bitwig.ramona.core.zjj.cfM(device, W2w, null)` whose nearest device (`AVL.IwV(xlG)`) is that device, so nested chain/layer devices are excluded; kinds come from `W2w.cfM()` (`kCk` groups), `PBl.aA_()`/`UNj()` give `componentId`/`label`, `D3M` audio, `gjc` note, `aBN` plug-in audio, `NgI` audio-in; a modulator host is `tad` (`modulatorId` `tad.kFU()`), a Grid module host `rSf`.

An entry is `{kind, track?}`, where `track` is a track ref (`{kind:"track", id, name}`, the name being the track's public name, since native bus names are blank or generic); a read's entry is copied verbatim into the write or into `expect`, and its display name is reported beside it (`name`, `sourceName`). Requestable output kinds: `none`, `track_audio_input`, `track_note_input`. Requestable input/sidechain kinds: `none`, `pre_fader`, `post_fader`, `track_notes` (each with the source `track`), `all_ins`, `computer_keyboard`, `onscreen_keyboard`. Anything else (hardware ports, device outputs, host-application buses) reads as `{kind:"other", name, nativeType}` (the name may be empty) and can only appear in an `expected…` field, where it is matched on the exact name and, when given, `nativeType`. Track entries are tracks of the current 16-track bank.

|---|---|
| `tracks.routing.get` | `target` (track ref), optional `includeChoices`. The result carries `ref`. Read-only, no stopped transport. `output:{entry, kinds, writable, reason?, choices?}`; `input:{entry, kinds, nativeSourceGroups, writable, choices?}` or `null` with `inputUnavailableReason` for track types without an input chooser (only Audio/Instrument/Hybrid have one, and the native track kind `ynF.BNq()` must agree). ### Export audio and tracks.bounce (version-gated)

The guide exports with the Export Audio dialog ([exporting audio](https://www.bitwig.com/userguide/latest/exporting_audio)); Bounce in Place "presents no dialog box" ([bouncing to audio](https://www.bitwig.com/userguide/latest/bouncing_to_audio)). The public API has neither. Both methods start Bitwig's own render job (a `DLy`) where its UI does, behind the 6.1.4 version/JAR-hash gate (`native_unavailable` otherwise):

- **Export:** `xlG.cfM(tracks, basePaths, wav, flac, flacDepth, mp3, …, vorbis, …, opus, …, start, end, tap, wavDepth, dither, realtime, sampleRate)`, the call the dialog makes after building its paths (flags matched to the `export_wav/flac/mp3/vorbis/opus`, `dither` and `real_time` preferences it reads). Paths are extensionless: the WAV writer appends `.wav`, the encoder `.<format>`. mp3/vorbis/opus and realtime are passed off.
- **Bounce:** static `SUv.MRY(project, tracks, start, end, tap)`, which builds an `x2r` job that replaces the range on each track's main lane with one audio clip in one undoable action. The audio goes to the project's managed audio folder.

| `tracks.bounce` | `targets` (1–1024 distinct audio/instrument track refs), `start`, `end`, `tap` (`pre_fx`, `pre_fader`, `post_fader`), `inPlace` (only `true`; default `true`). `{outcome:"applied", tracks:[{track (ref), clip, clipsBefore, clipsAfter, trackTypeBefore, trackTypeAfter, warning?}], nativeUndo:true, …}`. Observed on 6.1.4: bouncing an instrument track turns it into a Hybrid track; deleting the bounced clip does not turn it back, Undo does. `warning` is set when the observed public type changed; the type can lag the job by a flush, so re-read `tracks.get` |

**Before dispatch (errors, nothing changed):** observed stopped transport with recording and automation write off; existing output files (`target_exists`, unless `overwrite`) or a missing directory (`invalid_target`); a job of ours or Bitwig's already running (`busy`); a remote-session project (`unsupported_scope`); Bitwig's own refusals (`host_refused`: `g2L.FXc()` — project not open, engine not connected, recording, no project directory — or an inactive project engine, where the native call would return silently); missing files or plugins (`needs_confirmation`: the job would ask in a dialog). Bounce refuses group tracks (`unsupported_scope`).

**Verification:** dispatched once, never retried. The job registers as `g2L.oQj()` synchronously; none observed after dispatch is an `unknown` result. Completion is the job's `DLy.LaE()` latch, which also counts down on failure, so success is read back:

- export: every file new or changed, nonempty, a valid RIFF/WAVE (PCM or float) or FLAC STREAMINFO header with the requested bit depth and sample rate, and at least one frame. Otherwise `job_failed`: an error when nothing was written, else an `unknown` result.
- bounce: the lane is read before and after (the `arranger.list` readback, diffed by native clip identity). Each track must have exactly one new audio clip at `[start, end]` and nothing else overlapping the range; clips cut at the range edges may come back as new objects outside it. No lane changed is the error `job_failed`; any other difference is an `unknown` result (`readback_mismatch`) and holds further bounces (`render.quarantine`, refused `unresolved`) until you inspect `arranger.list` and `ack` it. Only a job's first verification can hold; later `jobs.get` reads just report.

A job without its latch by the deadline returns `{outcome:"unknown", reason:"deadline", job:"render:<n>", nativeCompletion:"pending", next}`; follow it with `jobs.get`. Further renders are `busy` while it runs (a job hold in `status.holds`); a bounce that completed after its request returned must be verified with `jobs.get` before the next render. After inspecting, `ack` on the job hold gives the job up so a job Bitwig never completes does not block further renders. A request that fails after dispatch names its `job` too.

**Side effects:** on a successful export Bitwig opens the folder in the file manager (`kd.FzB()` is constant true in 6.1.4; not suppressed). A playing transport is refused rather than stopped by the job.

**Not covered:** mp3/vorbis/opus, realtime rendering, custom taps, loop/selection-derived ranges, launcher-clip bounce, bounce without replacement, and normalization. Offline every binding resolved against the inspected 6.1.4 JAR; native behavior is not yet established.

### Device modulators

Device modulators (the 43 types of a device's Modulators browser: LFO, Random, Steps, ADSR, Macro, …) on one root device, typically a Poly Grid. The main use is modulating Grid module controls that have no input port (envelope times, step counts, drive, pulse width). Same 6.1.4 loaded-JAR gate. A modulator is addressed by its ref `{kind:"modulator", device, id, name}` (`id` is the native UUID; the `name` is compared only when the modulator itself is the target); its controls by parameter refs owned by it.

| Method | Params | Native operation |
|---|---|---|
| `modulators.list` | `target` (root device ref), optional `offset` 0–100000 (default 0), `limit` 1–128 (default 64) | read: the modulators with refs, typed `parameters`, read-only string `panels`, `outputs` and each output's `mappings` |
| `modulators.get` | `target` (modulator ref) | read: the same row for one modulator |
| `modulators.describe` | optional `type` or `query`, `lang`, `installationRoot` | client-side, offline: with `type`, per-control help (`docKey`, `title`, `description`, `documentedValues` marked unverified); without it, every type (ranked by `query`) with category and description from Bitwig's own help files |
| `modulators.insert` | `to` (root device ref), one of `typeName`/`typeId`, optional `params` {name: value} and `map` [{`target`, `amount`, `outputId?`, `transfer?`, `enabled?`}] (see [Insert and configure](#results-errors-and-recovery)) | the modulator browser's insertion point (`ModulatorGridInsertionPoint`, as Bitwig's own test harness uses), appended below the existing modulators |
| `modulators.delete` | `target` | the auxiliary device grid's undoable delete (shared with `grid.modules.delete`) |
| `modulators.map` | `source` (modulator ref), optional `outputId`, `target` (parameter ref of a Grid module or modulator on the same device), `amount`, optional `transfer`, `enabled`, `expect {amount}` | the public modulation add, wrapped by Bitwig in a named undo transaction |
| `modulators.unmap` | `source`, optional `outputId`, `target`, `expect {amount}` | Bitwig's "Clear modulation" undo transaction |

A modulator control is written with `parameters.set` (owner kind `modulator`): the bare raw value of its `kind` (`float`, `integer`, `boolean`, `enum` option value), `{display}` for a float in a unit the host's display table converts (`unsupported_unit` otherwise) or `{label}` for an enum, whose `options` are `[{value,label}]`; `expect {value}` compares the raw value first. It is the same external-controller raw write as `grid.parameters.set` and runs while playing.

Rows carry `ref`, `index`, `name`, `typeId`, `x`, `y`, `contentsAvailable`, `parameters:[{ref?,name,value:{value,display,kind,minimum,maximum,options?,...}}]` (the `ref` is absent for an empty `parameterId`, which a ref cannot carry), `panels:[{id,kind:"string",value}]` (read-only native string panels, empty strings and Unicode preserved without trimming; they are not parameter refs) and `outputs:[{outputId,mappings:[{target,amount,transfer,enabled,polyphonic,scaledByAnotherSource}]}]`. A mapping `target` is a parameter ref (owner a Grid module or a modulator on this device) or, for a control of the device itself or of something else, `{location:"device"|"external", path, parameterId}`. `modulators.list` returns `parent`, `count`, `window:{offset,limit,total,returned}`, `complete` (false for a partial page, unmaterialized contents or unsupported controls, listed in `unsupported`), `nativeMutation:false`. A modulator whose device was never opened has `contentsAvailable:false` and no parameters; nothing is loaded to read it. Limits apply to work: 4096 primary members, 256 direct children per modulator, 256 mappings per output, 1024 UTF-16 units per native text, 240000 serialized characters; overflow is `out_of_bounds`, never clipped data. Secondary and nested modulators are not covered.

`modulators.map` is an upsert: with no mapping between the output and the target it creates one (`transfer` default `linear`, `enabled` default true); with one it writes the `amount`, `transfer` and `enabled` it is given and keeps the ones it omits. `outputId` may be omitted only when the modulator has exactly one output. `amount` is in −1..1 and never clamped: an amount beyond the target's modulation range rejects. `expect {amount}` names the amount the mapping has now (a mapping that is absent has none): another one is `stale` with reason `target_changed` and `observed:{amount}`. `modulators.unmap` of a mapping that is not there is `already_matched`. `transfer` is one of `linear`, `rectify_pos`, `rectify_neg`, `abs_linear`, `inv_abs_linear`, `cubic`, `inv_cubic`. Polarity is not a mapping property: it is a modulator parameter (for example an LFO's bipolar switch). Bitwig refusing an output/target pair (for example a modulator modulating itself) is `unsupported_scope`. Results carry `ref` (the target parameter ref for `map`/`unmap`, the new modulator for `insert`), `previousMapping` and `mapping`.

Structure writes (insert, delete, map, unmap) need recording and both automation-write modes off and a stopped transport; value writes run while playing but need the write-context prerequisites of Grid parameter writes (undo manager idle, device lock owned by the default document context, control settable and untouched). Order: ref resolution and `expect`/range checks, prepare, re-read and re-check, then one native call; nothing is retried or rolled back. Insert, delete, map and unmap verify in a later document event: exact mapping readback (amount, transfer, enabled), or membership equal to the previous list plus exactly one modulator of the requested type (insert) or minus the deleted one. A disagreement after dispatch is an `unknown` result (`readback_mismatch`). Unmaterialized contents return `native_unavailable` for edits. A missing modulator, output or control returns `stale` with reason `target_not_found` and `next`; a renamed modulator or control, or a changed membership or amount, returns `target_changed` with `current`. `status {detail:"full"}` carries a `modulators` section (edit bindings known to be available or why not, the edit methods, the stopped-transport rule); binding availability is not native acceptance.

Root targeting uses the public observed index/name and native owning-track corroboration, not persistent physical-device identity. Both reads and edits report `nativeMutation` and `nativeUndo` as what was dispatched; owning project/context checks are not the application's active-project identity, and unobserved same-metadata replacement, native ABA and atomic model snapshots are not guaranteed. Prior 6.1.3 native coverage was limited to materialized primary Macro string panels and establishes nothing about 6.1.4 instance coverage, DSP, Undo, MIDI or whole-toolkit acceptance. See the current [verification record](VERIFICATION.md).

### Version-gated Grid controls

`grid.catalog` and `grid.get` are hidden read-only Grid methods (agents use `grid.describe` and `grid.export`; Grid availability is the `grid` section of `status` with `detail:"full"`). Their schemas come from the same strict Python catalog used by CLI and MCP: extra fields, explicit nulls, numeric strings and boolean-as-integer values are rejected. The standard client `timeoutMs` option remains envelope metadata, not a Grid parameter. No implicit selected-device target is accepted.

The native compatibility gate accepts only the Bitwig versions `src/bitwig_agent/shared/host.json` lists (**6.1.4** and **6.1.7**), each with its exact loaded host JAR SHA-256. Matching a filename or an unrelated installed JAR is insufficient. `status` with `detail:"full"` reports (in its `grid` section) the actual gate/binding result and separates catalog, structure and typed-parameter coverage; it does not promise full coverage merely because the host version matches. Unsupported or unresolved bindings fail closed rather than trying guessed reflection names, GUI selection, installation or automatic fallback.

`grid.catalog` filters native MODULE names (case, spaces, hyphens and punctuation ignored; every whitespace-separated query word must occur in the name, so `lowpass` and `low pass` find `Low-pass`) and returns deterministically ordered `{typeId, name}` entries with a `window` reporting `total`, `offset`, `limit` and `complete`. When nothing matches, up to five nearest names (edit-distance ratio on the normalized names) come back as `suggestions: [{typeId, name}]`. An empty query includes all mapped MODULE entries; it is not a device/preset catalog. Type UUIDs identify module types, not instances in a patch. `devices.catalog` remains the separate factory-device file discovery API.

`grid.get` takes `target`, the device ref from `devices.list` (a root device; a device inside a chain is `unsupported_scope`). For example, the following JSON has a valid shape but its refs must be replaced with discovered live ones:

```json
{"target":{"kind":"device","track":{"kind":"track","id":"12345678-1234-1234-1234-123456789abc","name":"Lead"},"index":0,"name":"Poly Grid"},"moduleOffset":0,"moduleLimit":32,"includeParameters":false}
```

For layout, wiring and module naming, use the structure-only example above. To get one module's parameter IDs, pass `moduleIds` (1–256 current `instanceId`s, UUID case-insensitive): only those rows are returned, with parameters, without paging every module. Ids absent from the graph are listed in `missingModuleIds`; a filtered read is never top-level `complete`, and `window` counts the selected rows. Connections remain the incoming links of the returned modules. `grid.get` rows are enough for parameter CAS writes: a parameter row's `kind` and `value` are valid `expectedKind`/`expectedValue` while still current (stale ones are refused as an error), so `grid.get` with `moduleIds` is the fresh read for a single value or a coupled boolean panel's linked parameter. None of this changes the `includeParameters:true` wire default or makes several pages atomic.

By default rows omit the obfuscated native `modelClass` of modules and ports, the per-port and per-parameter `path`, the top-level `device`/`graph` class metadata, `coverage`, `nativeRevisionAvailable` and `identityCaveat`; no write needs them. `diagnostics:true` restores them. The constant caveats they carried: coverage is mapped modules and ports only (nested children not traversed, connections are incoming links within the same graph, no native revision, unit and display readers unverified); `instanceId` is a current native UUID that changes across project reopen and must be reacquired; `localKey` and paths change after edits; the native owning-track UUID is corroborated before and after capture; device index and name remain public observations that can lag native rebinding and cannot distinguish same-track same-name replacement; there is no persistent device identity, native ABA detection or cross-request atomicity.

The result includes target metadata, modules, connections, a bounded window and explicit coverage/identity limitations. Read instance UUIDs, catalog type UUIDs and list-local keys as separate identities. Native instance UUIDs are not persistent: all seven observed module UUIDs changed on same-process project reopen while types, positions, ports, typed values and stored topology matched. Reacquire identifiers after reopening; labels and list-local keys are not substitutes for persistent identity. Unknown model types, unsupported parameter fields and excluded pages must not be interpreted as a complete graph. `includeParameters=false` requests structure without parameter values. A sequence of pages is not an atomic snapshot and no native revision is fabricated.

`window.complete` means the module page covers the current module window. Top-level `complete` additionally requires no recorded unsupported coverage: a structure-only read intentionally has `complete:false` with `parameters_not_requested`, and a full module page can still report unknown native children. Check the requested coverage and returned structure; do not require top-level `complete:true` merely to use an otherwise complete layout/wiring/name page, or mistake it for lossless native export.

Native path ancestry also changed after group insertion/save/reopen; device-local data survived, but full path strings are not stable identifiers. `target.nativeOwningTrack` reports before/after corroboration: derive the native device's nearest WSA track ancestor, apply the public channel-ID mapping (including kWY's channel alias), and compare its UUID with the requested track before graph traversal and again after capture. Missing ownership/alias/UUID rejects `native_unavailable`; mismatch rejects `target_changed`. There is no fallback to a name or old public observation. Device position remains `public_observed_only`; this guard does not establish persistent device identity, same-track same-name replacement detection, native ABA detection or cross-request atomicity.

In `grid.get`, modules expose `instanceId`, `localKey`, `typeId`, `x`, `y`, `width`, `height`, input/output ports and optional typed parameters. Footprints use native grid units, not pixels; unavailable dimensions remain null/partial. `name` is the native effective instance name; `customName` is its raw override (empty means no override); `typeName` comes from the catalog type UUID lookup. Ports retain their keys/paths and add native `name`, including disconnected inputs. Typed parameters retain structural `path` and add local/preset `parameterId`, stored `name` and `shortName`. These identifiers and labels are not promised persistent or globally unique. Empty native names remain empty; unavailable metadata is explicit JSON null with a field-specific `unsupported` reason, never a guessed fallback. Parameter `supported` describes the typed observation, not complete metadata coverage.

With `diagnostics:true`, `device.modelClass`, `graph.modelClass`, module/port `modelClass` and (always) `editContext.ancestorUndoManager.modelClass` expose concrete native runtime classes for compatibility diagnostics. They are not stable public identifiers or permission to mutate.

Float `numericUnit` is the native definition's **unit-kind token**, not a promise that the raw number is already in that unit; use the existing native display string for presentation. Integer `displayPrefix`/`displaySuffix` are native presentation affixes. Apart from the few verified display-write units in Grid usability additions, formatter output and labels define no reversible numeric-input grammar. Context-dependent/localized UI equivalence is not universally guaranteed. Connections describe **incoming stored links to the returned modules**: each source belongs to the same graph but can lie outside the module page. Therefore an endpoint absent from the current page does not imply a broken cable. Inspect `complete`, `unsupported` and `window` (and, with `diagnostics`, `coverage`/`identityCaveat`).

Connections are **stored native-model links**, not a proven active/audio/note signal graph. Independent native inspection found Note Grid with Enable All Expressions off showing four visible cables while the model retained eight links, including disabled expression paths. The reader does not infer activation from link existence or silently filter these paths. Use the native UI/behavior as a separate oracle until activation metadata is mapped and verified.

The `grid` section of `status` with `detail:"full"` exposes `gatePassed`, `available`, `binding` and `runtimeVerification` separately. `catalog`, `structure`, `nativeOwningTrack`, `typedParameters`, `display`, `moduleFootprint`, `moduleNames`, `typeNames`, `parameterNames`, `portNames`, `numericUnits`, `integerDisplayAffixes` and `parameterInspection` describe availability, coverage and binding failures. Native ownership is required for graph reads; failure disables structure/dependents, not the independent catalog. Context bindings gate parameter inspection separately without disabling existing graph reads. Descriptive metadata groups bind independently; missing labels remain null/partial. `native_unavailable` means a required binding/observation is unavailable, `out_of_bounds` a traversal bound, and `kind_mismatch` a non-Grid target; do not collapse these into an empty graph. Standard target/readiness/stale-context/deadline errors still apply.

The four read operations use the mapped native document dispatcher with deadline/cancellation and explicit target/ownership checks; they do not mutate the host or select a device. Both application dispatch-thread status and `Q_().isEventDispatchThread()` are checked. `Q_` returns the current scoped executor, not an executor owned by that model; ancestry and UUID checks remain separate. Read coverage does not establish parameter/topology writes or native undo. Insertion and cable writing are separately specified below.

Native names are not always inspector wording (`Hold Time` versus `Timeout`, `Clip Mode` versus `Clipping`). Nonempty FX numeric Remote Controls, native UUID races and the kWY track-alias branch lack comprehensive native coverage. Track scalar/send observations do not establish selection readability after reopen. See [coverage limits](VERIFICATION.md#coverage-limits-and-unresolved-results).

#### String panels

Exact `xMn` models (not arbitrary `btw` subclasses) appear in `grid.get` as `supported:true`, `kind:"string"`, `controlFamily:"string_panel"` with their actual identifier, path and native String value. `name`, `shortName` and `display` remain null; `string_panel_labels_unmapped` and `string_panel_display_unmapped` keep coverage partial. No numeric range, options, units or dependent-coverage claim is fabricated. Observation and write support are reported separately (see `status` `grid.stringPanels` (with `detail:"full"`)).

Empty strings, whitespace and Unicode are preserved exactly, without trimming, truncation or scalar coercion. The bridge's existing1024 UTF-16-unit text bound applies: null/wrong-type values reject `native_unavailable`, overflow rejects `out_of_bounds`. This is not a native string-length limit. A graph page with `includeParameters:true` can therefore reject on an oversized mapped string that was previously opaque; `includeParameters:false` does not read parameter values. Exact single-parameter inspection does not read unrelated values.

String panels retain common lifecycle/project/context/thread/default-transaction/context-predicate/undo/device-lock observations. Their actual `btw.cfM():com.bitwig.ramona.core.ESe` value property supplies descriptor-only `isSettable`; scalar license/touch are inapplicable, reported null with `scalarLicenseTouchApplicable:false`, as for boolean panels. False settable/non-writable context observations do not prevent otherwise valid reads. Unlike boolean panels, no coupled scalar consumer is required or reported.

`status` `grid.stringPanels` (with `detail:"full"`) separately reports exact native string-panel binding coverage and inspection availability (`inspectionAvailable`), and the write operation as `writeAvailable` (with `writeReason` when false): the write binds independently (`btw.hUR(String):void`, final public, declared on the string-panel base `btw`) behind the same exact 6.1.4 host version and JAR-hash gate, and its failure leaves string reads, scalar and boolean-panel support intact. Binding does not establish runtime acceptance; live string-panel GUI/selection/persistence checks remain separate.

A string-panel write is `grid.parameters.set` (single or batch entry) with `expectedKind:"string"`, a JSON string `expectedValue` (exact current text) and a JSON string `value`, each at most 1024 UTF-16 units, empty allowed, preserved verbatim (no trim, normalization or coercion); `display` is not valid with string kind. It uses the same kind of checks as the boolean-panel path (without a coupled scalar and without the scalar-specific parameter guard): native binding, kind/text compare-and-set before any no-op, the common edit-context/lifecycle/skip-predicate writability checks, dispatch, deadline check, context guard and an exact native readback; an unobserved requested text is an `unknown` result (`readback_mismatch`; never retried or rolled back). The native operation is the Undo-aware "Change Value" model change; Undo grouping is not verified. Results carry `outcome` (`applied`, or `already_matched` when nothing needed writing), `previousValue`, `requestedValue`, `mutationDispatched`, `verification:"native_readback"` and no coupling fields. A scalar request aimed at a string panel rejects `target_changed`, and a string request aimed at another kind likewise. The Label module displays the module name, not a string panel; rename it with `grid.modules.set` (or `grid.apply`).

#### Step tables

Exact `imU` models (the `FDM` float array behind Steps, Pitches, Gates, Probabilities and Accents) appear in `grid.get` as `kind:"steps"`, `controlFamily:"step_array"` with `parameterId` (the native identifier, possibly empty), `values` (the first `stepCount` entries, the module's `STEPS` value; `full:true` returns up to 256), `arrayLength` (native declared length; the schema default is 256 but 64 was observed natively on 6.1.4 for all five modules, so it is not tied to `STEPS`), `stepCount` (null with `step_count_unavailable` if `STEPS` is unreadable; then 64 entries), `valuesComplete`, `minimum` -128 and `maximum` 128. A native array shorter than its declared length reads zero-padded. Entries are 32-bit floats printed in their shortest decimal form. The reported -128..128 `minimum`/`maximum` is only a finite sanity bound (the shared native generators and transforms work in -1..1), not a per-module range; writes are never clamped. Natively observed on 6.1.4 (Poly Grid, values set in the UI and read back): Pitches values are in Grid pitch units, Gates are 1/0, Accents are 0/0.5/1, Probabilities are 0..1. Steps unipolar/bipolar was not part of that observation. Triggers has no step array.

A write is `grid.parameters.set` (single or batch entry) with `expectedKind:"steps"`, `expectedValues` (1–256 entries compared after rounding to float with the first live entries; the CAS window is its own length, bounded by `arrayLength`, not the live `STEPS`, so a batch that also changes `STEPS` stays all-or-nothing at preflight; normally pass the prefix from `grid.get`), `values` (1–256 entries within -128..128, not longer than `expectedValues`; rejected `invalid_params` otherwise) and optional `full`. It replaces the whole native array with `values` patched in at step 0, so every other entry stays unchanged, through the recorded `FDM.FzB(float[])` change, behind the same version and JAR-hash gate, CAS, context guards and exact whole-array readback as string panels (`unknown` / `readback_mismatch` on mismatch, never retried). Results carry `outcome`, `previousValues`, `requestedValues`, `verification:"native_readback"`. Undo grouping is not verified. `status` `grid.stepArrays` (with `detail:"full"`) reports `inspectionAvailable` and `writeAvailable`.

Child models that hold no user data (`BgP`, `Kiy`, `HQh`, `L1`, `uUS`, `fwH`, `qzH`, `Znu`: engine feeds, indicators, display state) are classified internal: they are not listed and not unsupported (module `internalChildren` counts them; `diagnostics` lists them as `reason:"internal_child_model"`), so `complete` reflects only real gaps.

#### Device voicing

`grid.voicing.get` reads the device's voice model (`xlG.Mb2()` → `jBG`): `voices` 1–64, `voiceStacking` 1–16, `monoMode` `true_mono`|`digi_mono` (native TRUE_MONO / ALTERNATING_VOICES), `retriggerMode` `never`|`on_note_on`|`always`, `notePriority` `last`|`high`|`low`, `legatoGlide`, `stealSameKey`, `allowOverlappingNotes`, and `mode` (`poly` when `voices` > 1, else the stored `monoMode`; mono is `voices` 1, not a separate switch). Natively observed on 6.1.4: a fresh Poly Grid reads `voices` 1, `monoMode` `true_mono`; setting `voices` 4 with `voiceStacking` 2 and back read back exactly with `changedUnrequested` empty. Only Poly Grid has the model: Note Grid and FX Grid return `supported:false` with a reason, and the write rejects `unsupported_scope`.

`grid.voicing.set` takes `expected` (exact current values, at least every field in `set`; extra fields are more preconditions) and `set` (at least one field). Stale expectations are refused as an error before dispatch, even for a no-op; nothing is clamped. Fields are written in a fixed order through the final recorded `SOn` setters, then read back exactly; `changedUnrequested` lists other fields the native change moved. The result `outcome` is `applied` when a field was written, else `already_matched`. Same recording/automation guards (playing is allowed), context checks and unknown-after-dispatch rule as the other Grid writes; undo grouping is not verified. `status` `grid.voicing` (with `detail:"full"`) reports availability.

#### Define Remote Controls pages

`devices.remote.define` gives a Grid device a named Remote Controls page whose knobs drive chosen scalar Grid parameters (for example a `Macros` page over the `VALUE` parameters of eight Value modules), shown in the device panel's Remote Controls page list. Bitwig generates one page per Grid module that has parameters, but none collecting arbitrary modules; this fills that gap without the UI's map mode.

Model (6.1.4, same version and JAR-hash gate): the device's Remote Controls host (`xlG.AgD()` → `pnr`) lists pages in the order **preset pages** (`LQR.BNq()` → `sZK`; "stored in the current preset"; a serialized field of the device's Remote Controls host), plugin pages, device pages (`BQF.fFs()` → `riz`), chain pages, one page list per Grid module (named after the module) and modulator pages. Only preset pages are created, edited or deleted: they are what the UI's "Add New Page" and the controller API's `createPresetPage` create, and the only list that can hold Grid module parameters. The page eligibility predicate (`vNq.cfM(v3U)`, also used by the UI's map mode) admits, on a device page, only parameters whose nearest `yzd` ancestor is the device (a Grid parameter's nearest is its module), while a preset page admits any remote-mappable parameter whose nearest device is the page's device.

`slots[k]` is slot `k` (0–7). Each non-null entry is a parameter ref owned by a gridModule ref of the target device (the `refs` of `grid.export` plus the parameter key); a ref of another device or another owner kind rejects `unsupported_scope`. A slot entry is `{parameter, label?}`: `label` (at most 256 UTF-16 units) is shown instead of the parameter's own name; a slot without one maps with Bitwig's default name and keeps the label an existing mapping has. A changed label alone clears and remaps the slot (the native map ignores an unchanged target). Only scalar parameters (`float`, `integer`, `enum`, `boolean`) map; boolean/string panels and step tables reject `unsupported_scope`. The same parameter in two slots rejects `invalid_params`. Null and trailing absent entries leave the slot empty.

The call is an upsert by `name`, with no `mode`: it edits the one preset page of that name in place, mapping slots that differ, clearing slots the request leaves empty and keeping matching ones; with no such page it creates one. A same-named device, module or plugin page is `target_exists`; several same-named preset pages are `ambiguous_name`. Names are compared as the page list shows them: module pages by module name, unnamed preset/device pages by their native fallback (`Perform` for the first preset page, else `Page <position>`).

Before any dispatch the writer resolves every slot (module, parameter, scalar kind, native mappability: a remote-mappable `bDH` whose nearest device is the target), checks an existing page's own eligibility for each parameter, the device's licence (the native create does nothing for an unlicensed device: `unsafe_state`), and the same document-context guards as the other Grid writes, applied to the device (owning project and attached context, default transaction, skip predicate, idle undo manager, device lock owner); recording and both automation-write modes must be off (a playing transport is fine). Then it calls the native operations the UI uses, each its own named undoable change: `riz.OzW()` ("Create Page", inherited by `sZK`; it also selects the new page in the device panel), the public final recorded name setter `faW.cfM(String)`, `vNq.cfM(int, String, SYo)` with `iok.TMF(bDH)` ("Map Remote Control Slot", what the UI's map mode reaches through `vNq.cfM(int, v3U)`) and `vNq.MRY(int)` ("Delete Remote Control"). A new page's own eligibility is rechecked before its first slot is mapped.

The result reads back exactly: the page is in the preset-page list and in the visible page list, its stored name is `name`, and every slot holds the requested native parameter object and, when the request gave one, its label (or is empty). It returns `{outcome, ref (the remotePage ref, when the page is visible), page:{name, kind:"preset", visible, pageIndex}, created, slots:[{parameter: <the slot's parameter ref>, label?}|null ×8], operations:[{op:"create"|"rename"|"map"|"clear", slot?}], pages:[visible page names], mutationDispatched, verification}` where `outcome` is `applied` when something was written, else `already_matched` (nothing dispatched), and `verification` is `native_readback`. `pageIndex` is the index in the device's visible page list, the list `devices.remote.get` observes (after its next host flush), so `devices.remote.page` can select it. Each operation is a separate Undo step (`undoGroupingVerified:false`). After the first dispatch any failure, including a readback mismatch, is an `unknown` result (`readback_mismatch` for readback): nothing is retried or rolled back; inspect with `devices.remote.get`. A new page that refuses a slot natively is left created, named and empty (`unsupported_scope`/`unknown`); remove it with `devices.remote.deletePage`.

`devices.remote.delete` deletes the page its remotePage ref names (the one preset page of that name, at the ref's visible index) through `riz.cfM(FyM)` ("Delete Page") under the same guards and verifies it is no longer listed (`outcome:"applied"`); a device/module/plugin page of that name rejects `unsupported_scope`, a missing page `target_not_found`, a page at another index `target_changed`. `status` with `detail:"full"` reports `grid.remotePages`. Bindings were resolved offline against the gated JAR; live Bitwig behaviour (visibility in the dropdown, Undo, save/reopen) is not established by these checks.

#### Write one Grid parameter

For a supported scalar or boolean panel, take the target from a recent `grid.get` parameter row . Send the device `target`, `moduleId`, `parameterId`, the row's `kind` as `expectedKind`, its raw `value` as `expectedValue`, and the requested raw `value`. The writer compares them with the live value and rebinds itself: a stale expectation rejects `target_changed` before any dispatch, even for a no-op, so no extra read is required first. String panels take `expectedKind:"string"` with string `expectedValue`/`value` (see `status` `grid.stringPanels` (with `detail:"full"`)). The server independently rebinds and rechecks live context; earlier `editContext` JSON is never authorization.

**Batch.** `writes` is 1–64 full single writes on one device (a repeated `moduleId`/`parameterId` pair rejects `invalid_params`; the single-write fields must then be absent). Every entry's live CAS, range, option and context checks run first; if any fails nothing is written and the call is an error (nothing changed) naming each failing entry (`#index reason: message`). Then entries dispatch in order, each as the ordinary single guarded write, and stop at the first entry that is not `applied`/`already_matched`: later entries are `not_applied` / `not_reached`; nothing is retried or rolled back. The result is `{outcome (the worst entry), written, writes:[{moduleId, parameterId, outcome, reason?, message?, previousValue(s), value(s), display?, requestedDisplay?, displayMismatch?, previousCoupledParameter?, coupledParameter?}]}`; a boolean-panel entry carries the same coupled-parameter observations as a single panel write. An entry refused before its own dispatch is `not_applied` with its `reason` and `message`; one that failed after its dispatch is `unknown`, whatever the error. Boolean-panel entries are preflighted too (support, linked bipolar parameter, context), so an unresolvable coupling writes nothing. If nothing was written and nothing is unknown, the call is an error instead.

| Kind | Accepted raw values |
|---|---|
| `boolean` | JSON `true`/`false` only, not0/1 |
| `integer` | Signed32-bit JSON integer tokens, within the actual native range |
| `enum` | Signed32-bit JSON integer tokens matching an actual listed option **value**, not its list position |
| `float` | Finite JSON numbers within native range; integer tokens must be exactly representable as binary64 |

Numeric strings, nulls, booleans-as-numbers, fractional/exponent tokens for integer/enum, nonfinite numbers and silent clamping are rejected. The TCP decoder preserves number lexemes before domain validation. Float fractional/exponent values use finite binary64 conversion; numeric positive/negative zero compare equal. Kind and exact raw-value preconditions precede even a no-op. A mismatch rejects `target_changed`; range/options/type failures reject `invalid_params`.

For scalar controls, the native editor invokes only the exact public final raw controller operation `aLw.UNj(double):void` for mapped rce/Hgx/iS3/Lig/RuU/nhW implementations. Exact Hgx→rXz→rce inheritance is checked; other subclasses are not automatically authorized. It adds no engine-input setter, parser, transaction wrapper, gesture/touch management, lock acquisition, retry or rollback. Live ownership/membership/lifecycle, project/context/default-transaction, thread, license/property, touch/undo and device-lock-owner relations are checked on the document callback before dispatch. The public controller's safely published stopped/nonrecording/nonautomation observations and monotonic epoch also reject observed changes/ABA while queued or completing. This is **observed safety**, not atomic native transport/recording exclusion.

For Hgx controls such as Attenuate VALUE, raw `0.5` means native `50%`, not raw `50`. Bipolar mode changes the live raw minimum; the same descriptor may change in place. Range is reread before dispatch, with no clamping or automatic mode change. A numeric write does not toggle bipolar/STEREOIZE or flatten panel references into a compound value. Changing bipolar mode is a separate native operation that can coerce a negative value to zero.

Results contain `outcome` (`applied` when written, else `already_matched`), the selected actual `parameter`, `previousValue`, `requestedValue`, `mutationDispatched` and `verification` (`native_readback`), plus the explicit `target` identity. A guarded already-matching request never invokes the setter. `nativeMutation`/`nativeUndo` indicate that the undo-aware native controller operation was invoked. Constant limits no longer echoed per result: Undo grouping is not verified, there is no engine acknowledgement, safety is observed nonrecording/nonautomation rather than atomic transport exclusion, and model readback is not DSP acknowledgement. After dispatch, native failure, timeout/cancellation, serialization or late target/safety failure is an `unknown` result. Inspect actual state before another write.

`status` `grid.parameterWrite` (with `detail:"full"`) is independently gated; unavailable writer bindings do not disable reads. Its `nativeUndoAwareOperation` describes the setter route; it exposes no dedicated Undo command or grouping guarantee. `graphWrites` describes the separately gated insertion, module move/delete/rename and single-input connection surface below, not scalar parameters or full topology editing. The capabilities call itself remains read-only.

Representative scalar observations do not establish all-module write behavior, disabled Note Grid DSP, atomic native transport exclusion or general undo grouping. See [coverage limits](VERIFICATION.md#coverage-limits-and-unresolved-results).

#### Boolean panels with a coupled scalar

The existing `grid.parameters.set` method also supports exact BMo boolean panels, not arbitrary BMo subclasses or every native GUI toggle. Discovery reports `kind:"boolean"`, `controlFamily:"boolean_panel"` and the panel's own `parameterId` (observed `BIPOLAR` on Attenuate). Unmapped labels/display remain explicit null with unsupported reasons. The panel is not a scalar controller: its `effectivelyLicensed` and `parameterTouched` are null, with `scalarLicenseTouchApplicable:false`, not invented false/true permission.

Inspection and writing require one uniquely referenced, exact Hgx control in the same module. `get` adds `coupledParameter` and `coupledEditContext`; the panel and scalar retain separate native identity/context checks. The writer uses the panel's public final `xqx.MRY(boolean):void`, never the numeric setter. It checks common panel context/property/undo/lock constraints plus the linked scalar's license/touch/context constraints. That linked-scalar policy is conservative toolkit policy, not a claim that native GUI code applies the identical guard.

Supply fresh `expectedKind:"boolean"`/`expectedValue` and a JSON boolean `value`. This is one panel CAS, not a two-control atomic transaction. The response adds actual `previousCoupledParameter` and `coupledParameter`, so a native range change or value coercion is visible. It reports `outcome:"applied"` with `verification:"native_readback"` on a dispatched match, or `already_matched` without a setter. Turning BIPOLAR off may clamp a negative VALUE to zero; turning it on is not a request to recover an earlier negative value. Scalar writes still reject values outside their current range.

`status` `grid.booleanPanels` (with `detail:"full"`) reports binding, inspection/write availability, operation and coupling requirements separately. No new RPC name, implicit GUI fallback, retry, rollback, Undo-group guarantee or DSP acknowledgement is introduced. Bounded coupled-control observations are not universal grouping, DSP acknowledgement or whole-project preservation; prior failed selection and audio-alignment criteria remain failures as summarized in [VERIFICATION](VERIFICATION.md#coverage-limits-and-unresolved-results).


#### Insert one catalog Grid module

`grid.modules.insert` requires `target`, `x`, `y` and exactly one of `typeId`/`typeName`, or `modules` instead of the last three. Discover the device target through `tracks.list`/`devices.list` and the canonical MODULE type UUID through `grid.catalog`; UUID hex case is accepted, but shortened UUID syntax, names, instance IDs and arbitrary resource paths are not substitutes. Coordinates are absolute native grid units, not pixels/deltas; decimal/exponent tokens, booleans, strings, nulls and out-of-int32 values reject. There is no implicit selection, default position, automatic connection or retry. `typeName` may replace `typeId`; see the batch form below.

The adapter verifies exactly one matching MODULE catalog entry, resolves its existing resource via native `TL.cfM(UUID):File`, constructs the public unnamed-package adapter, then calls `g2L.cfM(String[],ZuD)`. This normal loader can complete synchronously on a cache hit or asynchronously; parsing/conversion is not a pure read. On delivery, it requires exactly one mapped, detached, nondeleted, unowned module with the requested type and a fresh instance UUID. It rechecks the unchanged destination membership/identity/type/footprints/layout, target/owning-track/project/context, observed stopped/nonrecording/nonautomation epoch, native placement prerequisites and deadline before invoking public `IcG.cfM(Collection,int,int,false,null)`. It does not use the String convenience-placement overload or fabricate a module from catalog metadata.

The destination must contain at most127modules before loading and again before placement, so the inserted graph has at most128. Existing and incoming footprints must be positive; endpoints and prospective maximum-X plus cumulative widths must fit signed32-bit, and the entire occupied Y span must be at most65536 before native placement/layout allocation. Incoming dimensions are checked after loading the real module: a geometric rejection can therefore be an `unknown` result even though placement never ran. Do not infer that nothing changed from a message mentioning pre-allocation bounds. These limits are stricter than validating each coordinate independently. Native collection placement may reflow the whole graph rightward, including the inserted module; insertion does not inherit the move operation's occupied-anchor rejection. A later document event requires exactly one added module, unchanged survivor identities/types/footprints, unchanged Y and nondecreasing X relative to old/requested anchors. The inserted module keeps its identity/type/row but may change footprint once attached (variable-size modules such as Merge and Sum size themselves); the after layout re-checks every footprint and bound. The returned diff (or `graph:"full"`) comes from the full bounded actual membership/layout and mapped incoming connections, without parameter values; opaque children and unmapped coverage remain excluded.

Results include `outcome:"applied"`, `operation:"insert"`, `moduleId`, `typeId`, `requestedPosition`, `actualPosition` (a push right on the same row by native reflow is still `applied`; a row change is `unknown` / `readback_mismatch`), `loaderDispatched`, `placementDispatched`, `mutationDispatched`, `nativeMutation`, `nativeUndo`, `nativeLifetimeSettled:true`, `verification:"native_readback"` (a later document event observed the bounded native graph) and the topology diff above (`modulesAdded` holds the new module's row with ports). `mutationDispatched` starts at loader launch, not placement: conversion has native effects. `nativeLifetimeSettled` means the tracked native lifecycle reached healthy later-event settlement, not atomic commit, all future work drained, audio acknowledgement or persistence. The new `moduleId` and its port keys come straight from the row; parameter IDs need one `grid.get` with `moduleIds`.

The first delivered callback is claimed exactly once **before** checking the RPC deadline/future/target. Rejected placement invokes the delivered native completion's Exception overload once; accepted placement invokes its success overload only after native placement returns. The adapter uses `bTA(null)` so outward notification cannot precede native rejection cleanup, and returns normally for native captured-context pop. Native cleanup is conditional detached-object cleanup, not guaranteed full release or rollback. Duplicate delivery, early error without cleanup acknowledgement, cleanup/placement/callback failure or failed settlement poisons admission; a missing terminal callback leaves it pending. No cancellation handle or timeout-as-cancellation promise exists.

A `grid.modules.insert` that returns `unknown` / `deadline` places no hold: the native load can still land after the request returned. Read the device with `grid.export` before inserting again; never retry blindly.

Native lifetime settlement is independent of RPC completion, timeout, disconnection and extension close: a later native document event checks target/context and actual layout before releasing its reservation. It does not depend on controller scheduling or a live request deadline. A settled lifetime is not re-poisoned solely because later JSON/result delivery fails. After loader dispatch, failure/timeout/late request rejection is an `unknown` result, even when placement was rejected and native cleanup ran; inspect actual state rather than retrying.

`status` `grid.moduleInsert` (with `detail:"full"`) separates `bindingAvailable`, admission-aware `available`, and `bindingIdentity` from native acceptance. Loaded-class inspection uses `Class.forName(...,false,actualExtensionLoader)`, actual Class equality/public signatures and CodeSource equality; it constructs nothing and invokes no resolver, conversion or insertion. Its `runtimeConversionVerified:false`/`runtimeInsertionVerified:false` are inspection-scope facts, not a historical test ledger. Binding inspection does not exercise construction/conversion or insertion.

Native insertion coverage is bounded, not an all-type acceptance claim. In particular, later healthy state or musical measurements cannot authorize continued writes after an unknown outcome. Prior failed insertion criteria remain failures; see [VERIFICATION](VERIFICATION.md#coverage-limits-and-unresolved-results).

#### Shared topology lifecycle admission

Insert/move/delete/rename/connection editors share `GridTopologyQuarantine`: a String-only process marker in `System.getProperties()` (`dev.bitwigagent.grid.topology.native-lifetime.v1`), synchronized on that Properties object. It stores idle or the pending-owner UUID (one native topology lifetime at a time) and one record per quarantined Grid device (`...native-lifetime.v1.device.<trackId>/<device>`), never extension/native object references. It therefore spans ordinary extension classloader replacement in the same JVM; restarting only the extension does not clear a pending lifetime or a device quarantine. It is **not isolation from hostile replacement/removal of System properties** and is not a project revision lock or atomic native transport permission.

Pending, malformed or inaccessible marker state fails admission closed for every device. A device quarantine blocks only topology writes to that device (other devices, other domains and `project.save` keep working). `topologyAdmissionBlocked` is the process-wide block (pending lifetime, bad marker); `topologyQuarantined` is true if any device is quarantined; `topologyQuarantine` is `{state: idle|pending|quarantined, devices:[...], next}` with one entry per quarantined device: `id` (the `ack` id, `grid:<trackId>/<device>`), `origin`, `trackId`, `device` and the recorded detail (operation, moduleId, error). Two kinds: **native failure** (native exception, early error, duplicate/unexpected callback, cleanup failure, reader/binding failure; the outcome is unknown) and **settlement mismatch** (the insertion's callbacks returned normally but the later graph check disagreed: `readback_mismatch`, `target_changed`, `unsafe_state`, which can mean a pending placement list, busy undo or another Dt, or `out_of_bounds`). Both are released only by an explicit `ack` of that device's id (in `status.holds`, `topologyQuarantine.devices[].id` and the refusal's `next`: "Inspect with grid.export, then ack grid:<device>."), which re-reads the device and releases it only if it observes a consistent graph (every module mapped with a unique UUID and valid footprint, the bounded graph complete), no pending placement, idle undo and the default Dt; never by time, a later read or an automatic retry, and no Bitwig restart is needed. A release returns `{outcome:"applied", recorded?, found:{moduleCount, modulesBefore?, connectionCount, module?}, next, target}`; an inconsistent graph is the error `readback_mismatch` and the hold stays; an id that is not held, a pending lifetime, a hold rewritten while it was checked or an unobserved device is `unknown_hold`. While a native lifetime is pending, topology writes are refused `busy`; on a held device, `unresolved`. A late callback after a timeout is rejected, cleaned and settles by itself (pending until then). Normal insertion settlement releases only its matching owner; ordinary synchronous topology invocations reserve/release around native invocation and poison on synchronous failure. Prelaunch rejection releases its reservation. Reads and scalar writes remain independently gated. A missing settlement (the pending lifetime never ends) still requires a full Bitwig JVM restart; a restart does not prove rollback or cancel work already dispatched. Save the project first (`project.save`) if a restart is unavoidable. Later unrelated native failures are not globally detected.

**typeName and batch.** `typeName` resolves against the native catalog before anything loads: exactly one MODULE entry must match (exact string, then case-insensitive exact, then normalized name; first step with a hit decides); zero or several are refused as `invalid_params` listing candidates (matching names, else nearest names; ambiguous entries with their `typeId`s). `modules` (one device, no count cap beyond the 1024-module device total) first resolves every type, checks catalog membership, destination count plus the batch (at most 1024) and int32/y-span limits of the requested anchors; any failure is an error naming each failing entry and inserts nothing (module footprints are only known after loading, so a footprint-dependent rejection happens after that entry's loader dispatch: that entry is then `unknown`, like a single insert, and a clean pre-placement rejection releases the topology quarantine). Entries then run in order through the ordinary single-insert path, each settling before the next starts (a later insert can push earlier modules right, so give anchors with that in mind), and stop at the first entry that is not `applied`, or when the time left is below max(1.5 s, 2 x the slowest entry so far): that first un-run entry is `not_applied` / `deadline`, the rest `not_applied` / `not_reached`, and the batch `not_applied`. The result is `{outcome (worst entry), written, modules:[{typeId, requestedPosition, outcome, reason?, message?, moduleId?, actualPosition?}], slowestEntryMs, mutationDispatched, nativeMutation, nativeUndo, verification, …}` plus one topology diff for the whole batch (none when a dispatched entry failed: the last observed graph is not current). `actualPosition` is refreshed from the final graph, so it agrees with the diff and is a valid `expectedX`/`expectedY` for a follow-up move. An entry that failed after its loader dispatch is `unknown`: the topology quarantine applies as for a single insert and nothing is retried. If nothing was written and nothing is unknown, the call is an error instead.

#### Topology write results

Insert, move, delete, rename and connection writes share one result shape. The server captures the bounded graph (no parameters) before and after the edit and returns, by default, the **diff**; `graph:"full"` returns the whole bounded after-graph instead (rows omit native `modelClass`/`path`). Diff fields are absent when empty:

| Field | Meaning |
|---|---|
| `modulesAdded` | Full rows (`instanceId`, `typeId`, `name`, `customName`, `x`, `y`, `width`, `height`, `inputs`, `outputs`) for new modules; ports are included so an inserted module can be wired without another `grid.get` |
| `modulesRemoved` | `{moduleId, typeId, name}` |

The operation fields (`operation`, `moduleId`, positions, names, `previousSource`/`actualSource`, `mutationDispatched`, `nativeMutation`, `nativeUndo`, `verification`, the insert lifecycle flags) and the explicit `target` identity are unchanged. Constant disclosures no longer repeat in every result and apply to all of them: `nativeUndoScope` (native undo-aware operation, grouping/commit unverified), `undoGroupingVerified:false`, `engineAcknowledgement:false`, `safetyScope` (observed stopped/nonrecording/nonautomation, not atomic transport exclusion), `contextScope` (same project root/default transaction/idle undo/lock-owner observations, not atomic permission), `graphScope`/`projectScope` (the bounded graph holds modules, ports and same-graph sources, not DSP, opaque nested children or project-wide routing), `observationScope` (an ordinary later event after normal end-event drain, not universal cleanup) and the maxima (1024 modules, occupied Y span 65536).

#### Move or selectively delete a Grid module

Discover a fresh `instanceId` and native `x`/`y` with `grid.get`; retain the same device `target`. For `grid.modules.move`, supply those positions as `expectedX`/`expectedY`, and absolute destination `x`/`y`. All four must be signed32-bit JSON integer tokens: decimals, exponent tokens, booleans, strings and nulls reject, without coercion or clipping. CAS is checked before a same-position no-op. Missing IDs reject `target_not_found`, including repeated deletion; neither operation accepts implicit selection or catalog type IDs.

Movement passes one actual singleton List and `copy=false` to the native absolute-anchor operation. An anchor anywhere inside another module's half-open footprint rejects before dispatch; a new rectangle overlapping another module while its anchor is outside that footprint can trigger **native whole-graph rightward reflow**. Unselected modules may move, and the selected module's actual X can differ from the requested X. This toolkit does not implement another layout algorithm. Deletion uses the native selective List operation, including bypass/reconnection and full-graph cleanup; it is not simply removing incident cables and is never clear-all.

Both editors require complete bounded module membership (maximum 1024), positive native dimensions, checked int32 endpoints/translation/cumulative horizontal bounds and occupied vertical span at most65536. They independently recheck stopped/nonrecording/nonautomation observations and safety epochs, live device/graph ownership, every participating module's attachment/project/lifecycle, initialized context/root/default transaction, idle undo observations, device-lock owner, graph native veto and project closing/saving flags. Parameter-specific license/settable/touch rules are not transplanted. These observations do not establish global transaction idleness, a revision lock or atomic permission.

Native callbacks cannot finish the RPC before native close. After native return, a later actual document event re-resolves the target, checks all survivors and serializes their full bounded layout and mapped incoming connections. Move observations must preserve every unselected Y, selected requested Y, and X at least the original/requested baseline; incompatible results are unknown, not successful reflow. The returned diff (or `graph:"full"`) omits parameter values and retains explicit opaque-child/coverage limits.

Results expose `operation`, `moduleId`, `previousPosition`, `mutationDispatched`, `nativeMutation`, `nativeUndo` and `verification` (`native_readback` when something was written), plus the topology diff. All carry `outcome`: `applied` when something was written, else `already_matched` (delete: `applied`). Move adds `requestedPosition` and `actualPosition` (a push right on the same row by native reflow is still `applied`; a row change or a leftward move is an `unknown` result, `readback_mismatch`); delete adds `removedModuleId` and `removed:true`. Native undo-aware dispatch is not proof of one-call/one-Undo grouping, commit, DSP or persistence.

Unexpected synchronous native invocation/callback failure quarantines the shared insert/move/delete/rename/connection editors through the process guard described above; reads and scalar writing remain independently gated. The translated failure retains its actual cause chain; it is not rollback evidence. Preflight rejection does not quarantine. The failed device is quarantined, not the process: inspect `topologyQuarantine.devices` and the actual state, then `ack` it; ordinary extension classloader replacement is not a reset. Native failure, timeout, late context/safety/verification or serialization failure after dispatch returns `unknown`, never an automatic retry/rollback. `moduleMove`/`moduleDelete` report independent availability and limits.

Native move/delete coverage does not establish sample/null equivalence, disabled Note Grid DSP, general Undo grouping, race safety or injected-failure behavior. An original relative-envelope criterion failed six of 48 near-silent windows; a later absolute-error description is not retroactive passage. See [coverage limits](VERIFICATION.md#coverage-limits-and-unresolved-results).

#### Rename one current Grid module

`grid.modules.set` requires exactly the device `target`, a canonical current `moduleId`, and both `expectedCustomName` and `customName`. Copy `moduleId` from `grid.get.instanceId` and the expected raw string from that row's `customName`. Effective `name`, catalog `typeName`, type UUID, local key, path, position and GUI selection are not substitutes. No batch or selected-module fallback is provided.

Both name fields are strict JSON strings of at most1024UTF-16 code units; empty and whitespace-only strings are allowed and preserved. There is no trimming, stringification, truncation or special treatment of `"false"`/`"null"`. Null, omitted values and other JSON types reject `invalid_params` before enqueue. Empty `customName` resets the native override; its effective fallback is independently read, not filled from the catalog. Raw CAS rejects `target_changed` even for an otherwise matching no-op.

`moduleRename` has an independent availability gate requiring the exact declared public-final `com.bitwig.flt.document.core.master.device.Dgc.iHb(String):void` inherited by a real native `rSf`, raw/effective-name readers, actual owning device/track and shared topology context. Unrelated parameter/display/catalog/footprint bindings do not authorize or disable this name setter. At most128actual mapped modules are admitted; native names are bounded too. No move-only occupied-span limit, fake Grid owner, scalar setter, protected UI property or copied UI outer transaction is used.

The writer revalidates the requested current UUID/object membership, complete bounded member identities, native owning target and project/root/default-Dt/idle-Undo/lock-owner observations before dispatch and on a later document event. Controller delivery also rechecks explicit target epochs and stopped/nonrecording/nonautomation safety. These observations are not native atomic permission, a revision lock, DSP acknowledgement or detection of invisible same-name device replacement.

A changed request dispatches exactly one native setter; an authorized no-op dispatches none but still performs context, CAS and later observation. Success returns `outcome` (`applied`, or `already_matched` for a no-op), `operation:"rename"`, `moduleId`, `previousCustomName`, `requestedCustomName`, `actualCustomName`, `previousName`, `actualName` and the topology diff (or `graph:"full"`, without parameters). The first three name fields describe raw override semantics; effective before/after names are reported separately. A changed name carries `verification:"native_readback"`; a no-op carries none. Read `mutationDispatched`, `nativeMutation` and `nativeUndo`; the constant scope disclosures are listed under topology write results.

Native property bookkeeping is undo-aware, but one-call/one-Undo grouping, equivalence to the UI's outer transaction, commit, rollback, persistence and unchanged audio are not inferred from setter return. Native invocation failure poisons the shared topology guard; unknown outcomes do not permit a blind retry. Current UUIDs must be reacquired after reopening. Controlled-source naming audio acceptance remains unproved; bounded persistence observations do not repair missing baseline controls. See [coverage limits](VERIFICATION.md#coverage-limits-and-unresolved-results).

#### Connect, replace or disconnect one Grid input

Use `grid.get` to discover the fresh destination module `instanceId` and exact input `key`. Supply them as `targetModuleId` and `targetPortKey`, together with the same device `target`. Both `expectedSource` and `source` are **required**, including explicit JSON `null`: null means disconnected, not omitted/default. A nonnull endpoint has exactly `moduleId` (fresh canonical UUID) and `portKey` (exact output key). Keys are case-sensitive, untrimmed strings of at most1024 UTF-16 units; empty syntax is allowed but must resolve to an actual port. Unknown fields, wrong directions and missing endpoints reject.

`expectedSource` must match the input's current source before even a no-op. Set `source:null` to disconnect; supply an output endpoint to connect or replace. Endpoints must be exact members of the bounded same graph, not just objects with matching owner/key. No implicit selection, cross-graph cable, automatic retry or compensation is provided. Reacquire IDs and current state after reopening or any uncertain outcome.

The native route is public final `device.cXR.cfM(led)`, preserving the native undo-aware wrapper rather than bypassing it through a typed setter. Runtime destination class must be exactly `device.Wkj` and ancestor undo manager exactly `master.tj2`; unreviewed subclasses reject. `connectionWrite.available` reports binding/quarantine availability, **not per-target permission**. The writer rechecks all bounded modules/ports, ownership, lifecycle, project/context/default transaction, idle undo observations, device-lock owner and observed stopped/nonrecording/nonautomation epoch. Maximum 1024 modules and port/item bounds apply; move-only footprint/Y-span limits do not apply to cables.

Native repair can disconnect the requested source, alter other inputs or change project routing. Results report `outcome`, `previousSource`, `requestedSource`, `actualSource`, `mutationDispatched` and the topology diff (or `graph:"full"` without scalar values). A native repair mismatch (`actualSource` differs from `requestedSource`) is `unknown` / `readback_mismatch`, a real observed result, not silently retried or relabeled success. Compare `connectionsChanged`, which lists every changed input in the graph, not only the requested one. A written change carries `verification:"native_readback"`, which observes an ordinary later event after normal end-event drain, not universal cleanup/future-work completion, DSP acknowledgement or verified Undo grouping. The bounded graph does not certify project-wide routing preservation.

Synchronous native setter/listener/close failure triggers the shared topology quarantine. Later asynchronous native failures are not globally detected; absence of quarantine is not proof of global host health. Unknown results require inspection, not a reset/retry.

Full MIDI preservation failed in a native connection case: a sentinel note was observed at beat 1 initially versus beat 2 finally under the same 1/8-beat grid. Native mutation versus unacknowledged-window observation remains unresolved. Later first-read corrections do not retroactively pass this criterion. Rejected-cycle repair and Note Grid DSP remain unexercised; there is no generalized grouping, atomicity or project-wide-routing guarantee. Selection/sends remain partial. See [coverage limits](VERIFICATION.md#coverage-limits-and-unresolved-results).

### Architecture and evidence boundary

`HostBridge` validates, routes and wires the small host services (`Scheduler`, `TrackWindow`, `ProjectState`, `TransportSafety`, `SelectionLease`, `NativeRuntime`, `Holds`) into each module. `DeviceSources` owns fixed root/layer/child addresses and continuity; one `ParameterModule` owns continuous source-specific parameter data and the shared binding/request. Other domain modules retain their own observations. Grid separates RPC/target guards, the exact-version reflective adapter, bounded model serialization, scalar/panel/topology writers and shared lifecycle admission. The boolean-panel writer reuses parameter context/serialization while retaining its distinct setter and coupled scalar checks. Insertion adds a narrow public boundary and lazy unnamed-package loader subclass, not another transport or transaction layer. Python separates strict schemas, one catalog, transport, CLI and MCP. No project mirror, planner, workflow DSL, automatic GUI fallback, implicit retry or generic transaction layer is introduced.

`ModulatorModule` separately owns root-device read RPCs and bounded serialization through `BoundedJson`; `ModulatorSnapshotReader` owns nonloading primary/direct inventory and exact-value guards. `DeviceSources` supplies the existing root authority and an invalidatable root-read ticket: controller capture/final delivery recheck public observations, while native callbacks use the published epoch/deadline without Controller API getters. Results cross queues as immutable bounded JSON, not native references. This does not change layer cold-index/discontinuity rules or public direct-parameter bindings.

`NativeHost` is lazy/shared through `NativeRuntime`, centralizing exact version, loaded CodeSource/hash/ClassLoader, descriptor checks and document dispatch while keeping domain errors and bindings independent. `DeviceSources.Native`/`NativeDeviceTargetAccess` share native target/track-alias/UUID corroboration; `NativeReadContext`/`NativeReadContextAccess` share lifecycle and owning-context checks. Initialization, root equality and default Dt remain observations rather than new read gates. `NativeStringPanelAccess` is the shared exact native string-panel reader; Grid additionally uses its separately bound `btw.hUR(String)` write operation, which modulator reads do not. Grid retains its own edit-context, writers, quarantine and asynchronous cleanup; modulator reads do not couple to those write paths.

Offline client tests, simulated-host Java tests, transported MCP fixtures, native read-only preflight and independent musical/UI/persistence E2E are different evidence layers. Passing one does not promote another to passed. Native preflight verifies exact loopback socket ownership (including Linux IPv4-mapped TCP6 entries); project-name equality alone cannot establish which full project path is loaded.

### Launcher clips: timing, Next Action and the scene window

A launcher clip is addressed by a clip ref `{kind:"clip", track, slot:{scene}, name}` that `launcher.list`, `context.get` and every clip write return. The scene and the clip name are compared on every call: a scene renamed since the read, or another clip name in the slot, is `stale`/`target_changed` with `current` (the clip ref found there); an empty slot or a scene past the count is `stale`/`target_not_found`. An unnamed scene has `name:null` and so no rename protection: name the scenes you address repeatedly. Holds (`launcher.mutation`) are keyed by track and absolute scene.

**Scene window.** The launcher exposes 16 scenes at a time; there is no scene limit. Every operation that addresses a slot or scene holds the `SceneWindowLease` while it scrolls the window to its scene, settles, dispatches and verifies. Operations at the same window position share it; a write facing a window another operation holds is `pending`/`busy` (nothing changed), while `scenes.list`, `launcher.list` and `context.get` wait for the lease until their deadline. A copy within 16 scenes of its source holds the window that shows both.

`clips.get` reads timing and Next Action settings of one launcher clip without selecting a clip or moving the editor cursor; `clips.set` writes them. They require the same inspected Bitwig 6.1.4 binary/hash as the existing private bindings; another version fails closed. A matching name is a guard, not a persistent clip UUID.

`clips.set` Next Action fields: `nextAction` (`play_next` or `stop`), `nextActionEnabled`, `nextActionLinkToLoop`, `nextActionLoopCount` (1..64), and `nextActionDelay`. Times are quarter-note beats. For one complete clip loop followed by the next clip, use `nextAction=play_next`, enabled=true, linkToLoop=true, loopCount=1. Use `stop` on the last clip. Clips in a scene must have matching timing for synchronized transitions; this API does not configure every track automatically.

`clips.set` also takes `launchQuantization`, `launchMode` (each one of the ids the host lists through `EnumValue.enumDefinition()`, returned as `options` in the result; an unlisted id is `invalid_params` before the clip is selected) and `useLoopStartAsQuantizationReference`. These are public `Clip` properties, so unlike the Next Action fields this path binds the launcher cursor clip (it **selects the clip** and takes the selection lease), and needs observed stopped transport with recording and automation write off. `name`, `color` and `loop:{length}` use the same cursor binding. Fields of the three paths may be mixed in one call: they run in the order Next Action, launch fields, then name/color/loop, and the first field that does not succeed stops the rest (`not_applied`/`not_reached`). Only fields that differ from the readback are written (`already_matched` otherwise); a written launch field is `applied` only when its value callback fired after the write and the readback matches, else `unknown` with `not_observed`/`readback_mismatch`; each field reports its own outcome under `fields`. The idempotent setters do not hold. `loop:{length}` sets the loop length and then the play stop (`loopStart + length`); `color` is `"#rrggbb"` read back within half an 8-bit step (the host may snap to its palette: `unknown`/`readback_mismatch`).

`clips.delete` and `clips.copy` use the slot proxies and do not select; delete reads back the slot empty, copy the target slot's content transition and equal name (`nameChanged:{from,to}` if the host renamed the copy). `clips.transpose` shifts every channel-0 onset cell with velocity and duration kept; `clips.quantize` keeps channel-0 onset count, pitch multiset and loop length while at least one cell moves (positions inside a grid cell are not observable, so a clip already on grid reads as unobserved); `clips.transform` with `op:"doubleContent"` doubles the loop with the original first half unchanged; all three select the clip as the cursor clip, bind it like `notes.*`, and read the whole loop in one 1/32–1/16 window, so need a loop of at most 32 beats with channel-0 notes for transpose/quantize (`unverifiable_clip`/`no_notes`, nothing changed). Unobserved `delete`, `copy`, `transpose`, `quantize` below amount 1 and `doubleContent` are `unknown` and place the same per-slot hold as create/import (the target slot for a copy): later writes on it are refused `unresolved` until `ack`. `quantize` with `amount` 1 snaps to the host grid and is idempotent: no visible cell movement is `unknown`/`not_observed` without a hold. `clips.transform` over several targets is a batch: every ref and slot is checked before any write, then each target is written in order and the first entry that is not `applied`/`already_matched`/`sent` stops the rest.

Writes of Next Action fields require stopped transport with recording and both automation-write modes disabled. Native slot/clip/owning-track identity, attached project/context, model thread and deadline are checked before and after access. Each supplied field reports exact native post-write readback, and omitted settings are checked for unexpected coupling. A write is not an atomic multi-property transaction; partial failure is `unknown`, with settings and editor writes blocked by the shared launcher admission guards. Read-only inspection remains available. Do not retry unknown writes or treat a reload as evidence of recovery.

Timing (`playStart`, `playStop`, `loop.start`) and `loopEnabled` are read-only. An attempted native play-stop write was not observed during E2E validation; timing writes are therefore rejected before dispatch.

The settings adapter uses pinned model methods for Next Action and the same native timing properties as Bitwig's public Clip proxy. Returned values do not establish playback, Undo grouping, persistence, source-audio tempo/stretch behavior, or aesthetic acceptance. Audio-event source tempo remains a separate interface.

Native validation on Bitwig 6.1.4 (before the ref reshaping): all 56 clips in a seven-scene project returned matching timing and Next Action settings. Reversible enabled false/true, action stop/play_next and loop-count 2/1 writes were independently read back. Link-to-loop and delay writes are descriptor-checked but have not yet received native mutation E2E coverage. Scrolling the scene window past scene 15 has only simulated-host evidence until the P2-L native checklist is run.

### Scenes

`scenes.list`, `scenes.insert`, `scenes.set`, `scenes.launch`, `scenes.duplicate` and `scenes.delete` address a scene by a scene ref `{kind:"scene", index, name}` (zero-based absolute `index`; `name` is `null` for an unnamed scene and is compared on every call, so a rename since the read is `stale`/`target_changed` with `current`). Bitwig labels an unnamed scene by its position ("Scene N"), which shifts when scenes are inserted or deleted; the ref reports such a scene as unnamed, so `duplicate`/`delete` verification relies on the count, the clip count of the copy and explicitly named neighbours inside the held scene window. They use the public `SceneBank`/`Scene` proxies and do not select or move the cursor. Structure edits (`duplicate`, `delete`) wait for a settled project like `scenes.insert` and are refused (`busy`/`unresolved`) while a launcher cursor operation is pending or any launcher mutation is unresolved, because they shift the slot rows those holds are keyed on. No scene operation retries: `unknown` means re-read `scenes.list` before anything else.

#### Grid usability additions

- **Catalog.** The native module catalog entry carries only id, name, kind and a resource path (`modules/<name>.bwmodule`); there is no category, tag or description, so `grid.catalog` `query` matches names only (`Low-pass`, not `Filter`). Nothing is invented on top.
- **Parameter display.** A `grid.parameters.set` single result's `parameter.display` and each batch entry's `display` is the native display string read back after the write (the same source as `grid.get`), e.g. `"2.09 kHz"`; omitted when the parameter has no observable display (boolean panels). Raw values remain the native domain; pitch-unit parameters are MIDI-note valued (Low-pass `CUTOFF` raw 84 displays `"1.05 kHz"`, 96 `"2.09 kHz"`).
- **Display writes.** A `grid.parameters.set` entry (single or batch) may carry `display` instead of `value`, with `expectedKind:"float"` and the usual `expectedKind`/`expectedValue` CAS. Exactly one of `value`/`display`. The text is a number plus an explicit unit suffix; conversion exists only for the float `numericUnit` tokens below, kept in one table (`GridDisplayUnits`). Any other unit is refused as `unsupported_unit`.

  | `numericUnit` | Suffix | raw | Evidence |
  |---|---|---|---|
  | `hertz` | `Hz`, `kHz` | MIDI note: `raw = 69 + 12*log2(f/440)` | host rows (84 -> 1.05 kHz, 96 -> 2.09 kHz) and the native converter's `440*2^((x-69)/12)` |
  | `percent` | `%` | `raw = percent/100` | 17 recorded raw/display pairs over ranges -1..1, 0..1, 0..2 |
  | `decibel` | `dB` | `raw = dB` | one recorded pair (-96 -> `-96.0 dB`) and the native converter's `20*log10` over dB-valued raw |

  The token alone does not fix the scale (Detune has token `hertz` but a linear Hz raw; `seconds` rows follow differing power curves; `semitones_relative`/`module_semitones` have only zero pairs and stay unsupported). So the host first requires the row's current raw value to reproduce its current display under the table's model to the shown precision, else `unsupported_unit`; a current display of zero cannot confirm a scale and also rejects. The write is then the ordinary raw CAS with the converted raw value (range checked, no clamping). After the write the new display is compared with the requested text to the precision shown: the result carries `requestedDisplay` and `displayMismatch` (single result and each batch entry). A mismatch is only reported; nothing is written again.
- **Connection batch.** `connections:[{targetModuleId,targetPortKey,expectedSource,source}]` (1..32, distinct targets) on one device. Every `expectedSource`, port membership and runtime support is checked against the live graph first; any failure is an error that writes nothing, naming each failing entry. Entries then run in order through the ordinary single-input path (each its own later-event observation) and stop at the first entry that is not `applied`/`already_matched`; later entries are `not_applied` / `not_reached`. A native repair that left a different source is `unknown` / `readback_mismatch` and stops the batch, but the graph was observed, so the diff is kept. The result is `{outcome (worst entry), written, connections:[{targetModuleId, targetPortKey, outcome, reason?, message?, previousSource?, actualSource?}]}` plus one topology diff for the whole batch. A failure after an entry's native dispatch is `unknown`: the shared topology quarantine applies as for a single edit, no diff is returned (the last observed graph is not current), and nothing is retried. A failure before the first dispatch is an ordinary error.

#### `grid.describe`: module documentation (client-side)

Not a host method and needs no running Bitwig: it reads `<installationRoot>/resources/localization/{Module-descriptions,Modules,Categories}-resources[_lang].properties` from the local install (never copied into this package). Args: exactly one of `type` (module display name, loose spelling, or typeId) or `query` (keywords; ranked by name, keywords and description; `limit` 1..50, default 10); `lang` en|de|es|fr|ja|ko|zh (default en; missing keys fall back to English); `installationRoot` (else `$BITWIG_INSTALLATION_ROOT`, the install holding `$BITWIG_API_JAR`, then `/opt/bitwig-studio`).

`type` returns `{name, typeId, resourceId, description, keywords, category, categoryDescription, ports:[{key,name,direction,description?}], parameters:[{id,name,description?}], rawEntries, revisions?}` for the bundled schema of the connected host. Modules map to resource ids by normalized name (plus a small override table); port and parameter notes are matched best-effort by key/name, so a missing `description` does not mean the item is undocumented: check `rawEntries` (all resource entries under the module's prefix). A module with no resource entry has `resourceId: null`. Missing resources fail with `invalid_params` naming `installationRoot`.

#### `grid.apply`: declarative patch (client-side)

Not a host method: the Python client (MCP tool and `bitwig-agent grid apply`) composes the guarded Grid calls above; the extension is unchanged. Spec: `target` (as `G`), `modules:[{name, type|typeId, x, y, params?}]`, `connections:[{from:"module.OUT", to:"module.IN"}]` (split on the last `.`; endpoints must be declared modules; one source per input), optional `namespace`, `prune`, `pruneAll`, `dryRun`. A module's identity is its unique non-empty `customName`. **Partial mode:** a module entry without `type` or `typeId` is `{name, params}` only and sets those params on the live module of that name (value forms as below, validated against that module's live type before any write); it never inserts, moves or retypes. `x`, `y` and `replace` on such an entry, and `prune`, `pruneAll` or `replace` anywhere in a spec that has one, are `invalid_params`; a name that is not in the device is `invalid_params` with the nearest names. Example: `modules:[{name:"F: lp", params:{CUTOFF:{display:"800 Hz"}}}]`.

Blocks: `blocks:{name:{params?:{p:default}, modules, connections?}}` and `instances:[{block, prefix?, dx?, dy?, args?}]` are expanded client-side before any validation (no nesting). Inside a block module names and connection endpoints are local; an instance's module is named `prefix+local`, its x/y shifted by `dx`/`dy`, and a params value that is exactly `"${p}"` (also inside `{display}`/`{label}`) is replaced by the instance's `args.p` or the block default, keeping its JSON type. Top-level `connections` reach instance modules by expanded name (`"D1: osc.OUT"`). Every check below (unique names and cable targets, types, ports, footprints, display units) runs on the expanded spec; `dryRun` plans it, and the result adds `instances:[{block, prefix, modules:[names]}]`. `modules` may be omitted when instances supply them.

`{display}` seconds writes: for the (type, parameter) pairs in `SECONDS_PARAMS` (`grid/display.py`: AD/AR/ADSR/Pluck/Comb envelopes and Delay/Mod Delay/Freq Shift+ with raw = cbrt(seconds); Logic Delay, Gate Length, Gate Repeat, Lag, Average, Curves, Segments, Slope, Follower(RF), Velo Mult, CV Out, Sampler GRAIN_SIZE, Ø Lag with raw = log10(seconds); each row carries its schema default raw/display pair as evidence, re-checked by a test) the client converts `"3 ms"`/`"0.5 s"` to a raw value (suffix `ms`/`s`, range-checked against min/max) and writes that raw value; the skip compare uses the live display's precision. Other seconds parameters (All-pass Delay TIME, Audio Out HOLD_TIME, Long Delay TIME: default pair fits neither mapping unambiguously) reject display writes offline.

Order: validate whole spec (types, port keys, parameter ids/kinds/ranges/enum labels, footprint overlaps against the schema sizes and untouched modules, `{display}` writes the host would refuse: only hertz/percent/decibel (plus the seconds table below), nonzero default display; nothing written on failure, did-you-mean in `details.problems`) and read the graph (null `customName` fails closed); delete (prune); move existing modules to x/y in a collision-free order (vacate first, cycles parked at a free anchor; bounded); batch insert by `typeId` (16), renaming each batch's applied entries immediately (so a partial batch never leaves unnamed modules; after `unknown` they are listed in `unnamedModules`); re-read and move only what native reflow displaced; re-read parameters, batch `grid.parameters.set` (64, CAS from the fresh row; equal values skipped; `{label}` maps to the option value; `{display}` skips when the live display already shows it at its own precision); re-read, batch `grid.connections.set` (32, `expectedSource` from the fresh read). Existing modules are reused (type mismatch or duplicate name rejects before any write); unlisted inputs are left alone unless `prune`, which also disconnects them and deletes modules whose `customName` starts with `namespace` but are absent from the spec (never unnamed or out-of-namespace ones). String parameters (e.g. Comment `TEXT`; at most 1024 UTF-16 units, multi-line ok) are written with `expectedKind:"string"` and the live text as CAS; equal text is skipped. Step arrays (Steps, Pitches, Gates, Probabilities, Accents) are written as `"params":{"DATA":{"steps":[1,0,0.5]}}` (or `{"steps":"${row}"}` in a block with a list arg); the parameter id is the live row's `kind:"steps"` id (the bundled schema has none, so only the module type, finiteness, 1..256 entries and -128..128 are checked offline; `arrayLength` is checked against the live row, before any write for existing modules). The grid.get reads use `full:true`; the requested entries are compared with the live prefix of the same length after float32 rounding, equal arrays are skipped, otherwise one `expectedKind:"steps"` write with `expectedValues` = that live prefix (entries beyond the list stay unchanged). Top-level `voicing:{voices, voiceStacking, monoMode, ...}` (any `grid.voicing.set` fields) converges Poly Grid voicing: `grid.voicing.get` runs right after offline validation (also for `dryRun`), a device without voicing (Note/FX Grid) fails `invalid_params` before any write, and only differing fields are written (first phase, `expected` = their live values; equal voicing is `alreadyMatched.voicingFields`). `modules:[]` is allowed only with `prune:true` and a non-empty `namespace` and deletes every namespace module. A name that exists with another type is refused unless `replace:true` (spec-level default or per module): the old module is deleted, the new type inserted under the same name and wired per spec; replace drops undeclared cables on that module (listed in `plan.droppedConnections` and a warning). Use a delimited `namespace` such as `"H: "`: matching is by prefix, so `"H"` would also delete `Hello`. The result carries `notes` (measured behaviour for the module types used, from the connected host's `data/grid_notes_<version>.json`, value-free) and `warnings` (e.g. oscillator `PITCH_IN` connected while `PITCH_MOD` is 0). Validation is offline against the bundled schema of the connected host (`status` `grid.hostVersion` (with `detail:"full"`)); unsupported versions use live `grid.catalog` and check ports/parameters after insertion.

Warnings (also in `dryRun`, rules in `grid_notes_<version>.json`): PITCH_IN with PITCH_MOD 0; a phase cable into a step module with `DEVICE_PHASE` on; filter `KEYTRACK` > 0 in a Poly Grid; modules with no connections (Note In excepted); oscillators/envelopes whose outputs are all unused; a raw oscillator `DETUNE` write below 0.5 in magnitude (the scale is raw = cbrt(Hz), range +-3, so raw 0.25 is 0.02 Hz, effectively no detune; `{display:"1.5 Hz"}` converts and does not warn). `dryRun` stays read-only and adds `wouldFail:[{reason,message}]` for what a real apply would certainly be refused for: transport state (`unsafe_state`: recording or automation write on, or playing when the spec inserts, deletes, renames, moves or rewires; a spec that only writes parameter values, step arrays, voicing or partial entries may play), an unreadable target (then `plan` is empty). `{display}` writes the host converts itself and may refuse (`unsupported_unit`) are a warning, not a `wouldFail`; filter `CUTOFF` Hz/kHz is converted client-side (raw = MIDI note). A real apply returns `diagnosticsMarker` taken right after the build (pass it as `diagnostics.get` `sinceMarker`). Unknown parameter/port errors list the valid ids and near or case-insensitive matches; overlap errors name the blocker as `'customName' (Type@x,y)`.

The first non-success step (host error, `not_applied`, `unknown`) stops the run with no retry. Result: `{outcome, applied:{inserted,renamed,moved,paramsWritten,connections,disconnected,deleted}, alreadyMatched:{modules,positions,params,connections}, steps, moduleIds, params?, warnings?}` (`params` maps `"module name.PARAMETER"` to the display the host read back after each written parameter), where `outcome` is `applied` if anything was written, else `already_matched`; when stopped it is the stop's outcome (`not_applied` or `unknown`) with `reason`, `failure:{phase,method,response}` (method is an agent-callable method such as grid.export, or the step name when a hidden building block failed; response is the raw host response), `notReached` (phases not started and what was left undone) and `next`. `dryRun` returns `dryRun:true` (no `outcome`), `planned` counts and `plan` (moves of inserted modules are decided after insertion). Re-applying a spec converges: reused work costs reads only. `pruneAll:true` (mutually exclusive with `namespace`/`allowOutsideDisconnect`; implies `prune` and `replace`; `modules:[]` allowed) manages the whole device for generator specs whose modules span many prefixes: every live module the spec does not declare (unnamed ones included, `external` excepted) is deleted, a same-named module of another type is replaced, and every undeclared input of a declared module is disconnected. Deletes run before moves and inserts, so freed footprints are reusable; all of it is in the `dryRun` plan (`deletes`, `replaces`, `connections`) and in `warnings` (`pruneAll: deleting/replacing/disconnecting ...`). It is destructive: run `dryRun` first. Use ONE spec per Grid device (sections as namespaces inside it, so cross-section cables are expressible); two specs sharing a namespace with `prune` delete each other's modules.

#### `grid.export`: read a live patch by names (client-side)

Not a host method: it pages the Grid read (all pages, `not_ready` rather than a partial read; params pages of 64) and joins UUIDs to names. Read-only: it writes no file, so a pipe or the structured result is the way to keep it. Args: `G`, optional `namespace` (customName prefix), `includeParams` (`changed` default / `none` / `all`; `changed` = differing from the bundled 6.1.4 defaults).

It returns `{spec, refs, sizes, moduleCount, connectionCount, includeParams, unnamed?, warnings?}` (no `outcome`: nothing is written). `spec` is a `grid.apply` spec for the device: `target` (the device ref), `modules:[{name, type, x, y, params?}]` (raw values; enum as `{label}`; strings; step arrays as `{steps}`), `connections:[{from:"name.OUT", to:"name.IN"}]`, `voicing` on a Poly Grid (whole device only), and with `namespace`: only that prefix, `namespace`, and `external` (outside modules the kept cables reference). The spec holds only names and the device ref, so a saved export replays after an extension restart: applying it to the same device is `already_matched`. `refs` is `{module name: gridModule ref}` (a gridModule ref plus a parameter key is the parameter ref that `devices.remote.define`, and later automation and modulation, take) and `sizes` is `{module name: [width, height]}` in Grid cells, as the host measured them; neither is part of the spec. A module without a unique `customName` is named `_<type>_<x>_<y>` and listed in `unnamed` (warning); `grid.apply` matches unnamed live modules by that name, but modules sharing a customName must be renamed first.

`grid.apply` additions: `external:["X: sum", ...]` names live modules that cables may reference without declaring them (checked after the first read, `invalid_params` if missing or not unique; type, position and params untouched, never pruned or deleted). `prune` only disconnects unlisted inputs of declared modules inside `namespace`; inputs of declared modules outside it are kept and named in a warning (`X: sum.IN2 (from H: add.OUT)`) unless `allowOutsideDisconnect:true`, which cuts them and lists them in the warning and in `plan.connections`. (Without `namespace` every declared module is in scope, as before.)

#### `grid.render`: layout image (client-side)

Not a host method: the Python client (MCP tool and `bitwig-agent grid render`) pages the Grid read (structure only, 128 per page, until `window.total` is reached; `not_ready` rather than a partial drawing) and fetches parameters only for Comment modules (their `TEXT`). Read-only toward Bitwig; the only side effect is the file at `outPath`. Args: `G`, `outPath` (absolute normalized; `target_exists` unless `overwrite:true`), `fileType` `svg` (default) or `png` (via `rsvg-convert`, else `magick`; otherwise `invalid_params`), `namespace` (customName prefix highlighted, others dimmed), `showConnections` (default true), `scale` (0.25..4). Modules are drawn at grid x/y with their width/height, coloured by category (one table in `grid_render.py`: sequencing, random, pitch, oscillator, envelope, filter, fx, output, visualization, text, other), titled by `customName` (else type) with the type below, Label modules as headers, Comment modules with their text, cables from output to input side.

The written file is read back (its size and the SVG or PNG header): `outcome:"applied"` with `verification:"file_readback"`, else `unknown`/`readback_mismatch`. Result: `{outcome, verification?, outPath, fileType, bytes, imageSize, moduleCount, connectionCount, boundingBox:{x,y,width,height}, categories, overlapCount, overlaps:[[a,b]...] (footprint pairs, max 50), unconnectedCount, unconnected (max 50; Label/Comment excluded), sections:[{prefix,moduleCount,boundingBox}] (from `"P: "` name prefixes), density (occupied cells / bbox cells), namespace?}`.

#### `audio.route`, `audio.capture`, `audio.analyze` (client-side, no host call)

Verify what Bitwig outputs without hearing it. Linux/PipeWire only for route/capture (error `unsupported_platform` elsewhere or without `pw-link`/`pactl`/`pw-record`); all subprocesses use explicit argument lists and a 5 s timeout. Errors use the usual `{code,reason,message,next?}` envelope. `audio.route` `silent`/`restore` read the PipeWire links back after writing and return `applied` (`already_matched` when a route changed nothing) with `verification:"system_readback"`, or `unknown`/`readback_mismatch` when the links read back are not the requested ones; `audio.capture` returns `applied`; `status` mode and `audio.analyze` carry no outcome. A `pw-link` that fails or times out after links may have changed is an unknown result (`job_failed`/`deadline`).

- `audio.route {mode: silent|restore|status}`: only the links of ports `Bitwig Studio:out1/out2` are touched. `silent` creates/reuses the null sink `bwtest`, saves the previous targets in `$XDG_CACHE_HOME/bitwig-agent/audio-route.json` (default `~/.cache`) before moving the links to `bwtest:playback_FL/FR`; `restore` re-links exactly the saved targets, drops the `bwtest` links and deletes the state file. Idempotent. `not_ready` when no output link exists. Result: `links:[{from,to}]`, `silent`.
- `audio.capture {seconds 0.5..120, outPath, overwrite?, fromStart?, allowAudible?, soloTrack?, stopOthers?}`: `outPath` is an absolute `.wav`, refused if it exists (`target_exists`) unless `overwrite:true`. Requires silent routing (`not_isolated`) unless `allowAudible:true`, which only waives that requirement. The recording always comes from Bitwig's own output ports: a dedicated `pw-record` node (unique name `bwagent-capture-<pid>-<id>`, no autoconnect, 48 kHz stereo s32) is linked from `Bitwig Studio:out1`/`out2` (checked with `pw-link -o`; `not_ready` otherwise) with `pw-link`, so other applications and the default sink monitor are never recorded. Only the links it created are removed afterwards; existing links are never changed. `fromStart` (default true): `transport.set` playing=false, position=0, start recording, playing=true, wait `seconds`, playing=false, stop `pw-record` with SIGINT. `fromStart:false` never touches the transport. `soloTrack` really solos that track: it reads every track's solo (`tracks.list` + `tracks.get`; `not_ready` when a state cannot be read, `target_not_found` for an unknown track), sets `solo` on the target and clears it on other soloed tracks (`tracks.set`; the host has no exclusive-solo write), and restores every changed state afterwards, also on failure. It still refuses (`not_isolated`) while other tracks have playing launcher clips unless `stopOthers:true` stops them first. Result: `path, durationSeconds, peak, peakDb, rms, rmsDb, clipping (peak>=0.999), silent, source:{ports,node}`, plus `soloed, previousSolo, unsoloed, restored[, restoreFailed]` with `soloTrack`.
- `audio.analyze {path, mode: level|onsets|mono_pitch|probe|loudness|bands, bpm?, skipSeconds?, method?: flux|envelope, threshold?, windowSeconds?, windowBeats?, reference?, key?, spectrogramPath?}`: offline, any platform; needs the optional `audio` extra (numpy, scipy, soundfile: `pip install 'bitwig-agent[audio]'`, Arch `python-numpy python-scipy python-soundfile`), otherwise `unsupported_platform` naming that command (`audio.capture` refuses the same way before recording, since it reports levels). `path` is an absolute `.wav` or `.flac`, decoded by libsndfile (8/16/24/32-bit PCM, float, RF64, FLAC; channel 0; a WAV header left unfinalized by `parec`/`pw-record` with data size 0 is read to the end of the file). Times are seconds from file start. `level`: `peak, rms, silenceRatio, windows[{t,peak,rms,rmsDb}]`. `windowBeats` (1/16..64, `level` and `bands`, needs `bpm`, not with `windowSeconds`) sets the window to that many beats and adds `windowBeats` and each window's `beat` (`t` x bpm / 60: beat 0 is the file start, as after `audio.capture` from the start). `reference` (`level` only, an absolute `.wav` or `.flac`) analyzes the same span of that file (same `skipSeconds` and window length, channel 0) and adds per window `referenceRmsDb` and `deltaDb` (`rmsDb - referenceRmsDb`, `null` when either side is silent or the reference is shorter), plus `reference` and `summary{meanDeltaDb,minDeltaDb,maxDeltaDb}` over the windows with a delta (`null` when none). `onsets`: rising crossings of `threshold` (default 0.15) times the 5 ms peak envelope; `silent:true` below about -40 dBFS. `mono_pitch`: onsets plus the dominant spectral peak 10 ms later as fractional MIDI (4096-point FFT: monophonic, fundamental-dominant material only) with `summary{pitchClasses, range, intervals, stepwiseRatio, repeatRatio, leaps, leapRecoveryRatio, tuneError}` and, with `bpm`, `grid{positions16, offsetSeconds, onBeatRatio}`. `probe`: signed 10 ms means (at most 2000; page with `skipSeconds`), for a logic/CV signal wired straight to Audio Out. `bands` (channel 0, windows of `windowSeconds`, default 8, each sampling up to 16 Hann frames of 4096 samples): `windows[{t, rms, centroidHz, bandsDb:{sub,low,mid,high,air}}]` with band power relative to the window's total in dB (edges 60/250/2000/8000 Hz, `null` when empty), plus whole-file `stereoCorrelation` (L/R Pearson, the only use of channel 1; `null` for mono). `key` (`"F:aeolian"`; ionian, dorian, phrygian, lydian, mixolydian, aeolian, locrian, harmonic_minor) adds per-window and overall `chroma{inKeyShare, topPitchClasses}`: the power of every FFT bin at 50-1500 Hz folded to pitch classes, after a low-pass (80 dB down from 2 kHz) and decimation to about 4 kHz so higher partials cannot fold into the range; empty (`inKeyShare:null`) when that power is 60 dB or more below the window's total power (all frequencies); drums, noise and inharmonic partials pollute it, so use it on pitched material. `spectrogramPath` (absolute `.png`, replaced if present) writes a 256-row log-frequency spectrogram (30 Hz to 16 kHz, 80 dB range, at most 800 columns) and returns `spectrogram{path,width,height,...}`.
- `audio.analyze mode=loudness` (skipSeconds honored; every channel is read, unlike the other modes): ITU-R BS.1770-4 K-weighting, 400 ms blocks at 75 % overlap, per-channel weights (mono 1, stereo 1+1, six channels as 5.1 in WAV order L R C LFE Ls Rs with 1.41 for surrounds and LFE excluded, other counts all 1), -70 LUFS absolute and -10 LU relative gates. Result: `integratedLufs` (null when no block passes the gate), `momentaryMaxLufs`, `shortTermMaxLufs` (3 s, null under 3 s), `loudnessRangeLu` (EBU 3342: short-term values gated at -70 and -20 LU, 95th minus 10th percentile; null when under 3 s), `samplePeakDbfs`, `truePeakDbtp` and `perChannelTruePeakDbtp`, `gating:{blocks,absoluteGated,relativeGated,relativeThresholdLufs}`, `channelWeights`, `channelLayout`, `limits[]`. Limits: the 48 kHz K-weighting coefficients are the standard's, other rates are the same analog prototype through a bilinear transform; mono reads about 3 LU below the same signal on two speakers; true peak is the peak of the signal oversampled 4x by scipy's polyphase FIR (the Annex 2 method, not a certified meter: tones read within about +0.02 dB, wideband content near Nyquist up to about 1 dB low, as any 4x meter); at most 1800 s per call; it measures the file, not Bitwig's meters (the guide, §7.1.8, documents only peak/RMS).

#### `grid.probe` (client-side; Linux/PipeWire)

`grid.probe {target, port:"<module name>.<OUT key>", seconds 0.2..20, mode: probe|mono_pitch|onsets|level, allowAudible?, bpm?, skipSeconds?, method?, threshold?, windowSeconds?, timeoutMs ≤ 60000}`. Composed from `transport.get`, the Grid read, `grid.connections.set`, `audio.capture` and `audio.analyze`: refuses (`not_isolated`) unless output is on the silent sink (or `allowAudible`) and recording/automation write are observed off, stops a playing transport because rewiring cables is a structural write (it stays stopped, as after `audio.capture`), snapshots the cables into every `Audio Out` of the device, rewires the probe port to one existing Audio Out (the one already wired, else the first; the others are disconnected; no module is created), records from the start of the arrangement, then restores. The restore re-reads the graph and rewrites each Audio Out input by compare-and-set against the probe wiring; an input that someone else changed meanwhile is left alone. Result `{outcome:"applied", port, audioOut, cablesChanged, restored:true, capture, analysis, transportStopped}`. A capture or analysis error is returned after the restore. If the restore cannot finish the result is `{outcome:"unknown", reason:"job_failed", left, …}` with `left` (inputs still changed, with their original source) or, when the graph itself could not be read, `originally` plus `restoreError`; reconnect them with `grid.connections.set` first. Nothing is retried.

#### `diagnostics.get` (client-side)

Not a host method except one `status` call (for `instance.pid`). Args: `sinceSeconds` (1..86400, default 300) xor `sinceMarker` (opaque, from a previous result), `maxEvents` (1..500, default 50, newest kept; `droppedOlderEvents` says how many were cut). The Bitwig log (`~/.BitwigStudio/log/BitwigStudio.log`; macOS `~/Library/Logs/Bitwig/BitwigStudio.log` and Windows `%LOCALAPPDATA%\Bitwig Studio\log\BitwigStudio.log` are documented locations, unverified; `BITWIG_LOG_PATH` overrides) is read from the end in 1 MiB chunks, capped at 64 MiB. Not found: `{supported:false, platform, searched, note, dialogs}`.

The log is shared by all of the user's instances; each start writes a `Starting application version` header. The section is chosen by the process start time of `status.instance.pid` (Linux `/proc`) against those headers (within 120 s): `attribution.method` `pid_start_time`, else `latest_section`. `attribution.certain` is false, with `uncertainty[]`, when status or the start time is unavailable, a later start exists in the log (lines may interleave), several Bitwig processes run, or the read cap was hit. `sinceMarker` is valid only for the same section and an unchanged log; otherwise it is ignored with a `warnings` entry and `sinceSeconds` applies. Log times are local time.

`grid_rejected` bursts while a Grid build is still inserting modules are expected (the graph is incomplete between inserts and cables); judge only events after the build, using the `diagnosticsMarker` of `grid.apply`.

Result: `{platform, logPath, window, events:[{time, lastTime?, level, component, category, message (<=300 chars), count, detailLines?, gridComponent?, engineReady?}], summary:{counts, totalEvents, engineReady?, gridRejectedComponents?}, marker, attribution, dialogs}`. Identical consecutive events merge into `count`; stack-trace lines are not returned, only counted in `detailLines`. Categories: `grid_rejected` (`component X should be rejected from the network because ...`: the device was dropped from the audio network and is silent), `engine` (`FloatDocument.isEngineReadyChanged(a->b)`), `extension` (warn/error from extension/controller/script components, or an error mentioning them), `exception` (Java `...Exception`/`...Error`, `Caused by`), `dialog`, `other` (other warn/error; info lines are ignored). Known benign noise (`Cannot use realtime priority`, `Analyzing audio...`) is dropped. The extension/controller/exception patterns are heuristic: only `grid_rejected` and `engine` lines were observed natively (Bitwig 6.1.4).

Dialogs: modal UI (Dashboard, Save Project?, Recover Projects) was searched for in the real log and leaves no line; it is not detectable. The only observed signal is the `notifications` logger (e.g. `Update Available - vX: ...`), reported as `dialog` although it is a toast, not proof of a blocking modal.
