The MCP adapter connects to IPv4 loopback `127.0.0.1:61172` by default. Both the extension host process and client may set `BITWIG_AGENT_PORT` to the same alternate port; the extension reads it during initialization, validates ASCII decimal `1..65535`, and still binds only `127.0.0.1`. One UTF-8 JSON request and one JSON response per TCP connection, each terminated by newline. This is internal transport, not an extra agent orchestration protocol. No automatic retries. Requests and responses are limited to 1 MiB.

The TCP endpoint is unauthenticated. Any local process able to connect can invoke tools; use only in a trusted local environment and never expose or forward this port to a network. Context tokens and target guards are not authentication.

Request:

```json
{"id":"client-generated-unique-id","method":"status","params":{},"timeoutMs":5000}
```

`id` is a nonempty string (maximum 128 characters), `method` a known method, `params` an object, `timeoutMs` an integer from 100 through 10000 (through 60000 for `grid.modules.insert/move/delete/rename`, `grid.connections.set` and `grid.topology.reconcile`, whose per-entry verification reads the whole graph). Missing timeout defaults to 5000. Reject invalid input before scheduling work. The host adapter checks the monotonic deadline immediately before each mutation, including deferred callbacks. A dispatched host action cannot necessarily be cancelled.

Response:

```json
{"id":"client-generated-unique-id","result":{"status":"observed"}}
```

or

```json
{"id":"client-generated-unique-id","error":{"code":"deadline_exceeded","message":"Outcome unknown; inspect state before issuing another write.","outcome":"unknown"}}
```

The client checks response correlation. Errors after dispatch or a lost connection must not become an automatic replay. `id` correlates requests; it is not a persistent deduplication key. A result describes actual observation/verification scope, not universal success.

MCP returns the same envelope as both `structuredContent` and JSON text. Text uses compact separators without dropping values, nulls, error outcomes or verification fields; whitespace is not a protocol contract. The toolkit does not route to the GUI automatically. An agent may explicitly use Computer Use for unsupported operations, but must inspect uncertain writes rather than blindly repeat them through another interface.

Version `0.2.0` uses MCP SDK 2.3+. Expected bridge and argument-validation failures remain error-flagged tool results with the envelopes above. An unexpected uncaught adapter exception instead surfaces as an MCP JSON-RPC error under SDK 2, not a fabricated tool result or `not_dispatched` acknowledgement. Such a protocol error is not permission to retry: the host operation may already have run.

The registry includes `grid.*` and read-only `modulators.*` methods across discovery, flat and one-hop layer direct parameters, Actions, transport, tracks, devices/Remote Controls, launcher, MIDI and version-gated Grid inspection/scalar and boolean-panel writes/module insertion/move/selective delete/raw custom-name CAS/single-input cable editing. Existing request shapes remain unchanged. `capabilities` describes implemented domains and limits, not host acceptance. `bitwig-agent-rpc list` and `describe METHOD` expose the Python registry offline; the Java/MCP fixture checks transported schemas against the host registry. This is not complete Bitwig interface coverage.

Java transport boundary (Gson): `RpcServer.Handler.handle(String method, JsonObject params, long deadlineNanos)` returns `CompletableFuture<JsonObject>` containing the **result** object. Handler must enqueue work for the host and never call host model APIs from the network thread. Transport does not implement retries, host state, selection or business logic. Transport errors are envelopes; host method rejections may complete exceptionally using the shared `RpcException` type carrying `code`, `outcome`, and message.

## Core discovery and direct parameters

Parameter objects accept exactly the listed keys; extra keys and explicit nulls are rejected. Unless a narrower bound is documented, strings must be nonempty and at most4096 UTF-16 code units. `trackId` is a UUID reported by the current track bank, not a name. Root `deviceIndex` is an integer0–15; general paging is not implemented. The separate one-layer API below does not reinterpret flat device indices. MCP/CLI `timeoutMs` is removed from method params and sent in the transport envelope.

| Method | Exact params |
|---|---|
| `status` | `{}` |
| `tracks.list` | `{}` |
| `devices.list` | `{"trackId":"..."}` |
| `parameters.list` | `{"trackId":"...","deviceIndex":0,"expectedDeviceName":"..."}` |
| `parameters.set` | `{"trackId":"...","deviceIndex":0,"expectedDeviceName":"...","contextToken":"...","parameterId":"...","value":0.5}` |

`status` returns `status:"observed"`, `hostVersion`, `apiVersion`, `projectName`, `engineActive`, `playing`, `projectModified` (observed `Project.isModified()`: true unsaved, false saved, null unobserved), the two window capacities, and `instance:{pid,parentPid,display,waylandDisplay}` (which Bitwig process answered: its pid, its parent pid (the launcher that forked it) and `DISPLAY`/`WAYLAND_DISPLAY`, null when unset; `context.get` carries it too), and `parameterBindingDiagnostics`. Diagnostics report the current bank target, match/established state, source-local ID callback counters, cache generation and observed-proxy identity scope; when unbound, only established/identity scope are present. They are not a complete callback event trace. `status` and `capabilities` also return `extension:{version,build}`: package version and git short SHA (`-dirty` if uncommitted changes) embedded by `scripts/build.py`, or `"unknown"`. The Python client adds `extensionMismatch:{extensionVersion,clientVersion,warning}` to a `status` result when the versions differ; the call still succeeds. Status is a snapshot, not a project identity or host-test certificate.

`status` and `context.get` also carry `projectReady` (true/false/null) with `projectReadyReason` and `projectChangedMsAgo`. The public API has no project-loaded event, so this is a heuristic: null = project name not yet observed; false = a project-name change (extension start, project switch/recovery, Save As) within the last 3 s (`project_changed_settling`) or the track bank is unsized (`track_bank_unobserved`); true = `settled`. While false, `tracks.create`, `devices.insert`, `devices.delete`, `devices.move`, `devices.layers.insert`, `tracks.group`, `arranger.clips.create/copyFromLauncher/edit`, `launcher.create`, `launcher.import`, `scenes.append` and the Grid write methods (`project.saveAs` and `project.activateEngine` are never gated) (`grid.modules.*`, `grid.connections.set`, `grid.parameters.set`, `grid.voicing.set`, which `grid.apply` uses) fail `project_not_ready` (`outcome:not_applied`); null does not block. `context.get` also reports `engineActive`. With `engineActive:false`, `launcher.launch` fails `engine_inactive` (`not_applied`, nothing dispatched) and `transport.set` `playing:true` succeeds with a `warnings` entry; the client-side `audio.capture` and `grid.probe` check `status` first and fail `engine_inactive` before touching anything. Fix: `project.activateEngine`.

`tracks.list` returns `tracks:[{trackId,index,name}]`, `scope:"flat_track_bank"`, and `window:{offset,capacity,total,complete}`. `devices.list` returns `trackId`, `devices:[{deviceIndex,name,type}]`, `scope:"top_level"`, and the same window metadata. Both windows have capacity 16. `complete` describes the bank's count/window coverage only, not all project object types. A track or device outside the current window is rejected rather than silently selecting another target.

`parameters.list` binds a target within the existing track/device banks and returns `status:"observed"`, `target:{trackId,deviceIndex,deviceName,contextToken}`, `parameters:[{id,name,normalizedValue,readable}]`, `scope:"host_exposed_direct_parameters"`, and `identityScope:"observed_bank_proxy_context_not_persistent_device_identity"`. An unknown or inaccessible value is JSON null, not zero; names may initially be empty. Each fixed bank proxy continuously observes its own IDs/names/values; binding does not clear those observations or require unchanged IDs to replay. Parameter maps are allocated lazily. Copy `target.deviceName` into `expectedDeviceName` when writing. The token belongs to the observed context and process, not a durable device UUID. Rebinding and observed context/ID changes invalidate its token. A metadata-only name change retains that proxy's observations while invalidating the token; observed existence, track UUID or position changes evict the source cache. Replacement at the same track/position without an observable existence transition cannot be distinguished from the same proxy, even if its name changes; retained values may then be stale. Initial callback ordering and bank-shift recovery have not been established for all transitions. Re-enumerate after edits; this is not a persistent-device identity guarantee.

`parameters.set` requires the current context token, unchanged target, an ID from that context and a readable parameter. It never implicitly rebinds a stale target. `value` is finite and normalized to [0,1]; the host call uses resolution 16384, rounding to its 16383 intervals. Results include `target`, `parameterId`, `requestedValue`, `appliedValue`, `observedValue`, `difference`, `tolerance`, `matchesRequested`, `verification` and `resolution`.

The result is `status:"observed"` only when the target still matches and either the value was already within tolerance (`verification:"already_at_value"`, no write dispatched), or a subsequent callback from that same bank proxy matches (`"observer_after_write"`). Otherwise it is `status:"dispatched"`, with `verification:"readback_mismatch"` or `"not_observed"`; a stale pre-write cache or another source's callback is never returned as post-write evidence. Observation is bounded to roughly 750 ms and the request deadline. This is not an atomic transaction, persistent save verification, or proof that another actor did not write the same value. Observers are asynchronous; a context token is not a cross-tool lock.

Argument names are strict: there are no aliases. An unknown field gets a hint (closest accepted name, plus a small guessed-name map such as `offset`/`limit` -> `moduleOffset`/`moduleLimit`, `tempo` -> `tempoBpm`, `instanceId` -> `moduleId`/`targetModuleId`); fix the name and retry, nothing was dispatched.

Agents act on the error's `outcome`, not on a code list: `not_applied` means nothing was dispatched and the call may be fixed and retried; `unknown` means inspect state first. Codes an agent branches on: `invalid_params` (fix the arguments), `stale_target`/`stale_context` (rediscover the target, then retry; `stale_target` = the addressed identity differs from what was observed, e.g. `expectedDeviceName`/track mismatch on any root-device method, `stale_context` = a context token, epoch or window changed, including while a call was queued or running), `busy` (wait, retry) and `deadline_exceeded` (inspect, never blindly retry). Errors before parameter dispatch have `outcome:"not_applied"`; a deadline or target change after dispatch has `outcome:"unknown"`. A request ID is not an idempotency key. No automatic retry or GUI fallback is implemented.

### One-hop layer devices

`parent` is the shared `DeviceParent` schema, exactly `{"trackId":"<observed UUID>","deviceIndex":0,"expectedDeviceName":"<current root name>"}`. It always addresses a top-level device. Layer and child indices are not substituted into this root address. The same shape is used by read-only modulator methods; this shared schema does not extend layer traversal or change existing layer wire semantics.

| Method | Exact params |
|---|---|
| `devices.layers.list` | `{"parent":{...}}` |
| `parameters.layer.list` | `{"parent":{...},"layerId":"<observed UUID>","childDeviceIndex":0,"expectedChildDeviceName":"<current child name>","discoveryToken":"<from discovery>"}` |
| `parameters.layer.set` | The same child address plus `contextToken`, `parameterId`, and finite normalized `value` in0–1 |

Discovery returns the actual `parent`, `scope:"one_layer_hop"`, an observed layer `window`, and `layers`. Each layer carries `index`, `layerId`, `name`, `channelIndex`, `readiness`, its child `window`, and `devices`. Each child carries `index`, observed `childDeviceIndex`, `name`, `type`, `readiness` and `directContextAvailable`; only eligible contexts receive a `discoveryToken`. Windows expose nullable `offset`, `total`, `exists`, fixed `capacity`, `complete` and `readiness`. Unknown is not zero or empty. A parent without layer support rejects `unsupported_scope`; an unobserved/invalid window rejects `not_ready`.

Banks are created only at initialization: two layers per root, two children per layer, fixed zero-offset nested windows. Both parent and child must fall within observed counts. `childDeviceIndex` accepts only0–1. There is no deeper traversal, pad/slot target, nested Remote Control, private Grid-module target or paging fallback. Child-to-layer ownership follows construction of that layer's device bank, not a dynamic equality observer: native6.1.3 rejects an equality value for proxies that always refer to the same target. This is not persistent physical-device identity.

Copy the discovered child address into `parameters.layer.list`. Its `target` retains the same nested address and adds a `contextToken`; use that complete target plus `parameterId`/`value` for the write. Normalization, quantization and fresh same-source acknowledgement follow the flat parameter contract above. Discovery neither selects a device nor changes the active parameter binding. Flat and nested parameter operations share one active binding and pending request: switching targets invalidates the old binding token, while continuously observed per-source data survives request A→B→A without ID replay.

Discovery readiness does not mean parameter IDs/values have arrived. Nested data is admitted only with observed ancestry, including a nonnegative assigned track position and an assignment-aware layer channel index; ordinary proxy default zero is not assignment evidence. The integer observer reports unassignment as−1, without getter fallback or callback replay. Rejected initial callbacks are not resurrected from getters. Name changes invalidate tokens but preserve continuous data. Known discontinuities—including conservative ancestor/window and assigned channel-index changes—retire nested direct access for the extension lifetime; subsequent callbacks do not establish provenance. `channelIndex` is not the layer-bank slot, and a change is not proof of physical replacement: project-order renumbering may also close access conservatively. The response reports `physical_rebind_callback_provenance_unavailable_until_extension_reload`. Reload is a new observation lifetime, not an automatic retry or proof that the previous write failed. Unobserved same-metadata physical replacement remains undetectable. The existing root getter-snapshot admission policy is separate.

Layer discovery and parameter observations do not establish native write isolation, DSP, whole-hierarchy coverage or general persistence. See [coverage limits](VERIFICATION.md#coverage-limits-and-unresolved-results).


## Host Actions

`actions.list` accepts optional `query` (case-insensitive substring of id or name), `category` (exact category id or name, case-insensitive) and `limit` (1..1000, default 100) and returns `{status:"observed",scope:"host_action_catalog",total,complete,actions:[{actionId,name,category:{id,name}|null}]}` (`total` counts all matches, `complete` is false when `limit` truncated them) from `Application.getActions()` and the Action metadata. These are the host's current IDs and localized names, not guessed command names. Catalog membership does not establish enablement or completion in the current UI context.

`actions.invoke` accepts `{"actionId":"..."}` plus optional `discardUnsavedChanges` (bool) (the same nonempty, maximum 4096-character string rule) and resolves it using `Application.getAction(id)`. An absent ID is rejected with `unknown_action`, `outcome:"not_applied"`. The lookup and invocation run on the host thread; the deadline is checked again immediately before invocation. `Quit` closes every open project tab while only the current tab's saved state is observable, so it is refused with `unsaved_changes`, `outcome:"not_applied"` unless `discardUnsavedChanges:true` (user consent only). `Close` is refused unless the current tab is observed saved or consent is given. `New`/`Open` open another tab (observed on 6.1.4) and are not guarded; there is no other policy. A returned call reports only `{status:"dispatched",actionId,completion:"not_observed"}`. Actions may depend on selection/focus, open dialogs or change a project. A dispatched save/export Action is not proof of a written file. Observe the resulting state explicitly; no retries, completion polling, selection routing or GUI fallback are added. MCP exposes `timeoutMs` separately, as for the existing methods.

Transport uses raw BPM and quarter-note beats. Tempo 20–666 is a toolkit-supported range evidenced by a shipped controller, not a claim about every native raw limit. Position/loop start are nonnegative; duration is positive; their sum must remain finite. Recording/arranger automation/launcher automation write flags are read-only. While enabled, non-stop transport mutations are rejected; explicit stop remains available. Multi-field mutations are not transactions: each field is guarded and separately verified, and earlier changes can remain when a later field fails.

When an explicit `playing:false` accompanies other transport fields, the bridge waits for the stopped-state observation before dispatching those remaining fields, within the same bounded observation window. Sending stop and seek consecutively is not sufficient: an asynchronous stop can overwrite the requested position. Deferred writes still recheck cancellation, deadlines and recording/automation guards. A missing stop observation leaves remaining fields `not_dispatched`; partial or unknown completion still stops the caller rather than triggering a retry.

Both transport reads and write-result snapshots include `projectName` from the existing interested Application source. This lets callers check the expected project label and safety flags in one response instead of pairing `status` with `transport.get`. A null, missing or changed name is not permission to mutate. This is an observed name, not full-file-path identity, an atomic snapshot across fields or a project lock.

Track volume, pan and remote control values are normalized [0,1]; accompanying host display strings are not interchangeable numeric units. Track creation rejects an incomplete initial UUID/index/type window, or a full one (16 tracks, where the new track could not be observed), before invoking a factory. In a grouped project the factory index counts top-level tracks only; creation needs an observed complete track tree, else `unsupported_scope/not_applied` before any factory (see [Track tree and grouping](#track-tree-and-grouping)). After one supported factory call, attribution requires a complete after-window, one new UUID, matching type, top-level ordinal and repeated observations before assigning a name. A group appearing after dispatch or concurrent unrelated creation can still leave an unnamed created track with an unknown result. An unresolved dispatched creation blocks further factories; inspect the actual project rather than retrying.

Mix observations belong to continuously interested bank proxies. An established UUID/existence change invalidates operation generations and masks reads/writes until an actual controller `flush` refreshes previously observed getters with matching identity/existence. This is not an atomic physical-track snapshot. Readable getter baselines do not make prior-generation equality a verified no-op: a post-rebind same-value write can remain `unknown` if the host emits no fresh callback. Agents should submit only fields that differ from a fresh readable `tracks.get` snapshot; inspect overall completion and each field's verification, and never automatically retry an unknown composite result. Legacy selection can remain unreadable until a current-generation selection callback. Old operations never regain validity after same-UUID reappearance.

`tracks.select` is an explicit UI-navigation command, not a verified mix-field setter. Like `devices.select`, it returns `status:"dispatched"`, `completion:"not_observed"` and `verification:"selection_has_no_reliable_public_observer"`. It dispatches once even when a cached selection value is already true; that value cannot prove the requested editor navigation. Its snapshot can still contain `selected:null` after a project/proxy rebind, and it has no setter-style `fields` or `matchesRequested` acknowledgement. Inspect the actual track/device context and any selection-triggered arming before dependent edits. UUID/rebind, cancellation and deadline guards remain active; an error after dispatch can still be `unknown` and must stop the caller. A dispatch-only receipt is not permission to repeat the command blindly. While a launcher cursor operation (`notes.*`, `launcher.create/import`) is running, `tracks.select`, `devices.select` and `actions.invoke` fail fast with `busy`, `outcome:"not_applied"`; nothing is queued.

Explicit normalized volume, pan and Remote Control mutations use the native `setImmediately` API: absolute RPC values must not wait for physical-controller pickup. Global takeover preferences are untouched. Remote value writes additionally reject active or unobserved recording/automation-write modes immediately before dispatch.

Device insertion requires the expected count and complete top-level window. Confirmation observes a fresh appended device, a count delta and unchanged prefix; `requestedIdentifierVerified:false` explicitly distinguishes that observation from proof of the requested plug-in/preset identity. File insertion passes the path to the native host API, not a shell. `devices.catalog` checks local factory Grid file presence; insertion and rendered musical identity need separate native evidence. Community website UUIDs are not advertised as native device IDs.

### Device chain edits and preset search

`devices.insert` observes the chain's bank: the count must rise by one, every device before the insertion point must be unchanged (name, type, observed revision) and every device after it must appear shifted by one slot, with the new tail slot reporting fresh metadata. The result adds `position:{mode,index}` (the final slot) and `inserted` (that slot's name/type, null if not identified); `verification` is `observed_count_increment_and_unchanged_prefix` for an append and `observed_count_increment_shifted_suffix` elsewhere. `before`/`after` need the anchor's `deviceIndex` and exact `expectedDeviceName`: a wrong name is `stale_target`, an index at or past the count is `target_not_found`, and neither reaches the host. `start`, `end`, `before`, `after` use the public `startOfDeviceChainInsertionPoint`, `endOfDeviceChainInsertionPoint`, `Device.beforeDeviceInsertionPoint` and `Device.afterDeviceInsertionPoint`.

`devices.delete` and `devices.move` address one top-level device exactly like `devices.get` (`trackId`, `deviceIndex`, exact `expectedDeviceName`), require the complete top-level window and no recording/automation write, and compare the whole chain's observed names/types before and after. Delete reports `deleted`, `beforeCount`, `afterCount`, `before`, `after` and `verification:"observed_count_decrement_and_shifted_suffix"`. Move reports `moved:{deviceIndex,name,type,toIndex}` and `verification:"observed_expected_arrangement"`; moving later lands after the device currently at `toIndex`, moving earlier lands before it, so the device ends at `toIndex`. A move among devices with identical names and types cannot be told from no move: it dispatches once and returns `status:"dispatched"`, `verification:"move_indistinguishable_by_name_and_type"`. For all three, `status:"dispatched"` with `insertion_not_observed`/`deletion_not_observed`/`move_not_observed` or `ambiguous_chain_change` means inspect `devices.list` before another edit; nothing is retried. Each edit is one native Undo step. Moves and deletes act within the top-level chain only (at most 16 devices; a longer chain is `outside_window`); moving between chains or into layers is unsupported. Any edit that shifts a device (`start`/`before`/`after` insert, delete, move) retires the nested proxies of the shifted devices: afterwards `parameters.layer.*` for those parents may return `not_ready` until `extension.restart`.

`devices.layers.insert` takes the same `parent` as `devices.layers.list`, the layer's `layerId`, its current child count `expectedChildCount` (the layer window's `total`, a mismatch is `stale_context`) and inserts at the layer's `start` or `end` through that `DeviceLayer`'s public insertion points (Instrument Layer, FX Layer and Chain layers; drum pads are unsupported). Only the first two children of a layer are observable (the fixed layer window), so a layer that already holds two devices can be verified only by its count: `status:"observed"`, `verification:"observed_count_increment_beyond_window"`, `inserted:null`. Structural changes inside a layer retire the nested proxy: afterwards `parameters.layer.*` for that parent's children may return `not_ready` until `extension.restart`.

`presets.search` never calls the host. It walks the user library (`~/Bitwig Studio/Library`) and installed packages (`~/.BitwigStudio/installed-packages`, plus the macOS/Windows locations; `BITWIG_PRESET_ROOTS` replaces the roots) for `.bwpreset` files. User-library presets with a plain header yield `device`, `deviceType`, `category`, `deviceCategory`, `creator` and `comment`; package presets are encrypted, so only `path`, `creator`, `package` and `folders` are known (`metadataReadable:false`), and `device`/`category` then match folder and package names. Query words must all occur (case, spaces and punctuation ignored) in the name, folders, package, creator or readable metadata; results rank name hits first and carry `insert:{kind:"file",path}` for `devices.insert`. `deviceType` matches only readable metadata. A hit is a file on disk: that the host loads it, and what it sounds like, is separate evidence.

Remote tokens bind observed track/device/page/control metadata, not persistent physical devices or invisible same-name remappings. Observed lifecycle changes mask affected controls until actual host flush reconciles current previously observed getters; subscription history is retained because unchanged callbacks may not replay. Absent/remapping controls and never-observed/nonfinite getters remain unavailable. Flush refreshes page comparison baselines but never advances write acknowledgement sequences or freshness. Thus a recovered same-value request can dispatch and remain unacknowledged rather than claim a verified no-op. Old tokens and pending operations do not regain validity. Neither remote nor direct parameter controls expose Grid module creation/cables.

`launcher.launch` and `launcher.stop` report `completion:"observed"` when the requested playing/stopped state is observed. A confirmed queue reports `status:"dispatched"`, `playbackState:"queued"` and `completion:"not_observed"`: accept this only as an explicitly expected dispatch-only result, then independently inspect `launcher.list` for actual playback/stop before dependent edits. If neither the desired state nor a queue is observed within the bounded observation window, `completion:"unknown"` requires stopping the writer, not retrying. These are launcher-state observations, not musical/audio completion or cancellation guarantees.

`launcher.import` shares the launcher mutation/cursor lease, checks the explicit slot is empty immediately before `replaceInsertionPoint().insertFile`, and requires a fresh observed content transition. The result reports `verification:"slot_content_transition"` and `requestedFileVerified:false`: it does not prove file identity, decoding or audible output. Unsupported native content may silently do nothing; an unobserved dispatched import returns `import_not_observed/unknown`, never a retry. The SDK has no atomic conditional insertion; an external edit after the final occupancy check remains a race.

Unresolved dispatched launcher creation/import stays quarantined beyond the RPC future's lifetime. Conflicting creation, import and note writes reject with `unresolved_mutation/not_applied`; inspection remains available. Only normal positively observed completion releases the target. Late callbacks, an empty observation or elapsed time do not clear an ambiguous result. The affected UUID/slot and original bank proxy remain quarantined for the extension instance. Recreating the extension clears this in-memory guard but does not cancel or establish completion of pending native work: inspect and settle host state before using that reset boundary.

### Mixer levels, sends, meters, markers

Guide references are to the Bitwig Studio user guide (5.3 text, the latest published): sends §7.1.6, faders and meters §7.1.8, time signature §2.3.3, cue markers §5.5.1.

**Display-addressed levels.** The controller API has no dB or percent setter and publishes no fader curve, so `tracks.set` `volumeDb`/`volumeDisplay` and `panPercent`/`panDisplay`, and `tracks.sends.set` `display`, bisect the normalized value against the host's own displayed text (`Parameter.displayedValue`): write, wait for the value callback, let the display callback settle two polls, read the text, narrow. `volumeDb`/`panPercent` are numbers (pan negative = left); the `*Display` forms take the host's text (`"-6 dB"`, `"-inf dB"`, `"25% L"`, `"40% R"`, `"Center"`). The text is only parsed, never converted by a formula: dB needs a `dB` unit, `-inf`/`∞` means the bottom of the scale, pan needs `%`, a side letter or Center. Success needs the displayed number within half of the last displayed digit of the target; the result carries `volumeDisplayWrite`/`panDisplayWrite`/`displayWrite` `{requested,target,observedDisplay,normalized,originalNormalized,probes,matched,method:"bisection_on_observed_display"}` and the field verification `display_readback`. Failure (`display_unparseable`, `display_not_reachable` after at most 28 probes or when the bracket is below 2e-5, `probe_not_observed`, `target_changed`) writes the original value back, applies no other field of the call (`otherFieldsApplied:false`) and answers `status:"dispatched"`, `matchesRequested:false`, `completion:"observed"` when the restore was seen, else `unknown`. Unparseable request text is refused as `invalid_params` before any write. The search moves the fader during the call; it assumes display increases with the normalized value.

**`tracks.sends.set`.** The send is addressed by `sendIndex` (the `sendIndex` of a `tracks.get` send row, offset-adjusted) or by a `sendName` that matches exactly one existing send (`unknown_send`, `ambiguous_send`); `expectedSendName` is a compare-and-set guard (`stale_target`). `valueNormalized` is written with `setImmediately`, `enabled` last, each verified against an observer callback after the write (`observer_after_write`, `already_at_value` when nothing needed writing). A level write turns a disabled send on (guide §7.1.6: new projects start with all sends disabled); the result reports `autoEnabled`. Send pre/post mode is not exposed. `tracks.get` send rows additionally carry `effectTrack:{trackId,name}` (the effect track with the same ordinal as the send, null when not in the window) and `nameMatchesEffectTrack`.

**`tracks.meters`.** Registers `Channel.addVuMeterObserver(128, channel, peak|rms)` for left and right of every bank track at startup (a failed registration makes the method answer `unsupported_scope`). Values are the host's 0–127 steps; the public API gives no dB mapping, so none is claimed. A steady meter fires no callback, so the standing level at window start counts. Per track: `peakMax`, `rmsMax`, `rmsMean` (20 ms polls), `callbacks`, `silent`, `targetUnchanged`; plus `playingAtStart`/`playingAtEnd`. Meters move only while audio renders; set `timeoutMs` to at least `windowMs` + 300 or the call is refused (`invalid_params`). For loudness use `audio.analyze mode=loudness`.

**Cue markers.** `markers.list` reads `Arranger.createCueMarkerBank(64)`: `{markers:[{markerIndex,name,beat}],window,observationsComplete}` sorted by beat; `markerIndex` is a rank, not an id. Writes need the whole list inside the window and recording/automation off; `markers.insert` also needs an observed stopped transport and refuses a beat that already holds a marker (`marker_exists_at_beat`). Insert calls `Transport.addCueMarkerAtPlaybackPosition()` once, identifies the one new marker as the single multiset difference of the list, then sets its name and position in the same controller callback (the playhead never moves). Rename/delete require the exact `expectedName` (and optional `expectedBeat`) of the ranked marker (`stale_target`). Every write is verified by comparing the full observed list with the expected one (`observer_after_write`); an unobserved result is `completion:"unknown"`, is listed by `extension.restart` as unresolved and blocks further marker writes (`unresolved_mutation`). Time-signature change markers (guide §5.5.2) have no public API.

**Time signature.** `transport.set timeSignature:"7/8"` calls `TimeSignatureValue.set(String)` (numerator 1–32, denominator 1/2/4/8/16/32 as validated by the toolkit; the host decides what it accepts, readback is the proof) and is verified like the other transport fields; `transport.get` returns the string the host reports.

### MIDI window and edits

Every `notes.read/edit` request supplies `trackId`, `slotIndex` (below scene count; else `slot_out_of_range`) and optional `channel` (0–15, default 0). The five grid fields are supplied together or all omitted. Explicit: `stepSizeBeats` (1/128–4), `startStep` (0–1048576), `steps` (1–128), `pitchStart` (0–127), `pitchCount` (1–128; range must end at or below 128). Omitted on `notes.edit`: the finest grid among 1, 1/2 … 1/128 beat that aligns every beat/duration within 128 steps (so existing finer onsets stay visible to collision checks), `startStep` at the earliest edit and the pitch range of the edits are derived (echoed with `derived:true`); more than 128 steps is `invalid_params` (split by time or use a coarser grid). Omitted on `notes.read`: the loop is read over pitches 0–127 at 0.125 beat (1/32 note) when the loop is at most 16 beats, else 0.25 beat (1/16 note), at most 128 steps; if the loop is longer, `windowCoversLoop:false` and `continuation` names the next explicit window (never coarser than 1/16). MIDI numbers avoid octave-label conventions: 60 means the same pitch even when the UI calls it C3 rather than C4.

Each edit is either `{"op":"set","beat":0,"pitch":60,"velocity":90,"durationBeats":1}` or `{"op":"clear","beat":0,"pitch":60}`. Velocity is an integer 1–127, duration 1/128–4096 beats. Beat and duration must align exactly to the requested step grid. Set duration must fit the requested window and observed loop end. Duplicate cells, overlapping same-pitch sets, existing onset collisions and edits starting inside a sustain are rejected before note writes. Clearing an obstructing note requires an explicit earlier call; there is no whole-clip replacement.

`launcher.create` initializes the new clip's playback stop to `lengthBeats` as well as creating its loop extent. Creation is reported observed only when the requested name, loop length and playback stop read back. This avoids the native four-beat default stop on longer clips. It does not configure Next Action or automatic scene sequencing; those controls and scene naming still require the native interface.

For `.mid` / `.midi` imports, the extension validates Standard MIDI File parsing and requires a positive-velocity note-on or another channel event before dispatch. Controller/program/pitch-only MIDI remains eligible for host import. Malformed, metadata-only or note-off-only files return `invalid_midi_file` / `empty_midi_file` with `outcome:not_applied`, without quarantining subsequent writes. Use `launcher.create` for intentional silence. This preflight does not verify decoded host notes, multitrack placement or tempo metadata behavior. Other file formats retain host-side interpretation. An import already dispatched without an observed content transition still remains quarantined; there is no automatic or arbitrary reset for possible late writes.

`launcher.create`, `notes.read` and `notes.edit` explicitly select the launcher clip in the UI. They bind the cursor using slot-proxy equality and track UUID, with a local cursor-operation lease; no name fallback. This can affect host auto-arm/editor selection according to existing preferences. These calls do not silently change preferences.

Selection itself counts as dispatch, including for `notes.read`: a later context change, deadline or host failure reports `outcome:"unknown"` even when no note was written. `not_applied` must not imply that an already-dispatched selection had no UI or auto-arm side effect. A failed read is therefore not automatically safe to retry.

Readback reports actual `NoteStep` state, duration and grid-cell onset. Note rows are `{beat,pitch,velocity,durationBeats}` with integer MIDI `velocity` 1–127, the unit `notes.edit` accepts (the host's 0–1 value is rounded); channel is the window's and step is `beat/stepSizeBeats`. The public API does not establish exact sub-step onsets or multiple onsets within a cell; the read covers one channel and window, never the whole clip. `gridReadiness:"scheduled_settling_not_acknowledged"` means grid data follows observed cursor identity plus a fixed settle delay covering the known Bitwig 6.1.3 refresh debounce; the public API has no grid offset/step acknowledgement, so this is not a host-data barrier and delayed same-cell callbacks carry no source-window identity. Dense reads return at most 2048 onset rows, with `notesInWindow`, `notesReturned`, `completeWindow` and subdivision guidance.

`notes.edit` (and `noteWrite`) is compact by default: top-level `status`/`verification` are computed over every edit, `summary:{requested,dispatched,alreadyMatched,verified,unverified}` counts them, `notesInWindow` counts onsets, and `unverifiedEdits` lists only edits that were not read back (`{op,beat,pitch,verified:false,verification,observed}`; `observed` is the cell's onset row, or `{beat,pitch,state}` for an empty or sustained cell). `detail:"full"` instead returns the `notes.read`-style window listing plus an `edits` entry per edit (all edits, including verified). Failure semantics and write checks are identical in both modes. This is not a lossless arbitrary-MIDI exporter. A successfully dispatched cursor operation is not proof of audio-clip suitability, saved persistence or audible output.

Grid reconfiguration has a separate unresolved readiness limit: the installed API exposes setters but no acknowledged current step-size/scroll-offset revision. Configuration follows observed cursor identity, then waits 150 ms to cover the observed 6.1.3 100 ms grid-refresh debounce plus a delivery margin. Results expose `gridSettleMs`, `gridReadiness:"scheduled_settling_not_acknowledged"` and `gridGeneration`, not a data barrier. Generation scoping rejects known old/unsettled observations, but a late same-cell callback has no source-window ID. A cold first-read regression previously returned beat 1 for a note the native Inspector placed at beat 2. The correction does not retroactively pass the original preservation criterion or guarantee arbitrary delayed callback delivery. Alternating-window/step-size and independent native E2E remain separate evidence; consumers must not treat grid readback as atomic or lossless. See [coverage limits](VERIFICATION.md#coverage-limits-and-unresolved-results).

### Track tree and grouping

The guide describes group tracks as uniting "several component tracks … into one higher-level track for streamlined mixing" and grouping as "select the tracks you wish to group and then press [CTRL]+[G]" ([intro to tracks §3.2.1–3.2.2](https://www.bitwig.com/userguide/latest/intro_to_tracks)).

**Tree in `tracks.list`.** The flat bank lists tracks in tree pre-order. Each row adds `type`, `isGroup`, `groupExpanded` (groups only, else null), `parentId` (the parent group's trackId; null at top level), `depth` (0 at top level) and `parentResolved`. The parent comes from one public `Track.createParentTrack(0, 0)` proxy per bank slot. The first non-master track is top-level, so its observed parent identifies the root group. A track is top-level when its parent is that root, and a child when its parent is a Group in the window. `tree:{complete, groupsPresent, reason?, scope}` is true only when the window is complete and every parent is the root or a Group earlier in the window that every track in between descends from. Otherwise `parentId`/`depth` are null, never guessed. Reasons: `track_window_incomplete`, `parent_observation_missing`, `parent_not_a_group_in_window`, `parent_order_inconsistent`, `parent_cycle`. A project without groups needs no parent observation: every track is top-level.

**`tracks.create` with groups.** `Application.createAudioTrack/createInstrumentTrack/createEffectTrack(position)` insert into the root group's main or effect list (`kWY.cfM(track, min(position, count), …)` and `kWY.cfM(index, …)` in the inspected binary). In a grouped project the index therefore counts only top-level tracks: a group counts once, its children do not. Creation is refused (`unsupported_scope/not_applied`, no factory) only while `tree.complete` is false. Otherwise attribution additionally requires the new track to be observed top-level at the expected top-level ordinal of its list. A new track observed inside a group, at another index, or a group appearing during a flat-project creation is never named and stays `unknown`. `creation.parentScope` is `top_level_of_grouped_project` or `flat_project`.

**`tracks.group`** `{trackIds:[1–16 distinct track UUIDs], name?}` creates one group containing exactly those tracks without using the UI selection. The tracks must share one parent (top level or the same group). Effect and master tracks are refused (`unsupported_scope`). Needs observed recording and both automation-write modes off, a complete window of at most 15 tracks (room for the group) and `tree.complete`; another creation or grouping in flight is `busy`, a running launcher cursor operation `busy` (it holds the selection lease the grouping takes).

- **Native operation.** Gated like the other private bindings: exact Bitwig 6.1.4 and the hashed JAR, else `track_group_unavailable`. On the native document thread it resolves each bank proxy (`ControlSurfaceProxy.getDeepestTarget`) to a native track (`zwV`), corroborates its UUID (`RYd.kFU()`, or a group's channel alias `kWY.TD2().kFU()`, matching the public channelId), takes the common parent `RYd.QNk()` (must be one `SC` group), and checks owning-project/context lifecycle. It then calls `SC.MRY(List)`, the model operation behind the track-group command `group_tracks(tracks)`.
- **What the native operation does.** In one undoable transaction it creates a group at the first listed track's index, copies that track's color, expands it, moves the tracks into it in list order, and selects the new group. Tracks are passed in flat order, so their order is kept. When tracks hold plug-ins, Bitwig may first save plug-in states asynchronously, so observation waits up to 3 s within the deadline.
- **Verification** is public: exactly one new UUID in the window, of type Group, whose parent is the original parent; every requested track's `parentId` is the new group; every other track's parent is unchanged. The requested tracks keep their relative order. All of this must be seen in two consecutive observations. The result is `{trackId (the group), group:{children, parentId, verification:"unique_added_group_uuid_and_every_track_parent_observed_twice", nativeOperation, nativeUndo:true, selectionSideEffect}}`. With `name`, the name is then applied and verified like `tracks.set` (`fields.name`).
- **Unknown outcomes.** A dispatched grouping that is not attributed returns `status:"dispatched"`, `completion:"unknown"`, `reason`. It quarantines both `tracks.create` and `tracks.group` (`unresolved_creation`) until `extension.restart`. Inspect `tracks.list`; never retry. Undo grouping across the following rename is not verified.
- **Not covered:** ungrouping, moving tracks into an existing group, grouping effect tracks, and group-owned effect tracks as targets (they are listed with their parent).

### Arranger clips (version-gated)

The guide places clips on the timeline by dragging from the Browser "to the desired timeline position" ([arranger clips §5.1.1](https://www.bitwig.com/userguide/latest/arranger_clips_and_the_browser_panel)). It copies launcher clips to the arranger by dragging them onto a track's timeline ([acquiring launcher clips §6.2.2](https://www.bitwig.com/userguide/latest/acquiring_and_working_with_launcher_clips)). It moves and resizes clips by dragging their body and edges (§5.1.2–5.1.4).

The public controller API has no arranger-clip enumeration or creation. `ControllerHost.createArrangerCursorClip` only follows the UI-selected clip. These methods therefore use exact native bindings behind the same 6.1.4 version/JAR-hash gate (`arranger_unavailable` otherwise). They reach the clips on one track's **main clip lane** without selecting anything:

- player track `ynF.HVx()` → lane `Tsu`;
- `sru.iAj()` → note-clip timeline `VDz`, which holds instrument (`kOI`) and audio (`Nbl`) clips;
- events `qIe.cfM()`, ordered by start.

| Method | Parameters / operation |
|---|---|
| `arranger.clips.list` | `T`; read-only. `clips:[{clipIndex, startBeats, lengthBeats, endBeats, name, kind:"instrument"|"audio"|"other", loopEnabled, loopStartBeats, loopLengthBeats, playStartBeats, playStopBeats}]`, `count`, `lane:"main_clip_lane"`. Start/length are `SMz.x3t()`/`asx.nfq()`; timing uses the same native properties as `launcher.get`. No stopped transport needed |
| `arranger.clips.create` | `T`, `startBeats` (0–4194304), `lengthBeats` (1/128–65536), `name` (1–128), optional `notes` (1–256 `{beat, pitch, velocity, durationBeats}`, beats from the clip start on a 1/128 grid, no duplicate cell or same-pitch overlap, must fit `lengthBeats`) and `channel` (0–15, default 0, only with notes). Instrument tracks only. Inside one project transaction it builds the clip with `g1d.cfM(start, length)`, inserts it with `PSn.cfM(event, false, false, null)` ("Insert Event", without the range-clearing overwrite), names it with `Ob.g_(name)` and adds each note with `AGr.MRY(n1.cfM(beat, duration, velocity/127), pitch, channel, null)` ("Insert Note"). Readback: exactly one new clip, the created object, at the requested start/length/name; every note found in its pitch row with beat, duration and velocity (`noteWrite`), and the clip holds exactly the requested count |
| `arranger.clips.copyFromLauncher` | `T`, `slotIndex` (0–15), `expectedClipName` (1–256, from `launcher.list`), `startBeats`. Copies that occupied slot of the same track onto its arranger lane through Bitwig's copy-launcher-clips-to-arranger operation: `shO.cfM([slot], slot, start, i3D.COPY, false, null, null)`, a unique copy rather than an alias. The slot must be on the track's main lane. The copy's length is the clip's arrangement length `zZi.Mb2()` (`expectedLengthBeats`). Readback: exactly one new clip at `startBeats` with that length |
| `arranger.clips.edit` | `T`, `clipIndex` (0–4095), `expectedStartBeats`, `expectedName` (0–256, empty allowed) and one `op`. **Safety and evidence:**

- **Writes:** need observed stopped transport with recording and both automation-write modes off. The bank target, track UUID, lane and timeline identity, owning project/context lifecycle and model thread are checked before and after the native call.
- **Overlaps:** a create, copy, move or resize whose range overlaps another clip on the lane is refused (`arranger_overlap/not_applied`). Touching ends are allowed. Nothing is overwritten or trimmed.
- **Results:** `clip` (after), `previous` (edits), the whole lane `clips`, `verification:"native_timeline_readback"`, `nativeUndo:true`, `undoGroupingVerified:false`.
- **Unknown outcomes:** a readback mismatch after dispatch is `arranger_verification_failed`. It and any other post-dispatch failure have outcome `unknown` and quarantine further arranger writes (`unresolved_mutation`) until `extension.restart`. Reads stay available. Never retry.
- **Identity:** `clipIndex` is an index into a fresh list, guarded by start and name. It is not a persistent clip identity.
- **Aliases:** renaming an alias clip renames the shared content (the name lives on the clip content).

**Not covered:** automation clips, take/comp lanes, other clip lanes, group-track (meta) clips, effect/master tracks, splitting, fades, looping or other clip properties, audio file placement, cross-track copies, and arranger note editing after creation. Offline, every binding resolved against the inspected 6.1.4 JAR. Native behavior is established only by the native tests listed in VERIFICATION.

### Read-only primary modulators

These three methods use the same generic strict catalog, CLI, MCP and JSON transport. They require no selection, direct-parameter binding, context token or Grid write authorization.

| Method | Exact params |
|---|---|
| `modulators.capabilities` | `{}` |
| `modulators.list` | Required `parent:DeviceParent`; optional integer `offset`0–100000 (default0), integer `limit`1–128 (default64) |
| `modulators.parameters.get` | Required `parent:DeviceParent`, canonical current UUID `modulatorId`, exact string `parameterId` of0–1024 UTF-16 units |

`DeviceParent` has exactly canonical UUID `trackId`, integer `deviceIndex`0–15 and nonempty `expectedDeviceName` of at most4096 UTF-16 units. UUID hex case is accepted, shortened syntax is not. Extra keys, explicit nulls, numeric strings, boolean-as-integer values and decimal/exponent integer tokens reject `invalid_params` before scheduling. Empty `parameterId` is valid only when it identifies a unique direct child; identifiers are case-sensitive and never trimmed. `timeoutMs` remains the standard client/envelope option, not a method param.

Discover `trackId` with `tracks.list`, then the root index/name with `devices.list`. Pass that observed address as `parent` to `modulators.list`, choose a row and its supported descriptor, and pass its **current** `modulatorId` and exact `parameterId` to `modulators.parameters.get`. Neither type UUID, raw/custom name, row index nor display label is an alias. Reacquire current UUIDs after reopening or identity changes: the native UUID can change even on the same object. Use `bitwig-agent-rpc describe modulators.list` and `describe modulators.parameters.get` for offline request examples; examples are not live identities.

Capabilities report the exact6.1.4 loaded-JAR `runtimeGate`, independent `discovery` and `stringPanelRead` objects (`available`, nullable `reason`). Top-level `available` requires runtime and discovery; `parameterReadAvailable` additionally requires the string binding. String-binding failure does not disable inventory, nor do Grid-specific binding failures determine modulator availability. `writeAvailable:false`, `nativeMutation:false` and `nativeVerification:"not_established_by_binding"` are explicit. No supported binding establishes reachable-instance, DSP, GUI or persistence acceptance.

Inventory has observed completion, `parent`, `target`, `scope:"primary_modulators_on_root_device"`, `window:{offset,limit,total,returned}`, `modulators`, `complete` and explicit `coverage`. Only the primary collection is included; secondary/nested modulators, nested components, mappings and destinations are excluded. Every primary member's object/current UUID/order and ownership are checked before and after capture; names, contents and direct-child descriptors are inspected only for the requested page. Pagination is independent observations, not a revision-consistent cursor. An offset beyond the current total returns an empty page, not evidence of an empty collection.

Each row has `index`, current `modulatorId`, raw `name`/`customName` (nullable when absent), `contentsAvailable`, `contentState`, `typeId` and `parameters`. Nonloading access returns unmaterialized contents honestly: `contentsAvailable:false`, `contentState:"unmaterialized"`, `typeId:null`, `parameters:null`; no loader, restore or materialization fallback is called. Materialized contents expose direct-child descriptors with `parameterId` (null when not addressable), `modelClass`, `supported`, and nullable `kind`/`controlFamily`. An exact native string panel with an available reader reports `supported:true`, `kind:"string"`, `controlFamily:"string_panel"`. Other children remain explicit unsupported descriptors; inventory never reads their values or string-panel values. `complete` is false for pagination, unavailable contents or unsupported children; even true covers only this bounded primary/direct scope.

The single-parameter result returns current `modulatorId`, `typeId`, exact `parameterId`, `kind:"string"`, `controlFamily:"string_panel"` and the raw native String `value`. Empty strings, whitespace and Unicode are preserved without trimming, coercion or truncation. `labels`, `shortLabel` and `display` are null, not fabricated names. The reader checks the selected value again before returning; it does not read another control's value. `readContext` includes actual `lifecycle`/`attachedContext`, `owningProjectChecked:true`, `activeApplicationProjectIdentityChecked:false` and `nativeMutation:false`. Pure reads require no scalar license/touch gate, GUI property wrapper, undo manager or lock observations; those are not inferred write permissions.

Limits apply to work, not just emitted page size:4096total primary members,256direct children per inspected materialized contents,16384direct-child visits **including capture and revalidation**,1024UTF-16 units per inspected native text/parameter ID, and240000serialized result characters. Narrowing a page may reduce inspected child work but cannot bypass the total-primary bound. Overflow returns `modulator_bounds_exceeded`, never clipped data. Unknown model/identity/ownership and duplicate identities fail closed rather than being skipped. Unavailable exact bindings, unmaterialized selected contents or invalid native text types return `modulator_unavailable`; an existing selected non-string-panel family returns `unsupported_scope`. Missing current modulator/exact child IDs return `target_not_found`; changed target, current identity, membership, context or selected value returns `stale_context`. Public root readiness/window failures retain `not_ready`/`outside_window` and existing target errors; deadlines/cancellation retain transport outcomes, not write acknowledgement.

Both data methods report `nativeMutation:false`, `nativeUndo:false`, `nativeRevisionAvailable:false`. Root targeting uses public observed index/name and native owning-track corroboration, not persistent physical-device identity. Owning project/context checks are not application's active-project identity; unobserved same-metadata replacements, native ABA, atomic model snapshots and cross-page consistency are not guaranteed. These two methods never mutate; edits are the separate methods below.

Prior 6.1.3 native coverage was limited to materialized primary Macro string panels. Those observations do not establish 6.1.4 instance coverage, unmaterialized contents, DSP/Undo/MIDI/write or whole-toolkit acceptance. Macro panels cannot establish Grid-module string-panel reachability. See the current [verification record](VERIFICATION.md).

### Device modulators: insert, set, map

Device modulators (the 43 types of a device's Modulators browser: LFO, Random, Steps, ADSR, Macro, …) on one explicit root device, typically a Poly Grid. The main use is modulating Grid module controls that have no input port (envelope times, step counts, drive, pulse width). Same 6.1.4 loaded-JAR gate; `parent` is the `DeviceParent` above. Availability is `modulators.capabilities` → `edit` (`available`, `reason`); binding availability is not native acceptance.

| Method | Params | Native operation |
|---|---|---|
| `modulators.catalog` | optional `query`, `lang`, `installationRoot` | client-side, offline: names from `<root>/Library/modulators`, category and description from Bitwig's own help files |
| `modulators.describe` | exactly one of `type`, `query`; optional `lang`, `installationRoot` | client-side, offline: per-control help (`docKey`, `title`, `description`, `documentedValues` marked unverified) |
| `modulators.get` | `parent`, optional `modulatorId` | read: every modulator (at most 64) with typed `parameters`, `outputs` and each output's `mappings` |
| `modulators.insert` | `parent`, `expectedCount`, one of `typeName`/`typeId` | the modulator browser's insertion point (`ModulatorGridInsertionPoint`, as Bitwig's own test harness uses), appended below the existing modulators |
| `modulators.delete` | `parent`, `modulatorId`, `expectedCount` | the auxiliary device grid's undoable delete (shared with `grid.modules.delete`) |
| `modulators.parameters.set` | `parent`, `modulatorId`, `parameterId`, `expectedKind` (float/integer/enum/boolean), `expectedValue`, one of `value`/`display` | the same external-controller raw write as `grid.parameters.set` |
| `modulators.map` | `parent`, `modulatorId`, optional `outputId`, `target`, `expectedAmount` (number or explicit null), `amount`, optional `transfer`, `enabled` | the public modulation add, wrapped by Bitwig in a named undo transaction |
| `modulators.unmap` | `parent`, `modulatorId`, optional `outputId`, `target`, `expectedAmount` | Bitwig's "Clear modulation" undo transaction |

`target` is `{moduleId, parameterId}` (a Grid module control from `grid.get`) or `{modulatorId, parameterId}` (another modulator's control); both must be on the same device. `outputId` may be omitted only when the modulator has exactly one output. `amount` and `expectedAmount` are in −1..1 and are never clamped: an amount beyond the target's modulation range rejects. `expectedAmount: null` means "no mapping between this output and target now" and creates one (`transfer` default `linear`, `enabled` default true); a number must equal the existing amount and changes only the amount. Changing `transfer`/`enabled` of an existing mapping rejects (unmap, then map). `transfer` is one of `linear`, `rectify_pos`, `rectify_neg`, `abs_linear`, `inv_abs_linear`, `cubic`, `inv_cubic`. Polarity is not a mapping property: it is a modulator parameter (for example an LFO's bipolar switch). Bitwig refusing a pair (for example a modulator modulating itself) rejects `unsupported_scope` before dispatch.

`modulators.get` rows carry `index`, `modulatorId`, `name`, `typeId`, `x`, `y`, `contentsAvailable`, `parameters` (the `grid.get` row shape: `parameterId`, `name`, `kind`, `value`, `minimum`, `maximum`, `options`, `display`) and `outputs: [{outputId, mappings: [{target, amount, transfer, enabled, polyphonic, scaledByAnotherSource}]}]`. A mapping `target.kind` is `grid_module` (`moduleId`, `parameterId`), `modulator` (`modulatorId`, `parameterId`), `device` or `external` (`path`, `parameterId`). Controls of other families are listed in `unsupported` and `complete` is false.

Every write needs a stopped, nonrecording, nonautomation transport and the write-context prerequisites of Grid parameter writes (undo manager idle, device lock owned by the default document context, control settable and untouched). Order: CAS (`expectedCount`, `expectedAmount`, `expectedValue`) and range checks, prepare, re-read and re-check, then one native call; nothing is retried or rolled back. Insert, delete, map and unmap verify in a later document event: exact mapping readback (amount, transfer, enabled), or membership equal to the previous list plus exactly one modulator of the requested type (insert) or minus the deleted one. A disagreement after dispatch returns `modulator_verification_failed` (or `modulator_insert_rejected` when the native insertion reported failure) with `outcome:"unknown"`; inspect `modulators.get`, never retry blindly. Results report `mutationDispatched`, `verification`, `nativeUndo`, `nativeUndoScope` and `undoGroupingVerified:false`.

Unmaterialized contents (a modulator whose device was never opened) return `modulator_unavailable` for edits. Missing modulator, output or control ids return `target_not_found`; a changed count, amount, value, membership or identity returns `stale_context`.

### Version-gated Grid controls

`grid.capabilities`, `grid.catalog`, `grid.get` and `grid.parameters.get` are private read-only Grid methods. Their schemas come from the same strict Python catalog used by CLI and MCP: extra fields, explicit nulls, numeric strings and boolean-as-integer values are rejected. The standard client `timeoutMs` option remains envelope metadata, not a Grid parameter. No implicit selected-device target is accepted.

The `0.2.0` native compatibility gate accepts only Bitwig **6.1.4** with loaded host JAR SHA-256 `77a50264156a9f79c925fa85e0456720ce157bfa10e2503d6049e2f733af4ba6`; the older `0.1.2` release retains its separate 6.1.3 gate. Matching a filename or an unrelated installed JAR is insufficient. `grid.capabilities` reports the actual gate/binding result and separates catalog, structure and typed-parameter coverage; it does not promise full coverage merely because the host version matches. Unsupported or unresolved bindings fail closed rather than trying guessed reflection names, GUI selection, installation or automatic fallback.

`grid.catalog` filters native MODULE names (case, spaces, hyphens and punctuation ignored; every whitespace-separated query word must occur in the name, so `lowpass` and `low pass` find `Low-pass`) and returns deterministically ordered `{typeId, name}` entries with a `window` reporting `total`, `offset`, `limit` and `complete`. When nothing matches, up to five nearest names (edit-distance ratio on the normalized names) come back as `suggestions: [{typeId, name}]`. An empty query includes all mapped MODULE entries; it is not a device/preset catalog. Type UUIDs identify module types, not instances in a patch. `devices.catalog` remains the separate factory-device file discovery API.

`grid.get` reuses the explicit device target: obtain `trackId` from `tracks.list`, then `deviceIndex` (0–15) and exact `expectedDeviceName` from `devices.list`. For example, the following JSON has a valid shape but its UUID must be replaced with a discovered live track:

```json
{"trackId":"12345678-1234-1234-1234-123456789abc","deviceIndex":0,"expectedDeviceName":"Poly Grid","moduleOffset":0,"moduleLimit":32,"includeParameters":false}
```

For layout, wiring and module naming, use the structure-only example above. To get one module's parameter IDs, pass `moduleIds` (1–256 current `instanceId`s, UUID case-insensitive): only those rows are returned, with parameters, without paging every module. Ids absent from the graph are listed in `missingModuleIds`; a filtered read is never top-level `complete`, and `window` counts the selected rows. Connections remain the incoming links of the returned modules. `grid.get` rows are enough for parameter CAS writes: a parameter row's `kind` and `value` are valid `expectedKind`/`expectedValue` while still current (stale ones reject `not_applied`), so `grid.parameters.get` is only for a fresh single value or a coupled boolean panel's linked parameter. None of this changes the `includeParameters:true` wire default or makes several pages atomic.

By default rows omit the obfuscated native `modelClass` of modules and ports, the per-port and per-parameter `path`, the top-level `device`/`graph` class metadata, `coverage`, `nativeRevisionAvailable` and `identityCaveat`; no write needs them. `diagnostics:true` restores them. The constant caveats they carried: coverage is mapped modules and ports only (nested children not traversed, connections are incoming links within the same graph, no native revision, unit and display readers unverified); `instanceId` is a current native UUID that changes across project reopen and must be reacquired; `localKey` and paths change after edits; the native owning-track UUID is corroborated before and after capture; device index and name remain public observations that can lag native rebinding and cannot distinguish same-track same-name replacement; there is no persistent device identity, native ABA detection or cross-request atomicity.

The result includes target metadata, modules, connections, a bounded window and explicit coverage/identity limitations. Read instance UUIDs, catalog type UUIDs and list-local keys as separate identities. Native instance UUIDs are not persistent: all seven observed module UUIDs changed on same-process project reopen while types, positions, ports, typed values and stored topology matched. Reacquire identifiers after reopening; labels and list-local keys are not substitutes for persistent identity. Unknown model types, unsupported parameter fields and excluded pages must not be interpreted as a complete graph. `includeParameters=false` requests structure without parameter values. A sequence of pages is not an atomic snapshot and no native revision is fabricated.

`window.complete` means the module page covers the current module window. Top-level `complete` additionally requires no recorded unsupported coverage: a structure-only read intentionally has `complete:false` with `parameters_not_requested`, and a full module page can still report unknown native children. Check the requested coverage and returned structure; do not require top-level `complete:true` merely to use an otherwise complete layout/wiring/name page, or mistake it for lossless native export.

Native path ancestry also changed after group insertion/save/reopen; device-local data survived, but full path strings are not stable identifiers. `target.nativeOwningTrack` reports before/after corroboration: derive the native device's nearest WSA track ancestor, apply the public channel-ID mapping (including kWY's channel alias), and compare its UUID with the requested track before graph traversal and again after capture. Missing ownership/alias/UUID rejects `grid_unavailable`; mismatch rejects `stale_context`. There is no fallback to a name or old public observation. Device position remains `public_observed_only`; this guard does not establish persistent device identity, same-track same-name replacement detection, native ABA detection or cross-request atomicity.

In `grid.get`, modules expose `instanceId`, `localKey`, `typeId`, `x`, `y`, `width`, `height`, input/output ports and optional typed parameters. Footprints use native grid units, not pixels; unavailable dimensions remain null/partial. `name` is the native effective instance name; `customName` is its raw override (empty means no override); `typeName` comes from the catalog type UUID lookup. Ports retain their keys/paths and add native `name`, including disconnected inputs. Typed parameters retain structural `path` and add local/preset `parameterId`, stored `name` and `shortName`. These identifiers and labels are not promised persistent or globally unique. Empty native names remain empty; unavailable metadata is explicit JSON null with a field-specific `unsupported` reason, never a guessed fallback. Parameter `supported` describes the typed observation, not complete metadata coverage.

With `diagnostics:true`, `device.modelClass`, `graph.modelClass`, module/port `modelClass` and (always) `editContext.ancestorUndoManager.modelClass` expose concrete native runtime classes for compatibility diagnostics. They are not stable public identifiers or permission to mutate.

Float `numericUnit` is the native definition's **unit-kind token**, not a promise that the raw number is already in that unit; use the existing native display string for presentation. Integer `displayPrefix`/`displaySuffix` are native presentation affixes. Apart from the few verified display-write units in Grid usability additions, formatter output and labels define no reversible numeric-input grammar. Context-dependent/localized UI equivalence is not universally guaranteed. Connections describe **incoming stored links to the returned modules**: each source belongs to the same graph but can lie outside the module page. Therefore an endpoint absent from the current page does not imply a broken cable. Inspect `complete`, `unsupported` and `window` (and, with `diagnostics`, `coverage`/`identityCaveat`).

Connections are **stored native-model links**, not a proven active/audio/note signal graph. Independent native inspection found Note Grid with Enable All Expressions off showing four visible cables while the model retained eight links, including disabled expression paths. The reader does not infer activation from link existence or silently filter these paths. Use the native UI/behavior as a separate oracle until activation metadata is mapped and verified.

`grid.capabilities` (with `detail:"full"`; the default is the compact summary above) exposes `gatePassed`, `available`, `binding` and `runtimeVerification` separately. `catalog`, `structure`, `nativeOwningTrack`, `typedParameters`, `display`, `moduleFootprint`, `moduleNames`, `typeNames`, `parameterNames`, `portNames`, `numericUnits`, `integerDisplayAffixes` and `parameterInspection` describe availability, coverage and binding failures. Native ownership is required for graph reads; failure disables structure/dependents, not the independent catalog. Context bindings gate parameter inspection separately without disabling existing graph reads. Descriptive metadata groups bind independently; missing labels remain null/partial. `grid_unavailable` means a required binding/observation is unavailable, `grid_bounds_exceeded` a traversal bound, and `not_grid` a non-Grid target; do not collapse these into an empty graph. Standard target/readiness/stale-context/deadline errors still apply.

The four read operations use the mapped native document dispatcher with deadline/cancellation and explicit target/ownership checks; they do not mutate the host or select a device. Both application dispatch-thread status and `Q_().isEventDispatchThread()` are checked. `Q_` returns the current scoped executor, not an executor owned by that model; ancestry and UUID checks remain separate. Read coverage does not establish parameter/topology writes or native undo. Insertion and cable writing are separately specified below.

Native names are not always inspector wording (`Hold Time` versus `Timeout`, `Clip Mode` versus `Clipping`). Nonempty FX numeric Remote Controls, native UUID races and the kWY track-alias branch lack comprehensive native coverage. Track scalar/send observations do not establish selection readability after reopen. See [coverage limits](VERIFICATION.md#coverage-limits-and-unresolved-results).

#### Inspect one Grid parameter

Use the chosen module's current `instanceId` as `moduleId` and the control's exact `parameterId`, not its display name, path or catalog type UUID. UUID hex case is accepted; parameter IDs are case-sensitive and are never trimmed. Empty IDs are valid syntax, but must still identify exactly one supported scalar, boolean panel or string panel within that module. Missing, ambiguous, moved or replaced targets reject `stale_context`; unsupported families/bindings reject `grid_unavailable`. Reacquire module IDs after reopening.

The result contains `moduleId`, one `parameter` with the same raw value/range/options/metadata semantics as `grid.get`, and `editContext`. Selection scans bounded module/child lists without serializing unrelated parameters, checks membership/identity again at completion, and preserves the existing target/ownership/cancellation/size guards. `complete`/`unsupported` describe the selected typed observation; they are not write eligibility.

`editContext` records actual model/family, lifecycle flags, same owning project/attached context, application/scoped-executor/context thread predicates, context root/initialization/disposal and current/default transaction relations. It separately reports effective licensing, the actual GUI property's descriptor-only `isSettable`, opaque `nativeCIu`, this parameter's touch state, ancestor undo-manager presence/execution/active-change/opaque `nativeICL`, and device-lock owner relations. Unavailable/absent relations retain explicit nulls, rather than being converted to false or permission. GUI wrappers may be freshly allocated; they are not used as stable binding identities.

These are **read-only observations in one native callback**, not `canWrite`, readiness, a global idle/lock guarantee, native revision, DSP acknowledgement or Undo acceptance. Even a fully populated context with true license/property flags does not authorize mutation. No private parameter setter is implemented by this method. Equality of serialized context observations is not persistence of native objects. Unknown children and unforced conflict/unavailable-context cases remain outside acceptance.

#### String panels

Exact `xMn` models (not arbitrary `btw` subclasses) appear in `grid.get` and `grid.parameters.get` as `supported:true`, `kind:"string"`, `controlFamily:"string_panel"` with their actual identifier, path and native String value. `name`, `shortName` and `display` remain null; `string_panel_labels_unmapped` and `string_panel_display_unmapped` keep coverage partial. No numeric range, options, units or dependent-coverage claim is fabricated. Observation and write support are reported separately (see `grid.capabilities.stringPanels`).

Empty strings, whitespace and Unicode are preserved exactly, without trimming, truncation or scalar coercion. The bridge's existing1024 UTF-16-unit text bound applies: null/wrong-type values reject `grid_unavailable`, overflow rejects `grid_bounds_exceeded`. This is not a native string-length limit. A graph page with `includeParameters:true` can therefore reject on an oversized mapped string that was previously opaque; `includeParameters:false` does not read parameter values. Exact single-parameter inspection does not read unrelated values.

String panels retain common lifecycle/project/context/thread/default-transaction/context-predicate/undo/device-lock observations. Their actual `btw.cfM():com.bitwig.ramona.core.ESe` value property supplies descriptor-only `isSettable`; scalar license/touch are inapplicable, reported null with `scalarLicenseTouchApplicable:false`, as for boolean panels. False settable/non-writable context observations do not prevent otherwise valid reads. Unlike boolean panels, no coupled scalar consumer is required or reported.

`grid.capabilities.stringPanels` separately reports exact native string-panel binding coverage and inspection availability (`inspectionAvailable`), and the write operation as `writeAvailable` (with `writeReason` when false): the write binds independently (`btw.hUR(String):void`, final public, declared on the string-panel base `btw`) behind the same exact 6.1.4 host version and JAR-hash gate, and its failure leaves string reads, scalar and boolean-panel support intact. The compact `grid.capabilities` reports it as `writers.stringPanels`. Binding does not establish runtime acceptance; live string-panel GUI/selection/persistence checks remain separate.

A string-panel write is `grid.parameters.set` (single or batch entry) with `expectedKind:"string"`, a JSON string `expectedValue` (exact current text) and a JSON string `value`, each at most 1024 UTF-16 units, empty allowed, preserved verbatim (no trim, normalization or coercion); `display` is not valid with string kind. It uses the same kind of checks as the boolean-panel path (without a coupled scalar and without the scalar-specific parameter guard): native binding, kind/text compare-and-set before any no-op, the common edit-context/lifecycle/skip-predicate writability checks, dispatch, deadline check, context guard and an exact native readback; an unobserved requested text is `grid_verification_failed`/`unknown` (never retried or rolled back). The native operation is the Undo-aware "Change Value" model change; Undo grouping is not verified. Results carry `previousValue`, `requestedValue`, `mutationDispatched`, `verification:"exact_native_string_panel_readback"` (or `already_matched`) and no coupling fields. A scalar request aimed at a string panel rejects `stale_context`/`not_applied`, and a string request aimed at another kind likewise. The Label module displays the module name, not a string panel; set it with `grid.modules.rename`.

#### Step tables

Exact `imU` models (the `FDM` float array behind Steps, Pitches, Gates, Probabilities and Accents) appear in `grid.get` and `grid.parameters.get` as `kind:"steps"`, `controlFamily:"step_array"` with `parameterId` (the native identifier, possibly empty), `values` (the first `stepCount` entries, the module's `STEPS` value; `full:true` returns up to 256), `arrayLength` (native declared length; the schema default is 256 but 64 was observed natively on 6.1.4 for all five modules, so it is not tied to `STEPS`), `stepCount` (null with `step_count_unavailable` if `STEPS` is unreadable; then 64 entries), `valuesComplete`, `minimum` -128 and `maximum` 128. A native array shorter than its declared length reads zero-padded. Entries are 32-bit floats printed in their shortest decimal form. The reported -128..128 `minimum`/`maximum` is only a finite sanity bound (the shared native generators and transforms work in -1..1), not a per-module range; writes are never clamped. Natively observed on 6.1.4 (Poly Grid, values set in the UI and read back): Pitches values are in Grid pitch units, Gates are 1/0, Accents are 0/0.5/1, Probabilities are 0..1. Steps unipolar/bipolar was not part of that observation. Triggers has no step array.

A write is `grid.parameters.set` (single or batch entry) with `expectedKind:"steps"`, `expectedValues` (1–256 entries compared after rounding to float with the first live entries; the CAS window is its own length, bounded by `arrayLength`, not the live `STEPS`, so a batch that also changes `STEPS` stays all-or-nothing at preflight; normally pass the prefix from `grid.get`), `values` (1–256 entries within -128..128, not longer than `expectedValues`; rejected `invalid_params` otherwise) and optional `full`. It replaces the whole native array with `values` patched in at step 0, so every other entry stays unchanged, through the recorded `FDM.FzB(float[])` change, behind the same version and JAR-hash gate, CAS, context guards and exact whole-array readback as string panels (`grid_verification_failed`/`unknown` on mismatch, never retried). Results carry `previousValues`, `requestedValues`, `verification:"exact_native_step_array_readback"`. Undo grouping is not verified. `grid.capabilities.stepArrays` reports `inspectionAvailable` and `writeAvailable`.

Child models that hold no user data (`BgP`, `Kiy`, `HQh`, `L1`, `uUS`, `fwH`, `qzH`, `Znu`: engine feeds, indicators, display state) are classified internal: they are not listed and not unsupported (module `internalChildren` counts them; `diagnostics` lists them as `reason:"internal_child_model"`), so `complete` reflects only real gaps.

#### Device voicing

`grid.voicing.get` reads the device's voice model (`xlG.Mb2()` → `jBG`): `voices` 1–64, `voiceStacking` 1–16, `monoMode` `true_mono`|`digi_mono` (native TRUE_MONO / ALTERNATING_VOICES), `retriggerMode` `never`|`on_note_on`|`always`, `notePriority` `last`|`high`|`low`, `legatoGlide`, `stealSameKey`, `allowOverlappingNotes`, and `mode` (`poly` when `voices` > 1, else the stored `monoMode`; mono is `voices` 1, not a separate switch). Natively observed on 6.1.4: a fresh Poly Grid reads `voices` 1, `monoMode` `true_mono`; setting `voices` 4 with `voiceStacking` 2 and back read back exactly with `changedUnrequested` empty. Only Poly Grid has the model: Note Grid and FX Grid return `supported:false` with a reason, and the write rejects `unsupported_scope`.

`grid.voicing.set` takes `expected` (exact current values, at least every field in `set`; extra fields are more preconditions) and `set` (at least one field). Stale expectations reject `not_applied` before dispatch, even for a no-op; nothing is clamped. Fields are written in a fixed order through the final recorded `SOn` setters, then read back exactly; `changedUnrequested` lists other fields the native change moved. Same stopped/nonrecording guards, context checks and unknown-after-dispatch rule as the other Grid writes; undo grouping is not verified. `grid.capabilities.voicing` reports availability.

#### Define Remote Controls pages

`devices.remote.define` gives a Grid device a named Remote Controls page whose knobs drive chosen scalar Grid parameters (for example a `Macros` page over the `VALUE` parameters of eight Value modules), shown in the device panel's Remote Controls page list. Bitwig generates one page per Grid module that has parameters, but none collecting arbitrary modules; this fills that gap without the UI's map mode.

Model (6.1.4, same version and JAR-hash gate): the device's Remote Controls host (`xlG.AgD()` → `pnr`) lists pages in the order **preset pages** (`LQR.BNq()` → `sZK`; "stored in the current preset"; a serialized field of the device's Remote Controls host), plugin pages, device pages (`BQF.fFs()` → `riz`), chain pages, one page list per Grid module (named after the module) and modulator pages. Only preset pages are created, edited or deleted: they are what the UI's "Add New Page" and the controller API's `createPresetPage` create, and the only list that can hold Grid module parameters. The page eligibility predicate (`vNq.cfM(v3U)`, also used by the UI's map mode) admits, on a device page, only parameters whose nearest `yzd` ancestor is the device (a Grid parameter's nearest is its module), while a preset page admits any remote-mappable parameter whose nearest device is the page's device.

`slots[k]` is slot `k` (0–7). Each non-null entry names a module by current `moduleId` or by exact unique effective `moduleName` (as `grid.get` shows it), the exact `parameterId`, and an optional `label` (at most 256 UTF-16 units) shown instead of the parameter's own name; empty or absent keeps Bitwig's default name. Only scalar parameters (`float`, `integer`, `enum`, `boolean`) map; boolean/string panels and step tables reject `unsupported_scope`. The same parameter in two slots rejects `invalid_params`. Null and trailing absent entries leave the slot empty.

`mode:"create"` (default) refuses with `page_exists` if any page already shows that name. `mode:"replace"` edits the one preset page of that name in place, mapping slots that differ (target parameter or label; a label-only change clears and remaps the slot, since the native map ignores an unchanged target), clearing slots the request leaves empty and keeping matching ones; with no such page it creates one. A same-named device, module or plugin page is `page_exists` in both modes; several same-named preset pages are `stale_context`. Names are compared as the page list shows them: module pages by module name, unnamed preset/device pages by their native fallback (`Perform` for the first preset page, else `Page <position>`).

Before any dispatch the writer resolves every slot (module, parameter, scalar kind, native mappability: a remote-mappable `bDH` whose nearest device is the target), checks an existing page's own eligibility for each parameter, the device's licence (the native create does nothing for an unlicensed device: `unsafe_state`), and the same document-context guards as the other Grid writes, applied to the device (owning project and attached context, default transaction, skip predicate, idle undo manager, device lock owner); transport must be stopped and nonrecording. Then it calls the native operations the UI uses, each its own named undoable change: `riz.OzW()` ("Create Page", inherited by `sZK`; it also selects the new page in the device panel), the public final recorded name setter `faW.cfM(String)`, `vNq.cfM(int, String, SYo)` with `iok.TMF(bDH)` ("Map Remote Control Slot", what the UI's map mode reaches through `vNq.cfM(int, v3U)`) and `vNq.MRY(int)` ("Delete Remote Control"). A new page's own eligibility is rechecked before its first slot is mapped.

The result reads back exactly: the page is in the preset-page list and in the visible page list, its stored name is `pageName`, and every slot holds the requested native parameter object and label (or is empty). It returns `{status:"observed", page:{name, kind:"preset", visible, pageIndex}, created, slots:[{moduleId, moduleName?, parameterId, label}|null ×8], operations:[{op:"create"|"rename"|"map"|"clear", slot?}], pages:[visible page names], mutationDispatched, verification}` with `verification` `exact_native_remote_page_readback` or `already_matched` (nothing dispatched). `pageIndex` is the index in the device's visible page list, the list `devices.remote.get` observes (after its next host flush), so `devices.remote.page` can select it. Each operation is a separate Undo step (`undoGroupingVerified:false`). After the first dispatch any failure, including a readback mismatch, is outcome `unknown` (`grid_verification_failed` for readback): nothing is retried or rolled back; inspect with `devices.remote.get`. A new page that refuses a slot natively is left created, named and empty (`unsupported_scope`/`unknown`); remove it with `devices.remote.deletePage`.

`devices.remote.deletePage` deletes the one preset page of that name through `riz.cfM(FyM)` ("Delete Page") under the same guards and verifies it is no longer listed; a device/module/plugin page of that name rejects `unsupported_scope`, a missing name `stale_context`. `grid.capabilities` reports `remotePages` (compact: `writers.remotePages`). Bindings were resolved offline against the gated JAR; live Bitwig behaviour (visibility in the dropdown, Undo, save/reopen) is not established by these checks.

#### Write one Grid parameter

For a supported scalar or boolean panel, take the target from a recent `grid.get` parameter row (or `grid.parameters.get`). Send the explicit device target, `moduleId`, `parameterId`, the row's `kind` as `expectedKind`, its raw `value` as `expectedValue`, and the requested raw `value`. The writer compares them with the live value and rebinds itself: a stale expectation rejects `stale_context` with outcome `not_applied` before any dispatch, even for a no-op, so no `grid.parameters.get` is required first. String panels take `expectedKind:"string"` with string `expectedValue`/`value` (see `grid.capabilities.stringPanels`). The server independently rebinds and rechecks live context; earlier `editContext` JSON is never authorization.

**Batch.** `writes` is 1–64 full single writes on one device (a repeated `moduleId`/`parameterId` pair rejects `invalid_params`; the single-write fields must then be absent). Every entry's live CAS, range, option and context checks run first; if any fails nothing is written and the call rejects `not_applied` with a message naming each failing entry (`#index code: reason`). Then entries dispatch in order, each as the ordinary single guarded write. After the first failure or unknown outcome the remaining entries report `not_dispatched`; nothing is retried or rolled back. The result is `{status:"observed", batchStatus, completion, written, writes:[{moduleId, parameterId, status, previousValue, value, error?, previousCoupledParameter?, coupledParameter?}]}`; a boolean-panel entry carries the same coupled-parameter observations as a single panel write. Entry `status` is `applied`, `already_matched`, `failed` (known, not dispatched), `unknown` or `not_dispatched`; overall `batchStatus` is `applied`, `partial` (some applied, a later entry failed), `failed` (nothing applied) or `unknown` (`completion:"unknown"`: inspect state before any further write). Boolean-panel entries are preflighted too (support, linked bipolar parameter, context), so an unresolvable coupling writes nothing. Any error after an entry's own dispatch makes that entry `unknown`, whatever the error code. A first-entry failure that dispatched nothing is thrown as the ordinary `not_applied` error.

| Kind | Accepted raw values |
|---|---|
| `boolean` | JSON `true`/`false` only, not0/1 |
| `integer` | Signed32-bit JSON integer tokens, within the actual native range |
| `enum` | Signed32-bit JSON integer tokens matching an actual listed option **value**, not its list position |
| `float` | Finite JSON numbers within native range; integer tokens must be exactly representable as binary64 |

Numeric strings, nulls, booleans-as-numbers, fractional/exponent tokens for integer/enum, nonfinite numbers and silent clamping are rejected. The TCP decoder preserves number lexemes before domain validation. Float fractional/exponent values use finite binary64 conversion; numeric positive/negative zero compare equal. Kind and exact raw-value preconditions precede even a no-op. A mismatch rejects `stale_context`; range/options/type failures reject `invalid_params`.

For scalar controls, the native editor invokes only the exact public final raw controller operation `aLw.UNj(double):void` for mapped rce/Hgx/iS3/Lig/RuU/nhW implementations. Exact Hgx→rXz→rce inheritance is checked; other subclasses are not automatically authorized. It adds no engine-input setter, parser, transaction wrapper, gesture/touch management, lock acquisition, retry or rollback. Live ownership/membership/lifecycle, project/context/default-transaction, thread, license/property, touch/undo and device-lock-owner relations are checked on the document callback before dispatch. The public controller's safely published stopped/nonrecording/nonautomation observations and monotonic epoch also reject observed changes/ABA while queued or completing. This is **observed safety**, not atomic native transport/recording exclusion.

For Hgx controls such as Attenuate VALUE, raw `0.5` means native `50%`, not raw `50`. Bipolar mode changes the live raw minimum; the same descriptor may change in place. Range is reread before dispatch, with no clamping or automatic mode change. A numeric write does not toggle bipolar/STEREOIZE or flatten panel references into a compound value. Changing bipolar mode is a separate native operation that can coerce a negative value to zero.

Results contain the selected actual `parameter`, `previousValue`, `requestedValue`, `mutationDispatched` and `verification` (`exact_native_model_readback` or `already_matched`), plus the explicit `target` identity. A guarded already-matching request never invokes the setter. `nativeMutation`/`nativeUndo` indicate that the undo-aware native controller operation was invoked. Constant limits no longer echoed per result: Undo grouping is not verified, there is no engine acknowledgement, safety is observed stopped/nonrecording/nonautomation rather than atomic transport exclusion, and model readback is not DSP acknowledgement. After dispatch, native failure, timeout/cancellation, serialization or late target/safety failure has outcome `unknown`. Inspect actual state before another write.

`grid.capabilities.parameterWrite` is independently gated; unavailable writer bindings do not disable reads. Its `nativeUndoAwareOperation` describes the setter route; it exposes no dedicated Undo command or grouping guarantee. `graphWrites` describes the separately gated insertion, module move/delete/rename and single-input connection surface below, not scalar parameters or full topology editing. The capabilities call itself remains read-only.

Representative scalar observations do not establish all-module write behavior, disabled Note Grid DSP, atomic native transport exclusion or general undo grouping. See [coverage limits](VERIFICATION.md#coverage-limits-and-unresolved-results).

#### Boolean panels with a coupled scalar

The existing `grid.parameters.get/set` methods also support exact BMo boolean panels, not arbitrary BMo subclasses or every native GUI toggle. Discovery reports `kind:"boolean"`, `controlFamily:"boolean_panel"` and the panel's own `parameterId` (observed `BIPOLAR` on Attenuate). Unmapped labels/display remain explicit null with unsupported reasons. The panel is not a scalar controller: its `effectivelyLicensed` and `parameterTouched` are null, with `scalarLicenseTouchApplicable:false`, not invented false/true permission.

Inspection and writing require one uniquely referenced, exact Hgx control in the same module. `get` adds `coupledParameter` and `coupledEditContext`; the panel and scalar retain separate native identity/context checks. The writer uses the panel's public final `xqx.MRY(boolean):void`, never the numeric setter. It checks common panel context/property/undo/lock constraints plus the linked scalar's license/touch/context constraints. That linked-scalar policy is conservative toolkit policy, not a claim that native GUI code applies the identical guard.

Supply fresh `expectedKind:"boolean"`/`expectedValue` and a JSON boolean `value`. This is one panel CAS, not a two-control atomic transaction. The response adds actual `previousCoupledParameter` and `coupledParameter`, so a native range change or value coercion is visible. It reports `verification:"exact_native_boolean_panel_readback"` on a dispatched match or `"already_matched"` without a setter. Turning BIPOLAR off may clamp a negative VALUE to zero; turning it on is not a request to recover an earlier negative value. Scalar writes still reject values outside their current range.

`grid.capabilities.booleanPanels` reports binding, inspection/write availability, operation and coupling requirements separately. No new RPC name, implicit GUI fallback, retry, rollback, Undo-group guarantee or DSP acknowledgement is introduced. Bounded coupled-control observations are not universal grouping, DSP acknowledgement or whole-project preservation; prior failed selection and audio-alignment criteria remain failures as summarized in [VERIFICATION](VERIFICATION.md#coverage-limits-and-unresolved-results).


#### Insert one catalog Grid module

`grid.modules.insert` requires `trackId`, `deviceIndex`, `expectedDeviceName`, `x`, `y` and exactly one of `typeId`/`typeName`, or `modules` instead of the last three. Discover the device target through `tracks.list`/`devices.list` and the canonical MODULE type UUID through `grid.catalog`; UUID hex case is accepted, but shortened UUID syntax, names, instance IDs and arbitrary resource paths are not substitutes. Coordinates are absolute native grid units, not pixels/deltas; decimal/exponent tokens, booleans, strings, nulls and out-of-int32 values reject. There is no implicit selection, default position, automatic connection or retry. `typeName` may replace `typeId`; see the batch form below.

The adapter verifies exactly one matching MODULE catalog entry, resolves its existing resource via native `TL.cfM(UUID):File`, constructs the public unnamed-package adapter, then calls `g2L.cfM(String[],ZuD)`. This normal loader can complete synchronously on a cache hit or asynchronously; parsing/conversion is not a pure read. On delivery, it requires exactly one mapped, detached, nondeleted, unowned module with the requested type and a fresh instance UUID. It rechecks the unchanged destination membership/identity/type/footprints/layout, target/owning-track/project/context, observed stopped/nonrecording/nonautomation epoch, native placement prerequisites and deadline before invoking public `IcG.cfM(Collection,int,int,false,null)`. It does not use the String convenience-placement overload or fabricate a module from catalog metadata.

The destination must contain at most127modules before loading and again before placement, so the inserted graph has at most128. Existing and incoming footprints must be positive; endpoints and prospective maximum-X plus cumulative widths must fit signed32-bit, and the entire occupied Y span must be at most65536 before native placement/layout allocation. Incoming dimensions are checked after loading the real module: a geometric rejection can therefore report `outcome:"unknown"` even though placement never ran. Do not infer `not_applied` from an error message mentioning pre-allocation bounds. These limits are stricter than validating each coordinate independently. Native collection placement may reflow the whole graph rightward, including the inserted module; insertion does not inherit the move operation's occupied-anchor rejection. A later document event requires exactly one added module, unchanged survivor identities/types/footprints, unchanged Y and nondecreasing X relative to old/requested anchors. The inserted module keeps its identity/type/row but may change footprint once attached (variable-size modules such as Merge and Sum size themselves); the after layout re-checks every footprint and bound. The returned diff (or `graph:"full"`) comes from the full bounded actual membership/layout and mapped incoming connections, without parameter values; opaque children and unmapped coverage remain excluded.

Results include `operation:"insert"`, `moduleId`, `typeId`, `requestedPosition`, `actualPosition`, `matchesRequested`, `loaderDispatched`, `placementDispatched`, `mutationDispatched`, `nativeMutation`, `nativeUndo`, `nativeLifetimeSettled:true`, `verification:"later_document_event_bounded_native_graph_observation"` and the topology diff above (`modulesAdded` holds the new module's row with ports). `mutationDispatched` starts at loader launch, not placement: conversion has native effects. `nativeLifetimeSettled` means the tracked native lifecycle reached healthy later-event settlement, not atomic commit, all future work drained, audio acknowledgement or persistence. The new `moduleId` and its port keys come straight from the row; parameter IDs need one `grid.get` with `moduleIds`.

The first delivered callback is claimed exactly once **before** checking the RPC deadline/future/target. Rejected placement invokes the delivered native completion's Exception overload once; accepted placement invokes its success overload only after native placement returns. The adapter uses `bTA(null)` so outward notification cannot precede native rejection cleanup, and returns normally for native captured-context pop. Native cleanup is conditional detached-object cleanup, not guaranteed full release or rollback. Duplicate delivery, early error without cleanup acknowledgement, cleanup/placement/callback failure or failed settlement poisons admission; a missing terminal callback leaves it pending. No cancellation handle or timeout-as-cancellation promise exists.

Native lifetime settlement is independent of RPC completion, timeout, disconnection and extension close: a later native document event checks target/context and actual layout before releasing its reservation. It does not depend on controller scheduling or a live request deadline. A settled lifetime is not re-poisoned solely because later JSON/result delivery fails. After loader dispatch, failure/timeout/late request rejection has outcome `unknown`, even when placement was rejected and native cleanup ran; inspect actual state rather than retrying.

`grid.capabilities.moduleInsert` separates `bindingAvailable`, admission-aware `available`, and `bindingIdentity` from native acceptance. Loaded-class inspection uses `Class.forName(...,false,actualExtensionLoader)`, actual Class equality/public signatures and CodeSource equality; it constructs nothing and invokes no resolver, conversion or insertion. Its `runtimeConversionVerified:false`/`runtimeInsertionVerified:false` are inspection-scope facts, not a historical test ledger. Binding inspection does not exercise construction/conversion or insertion.

Native insertion coverage is bounded, not an all-type acceptance claim. In particular, later healthy state or musical measurements cannot authorize continued writes after an unknown outcome. Prior failed insertion criteria remain failures; see [VERIFICATION](VERIFICATION.md#coverage-limits-and-unresolved-results).

#### Shared topology lifecycle admission

Insert/move/delete/rename/connection editors share `GridTopologyQuarantine`: a String-only process marker in `System.getProperties()` (`dev.bitwigagent.grid.topology.native-lifetime.v1`), synchronized on that Properties object. It stores idle, pending-owner UUID or quarantined state, never extension/native object references. It therefore spans ordinary extension classloader replacement in the same JVM; restarting only the extension does not clear pending/quarantine. It is **not isolation from hostile replacement/removal of System properties** and is not a project revision lock or atomic native transport permission.

Pending, quarantined, malformed or inaccessible state fails admission closed. `topologyAdmissionBlocked` includes pending state; `topologyQuarantined` is separately reported; `topologyQuarantine` names the origin and the recorded detail (operation, trackId, moduleId, error). Two quarantine kinds: **native failure** (native exception, early error, duplicate/unexpected callback, cleanup failure, reader/binding failure) is sticky until a JVM restart; **settlement mismatch** (the insertion's callbacks returned normally but the later graph check disagreed: `grid_verification_failed`, `stale_context`, `unsafe_state`, which can mean a pending placement list, busy undo or another Dt, or `grid_bounds_exceeded`) is released only by `grid.topology.reconcile` re-verifying the recorded device (same track and same native Grid) and observing no pending placement, idle undo and the default Dt; never by time or a later read. A late callback after a timeout is rejected, cleaned and settles by itself (pending until then). Normal insertion settlement releases only its matching owner; ordinary synchronous topology invocations reserve/release around native invocation and poison on synchronous failure. Prelaunch rejection releases its reservation. Reads and scalar writes remain independently gated. Missing settlement or a native-failure quarantine requires full Bitwig JVM restart and state inspection; restart does not prove rollback or cancel work already dispatched. Later unrelated native failures are not globally detected.

**typeName and batch.** `typeName` resolves against the native catalog before anything loads: exactly one MODULE entry must match (exact string, then case-insensitive exact, then normalized name; first step with a hit decides); zero or several reject `not_applied` (`invalid_params`) listing candidates (matching names, else nearest names; ambiguous entries with their `typeId`s). `modules` (1..16, one device) first resolves every type, checks catalog membership, destination count plus the batch (at most 1024) and int32/y-span limits of the requested anchors; any failure rejects `not_applied` naming each failing entry and inserts nothing (module footprints are only known after loading, so a footprint-dependent rejection happens after that entry's loader dispatch: the batch then ends `unknown` like a single insert, and a clean pre-placement rejection releases the topology quarantine). Entries then run in order through the ordinary single-insert path, each settling before the next starts (a later insert can push earlier modules right, so give anchors with that in mind), and stop at the first failure, unknown, or when the time left is below max(1.5 s, 2 x the slowest entry so far) (`partial`, `stopReason:"deadline_margin"`, diff kept); later entries report `not_dispatched`. `slowestEntryMs` reports the slowest settled entry. Per-entry `actualPosition`/`matchesRequested` are refreshed from the final graph, so they agree with the diff and are valid `expectedX`/`expectedY` for a follow-up move. The result keeps `status:"observed"` and adds `batchStatus` (`applied`, `partial`, `failed`, `unknown`), `completion`, `written`, per-entry `modules` (`typeId`, `requestedPosition`, `status` applied/failed/unknown/not_dispatched, `moduleId`, `actualPosition`, `matchesRequested`, `error`) and one topology diff for the whole batch. Any failure after an entry's loader dispatch is `unknown`: the topology quarantine applies as for a single insert, no diff is returned and nothing is retried. A failure before the first dispatch is an ordinary `not_applied` error.

#### Topology write results

Insert, move, delete, rename and connection writes share one result shape. The server captures the bounded graph (no parameters) before and after the edit and returns, by default, the **diff**; `graph:"full"` returns the whole bounded after-graph instead (rows omit native `modelClass`/`path`). Diff fields are absent when empty:

| Field | Meaning |
|---|---|
| `modulesAdded` | Full rows (`instanceId`, `typeId`, `name`, `customName`, `x`, `y`, `width`, `height`, `inputs`, `outputs`) for new modules; ports are included so an inserted module can be wired without another `grid.get` |
| `modulesRemoved` | `{moduleId, typeId, name}` |
| `modulesMoved` | `{moduleId, from:{x,y}, to:{x,y}}`, including modules moved by native reflow |
| `modulesRenamed` | `{moduleId, from, to, name}` with raw `customName` and the new effective `name` |
| `connectionsChanged` | `{target:{moduleId,portKey}, from, to}` with `null` for disconnected; any input anywhere in the graph, so native repair side effects are visible |
| `moduleCount` | Modules after the edit |
| `graphComplete:false`, `graphUnsupported` | Present only if native coverage was partial (`parameters_not_requested` is not such a limit) |

The operation fields (`operation`, `moduleId`, positions, names, `previousSource`/`actualSource`, `matchesRequested`, `mutationDispatched`, `nativeMutation`, `nativeUndo`, `verification`, the insert lifecycle flags) and the explicit `target` identity are unchanged. Constant disclosures no longer repeat in every result and apply to all of them: `nativeUndoScope` (native undo-aware operation, grouping/commit unverified), `undoGroupingVerified:false`, `engineAcknowledgement:false`, `safetyScope` (observed stopped/nonrecording/nonautomation, not atomic transport exclusion), `contextScope` (same project root/default transaction/idle undo/lock-owner observations, not atomic permission), `graphScope`/`projectScope` (the bounded graph holds modules, ports and same-graph sources, not DSP, opaque nested children or project-wide routing), `observationScope` (an ordinary later event after normal end-event drain, not universal cleanup) and the maxima (1024 modules, occupied Y span 65536).

#### Move or selectively delete a Grid module

Discover a fresh `instanceId` and native `x`/`y` with `grid.get`; retain the same explicit device target. For `grid.modules.move`, supply those positions as `expectedX`/`expectedY`, and absolute destination `x`/`y`. All four must be signed32-bit JSON integer tokens: decimals, exponent tokens, booleans, strings and nulls reject, without coercion or clipping. CAS is checked before a same-position no-op. Missing IDs reject `stale_context`, including repeated deletion; neither operation accepts implicit selection or catalog type IDs.

Movement passes one actual singleton List and `copy=false` to the native absolute-anchor operation. An anchor anywhere inside another module's half-open footprint rejects before dispatch; a new rectangle overlapping another module while its anchor is outside that footprint can trigger **native whole-graph rightward reflow**. Unselected modules may move, and the selected module's actual X can differ from the requested X. This toolkit does not implement another layout algorithm. Deletion uses the native selective List operation, including bypass/reconnection and full-graph cleanup; it is not simply removing incident cables and is never clear-all.

Both editors require complete bounded module membership (maximum128), positive native dimensions, checked int32 endpoints/translation/cumulative horizontal bounds and occupied vertical span at most65536. They independently recheck stopped/nonrecording/nonautomation observations and safety epochs, live device/graph ownership, every participating module's attachment/project/lifecycle, initialized context/root/default transaction, idle undo observations, device-lock owner, graph native veto and project closing/saving flags. Parameter-specific license/settable/touch rules are not transplanted. These observations do not establish global transaction idleness, a revision lock or atomic permission.

Native callbacks cannot finish the RPC before native close. After native return, a later actual document event re-resolves the target, checks all survivors and serializes their full bounded layout and mapped incoming connections. Move observations must preserve every unselected Y, selected requested Y, and X at least the original/requested baseline; incompatible results are unknown, not successful reflow. The returned diff (or `graph:"full"`) omits parameter values and retains explicit opaque-child/coverage limits.

Results expose `operation`, `moduleId`, `previousPosition`, `mutationDispatched`, `nativeMutation`, `nativeUndo` and `verification` (`later_document_event_bounded_native_graph_observation` or `already_matched`), plus the topology diff. Move adds `requestedPosition`, `actualPosition`, `matchesRequested`; delete adds `removedModuleId` and `removed:true`. Native undo-aware dispatch is not proof of one-call/one-Undo grouping, commit, DSP or persistence.

Unexpected synchronous native invocation/callback failure quarantines the shared insert/move/delete/rename/connection editors through the process guard described above; reads and scalar writing remain independently gated. The translated failure retains its actual cause chain; it is not rollback evidence. Preflight rejection does not quarantine. Inspect `topologyAdmissionBlocked`, `topologyQuarantined` and actual state; ordinary extension classloader replacement is not a reset. Native failure, timeout, late context/safety/verification or serialization failure after dispatch returns `unknown`, never an automatic retry/rollback. `moduleMove`/`moduleDelete` report independent availability and limits.

Native move/delete coverage does not establish sample/null equivalence, disabled Note Grid DSP, general Undo grouping, race safety or injected-failure behavior. An original relative-envelope criterion failed six of 48 near-silent windows; a later absolute-error description is not retroactive passage. See [coverage limits](VERIFICATION.md#coverage-limits-and-unresolved-results).

#### Rename one current Grid module

`grid.modules.rename` requires exactly the three explicit device fields, a canonical current `moduleId`, and both `expectedCustomName` and `customName`. Copy `moduleId` from `grid.get.instanceId` and the expected raw string from that row's `customName`. Effective `name`, catalog `typeName`, type UUID, local key, path, position and GUI selection are not substitutes. No batch or selected-module fallback is provided.

Both name fields are strict JSON strings of at most1024UTF-16 code units; empty and whitespace-only strings are allowed and preserved. There is no trimming, stringification, truncation or special treatment of `"false"`/`"null"`. Null, omitted values and other JSON types reject `invalid_params` before enqueue. Empty `customName` resets the native override; its effective fallback is independently read, not filled from the catalog. Raw CAS rejects `stale_context` even for an otherwise matching no-op.

`moduleRename` has an independent availability gate requiring the exact declared public-final `com.bitwig.flt.document.core.master.device.Dgc.iHb(String):void` inherited by a real native `rSf`, raw/effective-name readers, actual owning device/track and shared topology context. Unrelated parameter/display/catalog/footprint bindings do not authorize or disable this name setter. At most128actual mapped modules are admitted; native names are bounded too. No move-only occupied-span limit, fake Grid owner, scalar setter, protected UI property or copied UI outer transaction is used.

The writer revalidates the requested current UUID/object membership, complete bounded member identities, native owning target and project/root/default-Dt/idle-Undo/lock-owner observations before dispatch and on a later document event. Controller delivery also rechecks explicit target epochs and stopped/nonrecording/nonautomation safety. These observations are not native atomic permission, a revision lock, DSP acknowledgement or detection of invisible same-name device replacement.

A changed request dispatches exactly one native setter; an authorized no-op dispatches none but still performs context, CAS and later observation. Success returns `operation:"rename"`, `moduleId`, `previousCustomName`, `requestedCustomName`, `actualCustomName`, `previousName`, `actualName` and the topology diff (or `graph:"full"`, without parameters). The first three name fields describe raw override semantics; effective before/after names are reported separately. Changed verification is `later_document_event_bounded_native_graph_observation`; no-op is `already_matched`. Read `mutationDispatched`, `nativeMutation` and `nativeUndo`; the constant scope disclosures are listed under topology write results.

Native property bookkeeping is undo-aware, but one-call/one-Undo grouping, equivalence to the UI's outer transaction, commit, rollback, persistence and unchanged audio are not inferred from setter return. Native invocation failure poisons the shared topology guard; unknown outcomes do not permit a blind retry. Current UUIDs must be reacquired after reopening. Controlled-source naming audio acceptance remains unproved; bounded persistence observations do not repair missing baseline controls. See [coverage limits](VERIFICATION.md#coverage-limits-and-unresolved-results).

#### Connect, replace or disconnect one Grid input

Use `grid.get` to discover the fresh destination module `instanceId` and exact input `key`. Supply them as `targetModuleId` and `targetPortKey`, together with the same explicit device target. Both `expectedSource` and `source` are **required**, including explicit JSON `null`: null means disconnected, not omitted/default. A nonnull endpoint has exactly `moduleId` (fresh canonical UUID) and `portKey` (exact output key). Endpoints must be exact members of the bounded same graph, not just objects with matching owner/key. No implicit selection, cross-graph cable, automatic retry or compensation is provided. Reacquire IDs and current state after reopening or any uncertain outcome.

The native route is public final `device.cXR.cfM(led)`, preserving the native undo-aware wrapper rather than bypassing it through a typed setter. The writer rechecks all bounded modules/ports, ownership, lifecycle, project/context/default transaction, idle undo observations, device-lock owner and observed stopped/nonrecording/nonautomation epoch. Maximum128modules and port/item bounds apply; move-only footprint/Y-span limits do not apply to cables.

Native repair can disconnect the requested source, alter other inputs or change project routing. Results report `previousSource`, `requestedSource`, `actualSource`, `matchesRequested`, `mutationDispatched` and the topology diff (or `graph:"full"` without scalar values). A native repair mismatch is a real observed result, not silently retried or relabeled success. Compare `connectionsChanged`, which lists every changed input in the graph, not only the requested one. `verification` is `already_matched` or `later_document_event_bounded_native_graph_observation`; the latter observes an ordinary later event after normal end-event drain, not universal cleanup/future-work completion, DSP acknowledgement or verified Undo grouping. The bounded graph does not certify project-wide routing preservation.

Synchronous native setter/listener/close failure triggers the shared topology quarantine. Later asynchronous native failures are not globally detected; absence of quarantine is not proof of global host health. Unknown results require inspection, not a reset/retry.

Full MIDI preservation failed in a native connection case: a sentinel note was observed at beat 1 initially versus beat 2 finally under the same 1/8-beat grid. Native mutation versus unacknowledged-window observation remains unresolved. Later first-read corrections do not retroactively pass this criterion. Rejected-cycle repair and Note Grid DSP remain unexercised; there is no generalized grouping, atomicity or project-wide-routing guarantee. Selection/sends remain partial. ### Architecture and evidence boundary

`HostBridge` validates and routes; `HostServices` owns shared proxies and scheduling. `DeviceSources` owns fixed root/layer/child addresses and continuity; one `ParameterModule` owns continuous source-specific parameter data and the shared binding/request. Other domain modules retain their own observations. Grid separates RPC/target guards, the exact-version reflective adapter, bounded model serialization, scalar/panel/topology writers and shared lifecycle admission. The boolean-panel writer reuses parameter context/serialization while retaining its distinct setter and coupled scalar checks. Insertion adds a narrow public boundary and lazy unnamed-package loader subclass, not another transport or transaction layer. Python separates strict schemas, one catalog, transport, CLI and MCP. No project mirror, planner, workflow DSL, automatic GUI fallback, implicit retry or generic transaction layer is introduced.

`ModulatorModule` separately owns root-device read RPCs and bounded serialization through `BoundedJson`; `ModulatorSnapshotReader` owns nonloading primary/direct inventory and exact-value guards. `DeviceSources` supplies the existing root authority and an invalidatable root-read ticket: controller capture/final delivery recheck public observations, while native callbacks use the published epoch/deadline without Controller API getters. Results cross queues as immutable bounded JSON, not native references. This does not change layer cold-index/discontinuity rules or public direct-parameter bindings.

`Bitwig614Runtime` is lazy/shared per `HostServices`, centralizing exact version, loaded CodeSource/hash/ClassLoader, descriptor checks and document dispatch while keeping domain errors and bindings independent. `NativeDeviceTarget`/`Bitwig614DeviceTargetAccess` share native target/track-alias/UUID corroboration; `NativeReadContext`/`Bitwig614ReadContextAccess` share lifecycle and owning-context checks. Initialization, root equality and default Dt remain observations rather than new read gates. `Bitwig614StringPanelAccess` is the shared exact native string-panel reader; Grid additionally uses its separately bound `btw.hUR(String)` write operation, which modulator reads do not. Grid retains its own edit-context, writers, quarantine and asynchronous cleanup; modulator reads do not couple to those write paths.

Offline client tests, simulated-host Java tests, transported MCP fixtures, native read-only preflight and independent musical/UI/persistence E2E are different evidence layers. Passing one does not promote another to passed. Native preflight verifies exact loopback socket ownership (including Linux IPv4-mapped TCP6 entries); project-name equality alone cannot establish which full project path is loaded.

### Launcher timing and Next Action settings

`launcher.get` and `launcher.set` take `trackId`, zero-based `slotIndex` (0..15), and the exact current `expectedClipName` from `launcher.list`. They access that native slot without selecting a clip or moving the editor cursor. The implementation requires the same inspected Bitwig 6.1.4 binary/hash as the existing private bindings; another version fails closed. A matching name is a guard, not a persistent clip UUID.

`launcher.set` accepts only supplied fields: `nextAction` (`play_next` or `stop`), `nextActionEnabled`, `nextActionLinkToLoop`, `nextActionLoopCount` (1..64), and `nextActionDelayBeats`. Times are quarter-note beats. For one complete clip loop followed by the next clip, use `nextAction=play_next`, enabled=true, linkToLoop=true, loopCount=1. Use `stop` on the last clip. Clips in a scene must have matching timing for synchronized transitions; this API does not configure every track automatically.

`clips.edit` takes the launcher selection lease. `rename`, `resize`, `color`, `transpose`, `quantize` and `duplicateContent` select the clip as the cursor clip and bind it like `notes.*` (cursor-slot equality plus track UUID), so they move the editor cursor; `delete` and `copyTo` use the slot proxies and do not. Readback per op: `rename` slot name; `resize` loop length, then play stop (`loopStart + lengthBeats`); `color` clip color within half an 8-bit step; `delete` slot empty (needs observed stopped transport, recording and automation-write off, and a clip that is neither playing, queued nor recording; else `unsafe_state`); `copyTo` (dispatched through the target slot's `replaceInsertionPoint().copySlotsOrScenes(source)`) target slot content transition and equal name; if the host renamed the copy the result is still observed with `nameChanged:{from,to}`. `transpose` shifts every channel-0 onset cell with velocity and duration kept; `quantize` keeps channel-0 onset count, pitch multiset and loop length while at least one cell moves (positions inside a grid cell are not observable, so a clip already on grid reads as unobserved); `duplicateContent` doubles the loop with the original first half of the channel-0 cells unchanged (the copied half is not read). These three read the whole loop in one window (at most 32 beats at 1/16 note) before and after: for `transpose` and `quantize` a longer loop is `unverifiable_clip`, no channel-0 onsets is `no_notes`, a transpose leaving 0–127 is `invalid_params`, all `not_applied`; `duplicateContent` has neither check and compares only the loop length and first half. Other MIDI channels and notes outside the loop are moved by the host but neither read nor range-checked. The result carries `op`, `verification` and, for those three, `compared` (note counts, pitch range, loop length, `verifiedChannel`) plus a `comparison` sentence.

`rename`, `resize` and `color` are absolute setters: an unread value returns `status:"dispatched"`, `verification:"readback_mismatch"` without quarantine, and an already matching value is not rewritten. `quantize` with `amount` 1 snaps to the host grid and is idempotent: no visible cell movement returns `status:"dispatched"`, `verification:"no_cell_change"` without quarantine. `delete`, `copyTo`, `transpose`, `quantize` with `amount` below 1 and `duplicateContent` are never retried: an unobserved outcome is `*_not_observed`/`unknown` and records the same per-slot unresolved mutation as create/import (the target slot for `copyTo`), listed by `extension.restart`; later writes on it return `unresolved_mutation`.

Writes require stopped transport with recording and both automation-write modes disabled. Native slot/clip/owning-track identity, attached project/context, model thread and deadline are checked before and after access. Each supplied field reports exact native post-write readback, and omitted settings are checked for unexpected coupling. A write is not an atomic multi-property transaction; partial failure is `unknown`, with settings and editor writes blocked by the shared launcher admission guards. Read-only inspection remains available. Do not retry unknown writes or treat a reload as evidence of recovery.

Timing (`playStartBeats`, `playStopBeats`, `loopStartBeats`, `loopLengthBeats`) and `loopEnabled` are read-only. An attempted native play-stop write was not observed during E2E validation; timing writes are therefore rejected before dispatch.

The settings adapter uses pinned model methods for Next Action and the same native timing properties as Bitwig's public Clip proxy. Returned values do not establish playback, Undo grouping, persistence, source-audio tempo/stretch behavior, or aesthetic acceptance. Audio-event source tempo and Scene naming remain separate interfaces.

Native validation on Bitwig 6.1.4: all 56 clips in a seven-scene project returned matching timing and Next Action settings. Reversible enabled false/true, action stop/play_next and loop-count 2/1 writes were independently read back. Link-to-loop and delay writes are descriptor-checked but have not yet received native mutation E2E coverage.

#### Grid usability additions

- **Catalog.** The native module catalog entry carries only id, name, kind and a resource path (`modules/<name>.bwmodule`); there is no category, tag or description, so `grid.catalog` `query` matches names only (`Low-pass`, not `Filter`). Nothing is invented on top.
- **Parameter display.** A `grid.parameters.set` single result's `parameter.display` and each batch entry's `display` is the native display string read back after the write (the same source as `grid.get`), e.g. `"2.09 kHz"`; omitted when the parameter has no observable display (boolean panels). Raw values remain the native domain; pitch-unit parameters are MIDI-note valued (Low-pass `CUTOFF` raw 84 displays `"1.05 kHz"`, 96 `"2.09 kHz"`).
- **Display writes.** A `grid.parameters.set` entry (single or batch) may carry `display` instead of `value`, with `expectedKind:"float"` and the usual `expectedKind`/`expectedValue` CAS. Exactly one of `value`/`display`. The text is a number plus an explicit unit suffix; conversion exists only for the float `numericUnit` tokens below, kept in one table (`GridDisplayUnits`). Any other unit rejects `not_applied` `unsupported_unit`.

  | `numericUnit` | Suffix | raw | Evidence |
  |---|---|---|---|
  | `hertz` | `Hz`, `kHz` | MIDI note: `raw = 69 + 12*log2(f/440)` | host rows (84 -> 1.05 kHz, 96 -> 2.09 kHz) and the native converter's `440*2^((x-69)/12)` |
  | `percent` | `%` | `raw = percent/100` | 17 recorded raw/display pairs over ranges -1..1, 0..1, 0..2 |
  | `decibel` | `dB` | `raw = dB` | one recorded pair (-96 -> `-96.0 dB`) and the native converter's `20*log10` over dB-valued raw |

  The token alone does not fix the scale (Detune has token `hertz` but a linear Hz raw; `seconds` rows follow differing power curves; `semitones_relative`/`module_semitones` have only zero pairs and stay unsupported). So the host first requires the row's current raw value to reproduce its current display under the table's model to the shown precision, else `unsupported_unit`; a current display of zero cannot confirm a scale and also rejects. The write is then the ordinary raw CAS with the converted raw value (range checked, no clamping). After the write the new display is compared with the requested text to the precision shown: the result carries `requestedDisplay` and `displayMismatch` (single result and each batch entry). A mismatch is only reported; nothing is written again.
- **Connection batch.** `connections:[{targetModuleId,targetPortKey,expectedSource,source}]` (1..32, distinct targets) on one device. Every `expectedSource`, port membership and runtime support is checked against the live graph first; any failure rejects the call with `not_applied` and writes nothing, naming each failing entry. Entries then run in order through the ordinary single-input path (each its own later-event observation) and stop at the first failure, unknown or `mismatch` (native repair left a different source; `batchStatus:"partial"`, state known, diff returned); later entries report `not_dispatched`. The result keeps `status:"observed"` and adds `batchStatus` (`applied`, `partial`, `failed`, `unknown`), `completion`, `written`, per-entry `connections` (`status` applied/already_matched/mismatch/failed/unknown/not_dispatched, `previousSource`, `actualSource`, `matchesRequested`, `error`) and one topology diff for the whole batch. A failure after an entry's native dispatch is `unknown`: the shared topology quarantine applies as for a single edit, no diff is returned (the last observed graph is not current), and nothing is retried. A failure before the first dispatch is an ordinary `not_applied` error.

#### `grid.describe`: module documentation (client-side)

Not a host method and needs no running Bitwig: it reads `<installationRoot>/resources/localization/{Module-descriptions,Modules,Categories}-resources[_lang].properties` from the local install (never copied into this package). Args: exactly one of `type` (module display name, loose spelling, or typeId) or `query` (keywords; ranked by name, keywords and description; `limit` 1..50, default 10); `lang` en|de|es|fr|ja|ko|zh (default en; missing keys fall back to English); `installationRoot` (else `$BITWIG_INSTALLATION_ROOT`, the install holding `$BITWIG_API_JAR`, then `/opt/bitwig-studio`).

`type` returns `{name, typeId, resourceId, description, keywords, category, categoryDescription, ports:[{key,name,direction,description?}], parameters:[{id,name,description?}], rawEntries, revisions?}` for the bundled 6.1.4 schema. Modules map to resource ids by normalized name (plus a small override table); port and parameter notes are matched best-effort by key/name, so a missing `description` does not mean the item is undocumented: check `rawEntries` (all resource entries under the module's prefix). A module with no resource entry has `resourceId: null`. Missing resources fail with `invalid_params` naming `installationRoot`.

#### `grid.apply`: declarative patch (client-side)

Not a host method: the Python client (MCP tool and `bitwig-agent-rpc grid.apply`) composes the guarded `grid.*` calls above; the extension is unchanged. Spec: `target` (as `D`), `modules:[{name, type|typeId, x, y, params?}]`, `connections:[{from:"module.OUT", to:"module.IN"}]` (split on the last `.`; endpoints must be declared modules; one source per input), optional `namespace`, `prune`, `pruneAll`, `dryRun`. A module's identity is its unique non-empty `customName`.

Blocks: `blocks:{name:{params?:{p:default}, modules, connections?}}` and `instances:[{block, prefix?, dx?, dy?, args?}]` are expanded client-side before any validation (no nesting). Inside a block module names and connection endpoints are local; an instance's module is named `prefix+local`, its x/y shifted by `dx`/`dy`, and a params value that is exactly `"${p}"` (also inside `{display}`/`{label}`) is replaced by the instance's `args.p` or the block default, keeping its JSON type. Top-level `connections` reach instance modules by expanded name (`"D1: osc.OUT"`). Every check below (unique names and cable targets, types, ports, footprints, display units) runs on the expanded spec; `dryRun` plans it, and the result adds `instances:[{block, prefix, modules:[names]}]`. `modules` may be omitted when instances supply them.

`{display}` seconds writes: for the (type, parameter) pairs in `SECONDS_PARAMS` (`grid_apply.py`: AD/AR/ADSR/Pluck/Comb envelopes and Delay/Mod Delay/Freq Shift+ with raw = cbrt(seconds); Logic Delay, Gate Length, Gate Repeat, Lag, Average, Curves, Segments, Slope, Follower(RF), Velo Mult, CV Out, Sampler GRAIN_SIZE, Ø Lag with raw = log10(seconds); each row carries its schema default raw/display pair as evidence, re-checked by a test) the client converts `"3 ms"`/`"0.5 s"` to a raw value (suffix `ms`/`s`, range-checked against min/max) and writes that raw value; the skip compare uses the live display's precision. Other seconds parameters (All-pass Delay TIME, Audio Out HOLD_TIME, Long Delay TIME: default pair fits neither mapping unambiguously) reject display writes offline.

Order: validate whole spec (types, port keys, parameter ids/kinds/ranges/enum labels, footprint overlaps against the schema sizes and untouched modules, `{display}` writes the host would refuse: only hertz/percent/decibel (plus the seconds table below), nonzero default display; nothing written on failure, did-you-mean in `details.problems`) and read the graph (null `customName` fails closed); delete (prune); move existing modules to x/y in a collision-free order (vacate first, cycles parked at a free anchor; bounded); batch insert by `typeId` (16), renaming each batch's applied entries immediately (so a partial batch never leaves unnamed modules; after `unknown` they are listed in `unnamedModules`); re-read and move only what native reflow displaced; re-read parameters, batch `grid.parameters.set` (64, CAS from the fresh row; equal values skipped; `{label}` maps to the option value; `{display}` skips when the live display already shows it at its own precision); re-read, batch `grid.connections.set` (32, `expectedSource` from the fresh read). Existing modules are reused (type mismatch or duplicate name rejects before any write); unlisted inputs are left alone unless `prune`, which also disconnects them and deletes modules whose `customName` starts with `namespace` but are absent from the spec (never unnamed or out-of-namespace ones). String parameters (e.g. Comment `TEXT`; at most 1024 UTF-16 units, multi-line ok) are written with `expectedKind:"string"` and the live text as CAS; equal text is skipped. Step arrays (Steps, Pitches, Gates, Probabilities, Accents) are written as `"params":{"DATA":{"steps":[1,0,0.5]}}` (or `{"steps":"${row}"}` in a block with a list arg); the parameter id is the live row's `kind:"steps"` id (the bundled schema has none, so only the module type, finiteness, 1..256 entries and -128..128 are checked offline; `arrayLength` is checked against the live row, before any write for existing modules). The grid.get reads use `full:true`; the requested entries are compared with the live prefix of the same length after float32 rounding, equal arrays are skipped, otherwise one `expectedKind:"steps"` write with `expectedValues` = that live prefix (entries beyond the list stay unchanged). Top-level `voicing:{voices, voiceStacking, monoMode, ...}` (any `grid.voicing.set` fields) converges Poly Grid voicing: `grid.voicing.get` runs right after offline validation (also for `dryRun`), a device without voicing (Note/FX Grid) fails `invalid_spec` before any write, and only differing fields are written (first phase, `expected` = their live values; equal voicing is `alreadyMatched.voicingFields`). `modules:[]` is allowed only with `prune:true` and a non-empty `namespace` and deletes every namespace module. A name that exists with another type is refused unless `replace:true` (spec-level default or per module): the old module is deleted, the new type inserted under the same name and wired per spec; replace drops undeclared cables on that module (listed in `plan.droppedConnections` and a warning). Use a delimited `namespace` such as `"H: "`: matching is by prefix, so `"H"` would also delete `Hello`. The result carries `notes` (measured 6.1.4 behaviour for the module types used, from `data/grid_notes_6_1_4.json`, value-free) and `warnings` (e.g. oscillator `PITCH_IN` connected while `PITCH_MOD` is 0). Validation is offline against the bundled 6.1.4 schema (`grid.capabilities.hostVersion`); other versions use live `grid.catalog` and check ports/parameters after insertion.

Warnings (also in `dryRun`, rules in `grid_notes_6_1_4.json`): PITCH_IN with PITCH_MOD 0; a phase cable into a step module with `DEVICE_PHASE` on; filter `KEYTRACK` > 0 in a Poly Grid; modules with no connections (Note In excepted); oscillators/envelopes whose outputs are all unused; a raw oscillator `DETUNE` write below 0.5 in magnitude (the scale is raw = cbrt(Hz), range +-3, so raw 0.25 is 0.02 Hz, effectively no detune; `{display:"1.5 Hz"}` converts and does not warn). `dryRun` stays read-only and adds `wouldFail:[{code,message}]` for what a real apply would be refused for: transport playing/recording (`unsafe_state`), `{display}` writes the host converts itself (`display_unverified`), an unreadable target (then `plan` is empty). A real apply returns `diagnosticsMarker` taken right after the build (pass it as `host.diagnostics` `sinceMarker`). Unknown parameter/port errors list the valid ids and near or case-insensitive matches; overlap errors name the blocker as `'customName' (Type@x,y)`.

The first unclean outcome (host error, `unknown`, `partial`, `mismatch`) stops the run with no retry. Result: `{status: applied|unchanged|dryRun|partial|failed|unknown, applied:{inserted,renamed,moved,paramsWritten,connections,disconnected,deleted}, alreadyMatched:{modules,positions,params,connections}, steps, moduleIds, warnings?}`; when stopped also `failure:{phase,method,response}` (raw host response) and `notDispatched`. `dryRun` returns `planned` counts and `plan` (moves of inserted modules are decided after insertion). Re-applying a spec converges: reused work costs reads only. `pruneAll:true` (mutually exclusive with `namespace`/`allowOutsideDisconnect`; implies `prune` and `replace`; `modules:[]` allowed) manages the whole device for generator specs whose modules span many prefixes: every live module the spec does not declare (unnamed ones included, `external` excepted) is deleted, a same-named module of another type is replaced, and every undeclared input of a declared module is disconnected. Deletes run before moves and inserts, so freed footprints are reusable; all of it is in the `dryRun` plan (`deletes`, `replaces`, `connections`) and in `warnings` (`pruneAll: deleting/replacing/disconnecting ...`). It is destructive: run `dryRun` first. Use ONE spec per Grid device (sections as namespaces inside it, so cross-section cables are expressible); two specs sharing a namespace with `prune` delete each other's modules.

#### `grid.export` / `grid.graph`: read a live patch by names (client-side)

Not host methods: both page `grid.get` (all pages, `graph_incomplete` rather than a partial read; params pages of 64) and join UUIDs to names. Args: `D`, optional `namespace` (customName prefix), `includeParams` (`changed` default for export / `none` default for graph / `all`; `changed` = differing from the bundled 6.1.4 defaults).

`grid.export` returns `{status:"exported", spec, moduleCount, connectionCount, unnamed?, warnings?}`, where `spec` is a `grid.apply` spec for the device: `target`, `modules:[{name, type, x, y, params?}]` (raw values; enum as `{label}`; strings; step arrays as `{steps}`), `connections:[{from:"name.OUT", to:"name.IN"}]`, `voicing` on a Poly Grid (whole device only), and with `namespace`: only that prefix, `namespace`, and `external` (outside modules the kept cables reference). Applying the export to the same device is `unchanged`. A module without a unique `customName` is named `_<type>_<x>_<y>` and listed in `unnamed` (warning); `grid.apply` matches unnamed live modules by that name, but modules sharing a customName must be renamed first. `outPath` (absolute, `overwrite` as `grid.render`) writes the spec JSON and omits `spec` from the result.

`grid.graph` returns `{status:"observed", modules:[{name, type, x, y, size:[w,h], params?, unnamed?}], connections:[{from, to}], external?}`: the same names, for reading a patch.

`grid.apply` additions: `external:["X: sum", ...]` names live modules that cables may reference without declaring them (checked after the first read, `invalid_spec` if missing or not unique; type, position and params untouched, never pruned or deleted). `prune` only disconnects unlisted inputs of declared modules inside `namespace`; inputs of declared modules outside it are kept and named in a warning (`X: sum.IN2 (from H: add.OUT)`) unless `allowOutsideDisconnect:true`, which cuts them and lists them in the warning and in `plan.connections`. (Without `namespace` every declared module is in scope, as before.)

#### `grid.render`: layout image (client-side)

Not a host method: the Python client (MCP tool and `bitwig-agent-rpc grid.render`) pages `grid.get` (structure only, 128 per page, until `window.total` is reached; `graph_incomplete` rather than a partial drawing) and fetches parameters only for Comment modules (their `TEXT`). Read-only toward Bitwig; the only side effect is the file at `outPath`. Args: `D`, `outPath` (absolute normalized; `file_exists` unless `overwrite:true`), `format` `svg` (default) or `png` (via `rsvg-convert`, else `magick`; otherwise `invalid_params`), `namespace` (customName prefix highlighted, others dimmed), `showConnections` (default true), `scale` (0.25..4). Modules are drawn at grid x/y with their width/height, coloured by category (one table in `grid_render.py`: sequencing, random, pitch, oscillator, envelope, filter, fx, output, visualization, text, other), titled by `customName` (else type) with the type below, Label modules as headers, Comment modules with their text, cables from output to input side.

Result: `{status:"rendered", outPath, format, bytes, imageSize, moduleCount, connectionCount, boundingBox:{x,y,width,height}, categories, overlapCount, overlaps:[[a,b]...] (footprint pairs, max 50), unconnectedCount, unconnected (max 50; Label/Comment excluded), sections:[{prefix,moduleCount,boundingBox}] (from `"P: "` name prefixes), density (occupied cells / bbox cells), namespace?}`.

#### `audio.route`, `audio.capture`, `audio.analyze` (client-side, no host call)

Verify what Bitwig outputs without hearing it. Linux/PipeWire only for route/capture (`unsupported_platform`, `not_dispatched` elsewhere or without `pw-link`/`pactl`/`pw-record`); all subprocesses use explicit argument lists and a 5 s timeout. Errors use the usual `{code,message,outcome}` envelope.

- `audio.route {mode: silent|restore|status}`: only the links of ports `Bitwig Studio:out1/out2` are touched. `silent` creates/reuses the null sink `bwtest`, saves the previous targets in `$XDG_CACHE_HOME/bitwig-agent/audio-route.json` (default `~/.cache`) before moving the links to `bwtest:playback_FL/FR`; `restore` re-links exactly the saved targets, drops the `bwtest` links and deletes the state file. Idempotent. `bitwig_not_found` when no output link exists. Result: `links:[{from,to}]`, `silent`.
- `audio.capture {seconds 0.5..120, outPath, overwrite?, fromStart?, allowAudible?, soloTrack?, stopOthers?}`: `outPath` is an absolute `.wav`, refused if it exists (`file_exists`) unless `overwrite:true`. Requires silent routing (`not_silent`) unless `allowAudible:true`, which only waives that requirement. The recording always comes from Bitwig's own output ports: a dedicated `pw-record` node (unique name `bwagent-capture-<pid>-<id>`, no autoconnect, 48 kHz stereo s32) is linked from `Bitwig Studio:out1`/`out2` (checked with `pw-link -o`; `bitwig_not_found` otherwise) with `pw-link`, so other applications and the default sink monitor are never recorded. Only the links it created are removed afterwards; existing links are never changed. `fromStart` (default true): `transport.set` playing=false, positionBeats=0, start recording, playing=true, wait `seconds`, playing=false, stop `pw-record` with SIGINT. `fromStart:false` never touches the transport. `soloTrack` really solos that track: it reads every track's solo (`tracks.list` + `tracks.get`; `solo_unreadable` and `unknown_track` are `not_applied`), sets `solo` on the target and clears it on other soloed tracks (`tracks.set`; the host has no exclusive-solo write), and restores every changed state afterwards, also on failure. It still refuses (`not_isolated`) while other tracks have playing launcher clips unless `stopOthers:true` stops them first. Result: `path, durationSeconds, peak, peakDb, rms, rmsDb, clipping (peak>=0.999), silent, source:{ports,node}`, plus `soloed, previousSolo, unsoloed, restored[, restoreFailed]` with `soloTrack`.
- `audio.analyze {path, mode: level|onsets|mono_pitch|probe|loudness|bands, bpm?, skipSeconds?, method?: flux|envelope, threshold?, windowSeconds?, key?, spectrogramPath?}`: offline, any platform, stdlib only (16/24/32-bit PCM or float WAV, channel 0; headers left unfinalized by `parec` are tolerated). Times are seconds from file start. `level`: `peak, rms, silenceRatio, windows[{t,peak,rms}]`. `onsets`: rising crossings of `threshold` (default 0.15) times the 5 ms peak envelope; `silent:true` below about -40 dBFS. `mono_pitch`: onsets plus the dominant spectral peak 10 ms later as fractional MIDI (4096-point FFT: monophonic, fundamental-dominant material only) with `summary{pitchClasses, range, intervals, stepwiseRatio, repeatRatio, leaps, leapRecoveryRatio, tuneError}` and, with `bpm`, `grid{positions16, offsetSeconds, onBeatRatio}`. `probe`: signed 10 ms means (at most 2000; page with `skipSeconds`), for a logic/CV signal wired straight to Audio Out. `bands` (channel 0, windows of `windowSeconds`, default 8, each sampling up to 16 Hann frames of 4096 samples): `windows[{t, rms, centroidHz, bandsDb:{sub,low,mid,high,air}}]` with band power relative to the window's total in dB (edges 60/250/2000/8000 Hz, `null` when empty), plus whole-file `stereoCorrelation` (L/R Pearson, the only use of channel 1; `null` for mono). `key` (`"F:aeolian"`; ionian, dorian, phrygian, lydian, mixolydian, aeolian, locrian, harmonic_minor) adds per-window and overall `chroma{inKeyShare, topPitchClasses}` from spectral peaks at 50-1500 Hz folded to pitch classes; drums, noise and inharmonic partials pollute it, so use it on pitched material. `spectrogramPath` (absolute `.png`, replaced if present) writes a 256-row log-frequency spectrogram (30 Hz to 16 kHz, 80 dB range, at most 800 columns) and returns `spectrogram{path,width,height,...}`.
- `audio.analyze mode=loudness` (skipSeconds honored; every channel is read, unlike the other modes): ITU-R BS.1770-4 K-weighting, 400 ms blocks at 75 % overlap, per-channel weights (mono 1, stereo 1+1, six channels as 5.1 in WAV order L R C LFE Ls Rs with 1.41 for surrounds and LFE excluded, other counts all 1), -70 LUFS absolute and -10 LU relative gates. Result: `integratedLufs` (null when no block passes the gate), `momentaryMaxLufs`, `shortTermMaxLufs` (3 s, null under 3 s), `loudnessRangeLu` (EBU 3342: short-term values gated at -70 and -20 LU, 95th minus 10th percentile; null when under 3 s), `samplePeakDbfs`, `truePeakDbtp` and `perChannelTruePeakDbtp`, `gating:{blocks,absoluteGated,relativeGated,relativeThresholdLufs}`, `channelWeights`, `channelLayout`, `limits[]`. Limits: the 48 kHz K-weighting coefficients are the standard's, other rates are the same analog prototype through a bilinear transform; mono reads about 3 LU below the same signal on two speakers; true peak is a 4x windowed-sinc estimate evaluated only on intervals within 6 dB of the sample peak (about ±0.1 dB, not a certified Annex 2 meter); at most 1800 s per call, pure Python (about 2 s per stereo minute); it measures the file, not Bitwig's meters (the guide, §7.1.8, documents only peak/RMS).

#### `grid.probe` (client-side; Linux/PipeWire)

`grid.probe {trackId, deviceIndex, expectedDeviceName, port:"<module name>.<OUT key>", seconds 0.2..20, mode: probe|mono_pitch|onsets|level, allowAudible?, bpm?, skipSeconds?, method?, threshold?, windowSeconds?, timeoutMs ≤ 60000}`. Composed from `transport.get`, `grid.get`, `grid.connections.set`, `audio.capture` and `audio.analyze`: refuses (`not_dispatched`) unless output is on the silent sink (or `allowAudible`) and recording/automation write are observed off, stops a playing transport (it stays stopped, as after `audio.capture`), snapshots the cables into every `Audio Out` of the device, rewires the probe port to one existing Audio Out (the one already wired, else the first; the others are disconnected; no module is created), records from the start of the arrangement, then restores. The restore re-reads the graph and rewrites each Audio Out input by compare-and-set against the probe wiring; an input that someone else changed meanwhile is left alone. Result `{status:"probed", port, audioOut, cablesChanged, restored:true, capture, analysis, transportStopped}`. A capture or analysis error is returned after the restore. If the restore cannot finish the error is `probe_restore_failed` (`outcome:"unknown"`) with `details.left` (inputs still changed, with their original source) or, when the graph itself could not be read, `details.originally` plus `details.restoreError`; nothing is retried.

#### `host.diagnostics` (client-side)

Not a host method except one `status` call (for `instance.pid`). Args: `sinceSeconds` (1..86400, default 300) xor `sinceMarker` (opaque, from a previous result), `maxEvents` (1..500, default 50, newest kept; `droppedOlderEvents` says how many were cut). The Bitwig log (`~/.BitwigStudio/log/BitwigStudio.log`; macOS `~/Library/Logs/Bitwig/BitwigStudio.log` and Windows `%LOCALAPPDATA%\Bitwig Studio\log\BitwigStudio.log` are documented locations, unverified; `BITWIG_LOG_PATH` overrides) is read from the end in 1 MiB chunks, capped at 64 MiB. Not found: `{status:"unsupported", searched, reason}`.

The log is shared by all of the user's instances; each start writes a `Starting application version` header. The section is chosen by the process start time of `status.instance.pid` (Linux `/proc`) against those headers (within 120 s): `attribution.method` `pid_start_time`, else `latest_section`. `attribution.certain` is false, with `uncertainty[]`, when status or the start time is unavailable, a later start exists in the log (lines may interleave), several Bitwig processes run, or the read cap was hit. `sinceMarker` is valid only for the same section and an unchanged log; otherwise it is ignored with a `warnings` entry and `sinceSeconds` applies. Log times are local time.

`grid_rejected` bursts while a Grid build is still inserting modules are expected (the graph is incomplete between inserts and cables); judge only events after the build, using the `diagnosticsMarker` of `grid.apply`.

Result: `{status:"observed", logPath, window, events:[{time, lastTime?, level, component, category, message (<=300 chars), count, detailLines?, gridComponent?, engineReady?}], summary:{counts, totalEvents, engineReady?, gridRejectedComponents?}, marker, attribution, dialogs}`. Identical consecutive events merge into `count`; stack-trace lines are not returned, only counted in `detailLines`. Categories: `grid_rejected` (`component X should be rejected from the network because ...`: the device was dropped from the audio network and is silent), `engine` (`FloatDocument.isEngineReadyChanged(a->b)`), `extension` (warn/error from extension/controller/script components, or an error mentioning them), `exception` (Java `...Exception`/`...Error`, `Caused by`), `dialog`, `other` (other warn/error; info lines are ignored). Known benign noise (`Cannot use realtime priority`, `Analyzing audio...`) is dropped. The extension/controller/exception patterns are heuristic: only `grid_rejected` and `engine` lines were observed natively (Bitwig 6.1.4).

Dialogs: modal UI (Dashboard, Save Project?, Recover Projects) was searched for in the real log and leaves no line; it is not detectable. The only observed signal is the `notifications` logger (e.g. `Update Available - vX: ...`), reported as `dialog` although it is a toast, not proof of a blocking modal.
